# RFC-112: Support Spark Declarative Pipelines

## Proposers

- @cshuo
- @danny0405

## Approvers

- TBD

## Status

RFC reservation: [#19993](https://github.com/apache/hudi/pull/19993)

## Abstract

[Spark Declarative Pipelines (SDP)](https://spark.apache.org/docs/4.1.1/declarative-pipelines-programming-guide.html) lets users define tables and transformations while Spark builds the dependency graph and runs the batch and streaming flows. Hudi provides atomic commits, keyed updates, event ordering, deletes, incremental queries, and table services.

This RFC makes Hudi a supported SDP source and target. It covers catalog-based table creation, materialized views, streaming tables, basic Hudi-to-Hudi incremental reads, and keyed upserts through Hudi's existing writer.

SDP and Hudi retain their existing responsibilities:

- SDP owns dataset declarations, dependency analysis, orchestration, flow checkpoints, retries, and execution order.
- Hudi owns table storage, commit atomicity, record reconciliation, incremental read semantics, and table services.

Users can build the same pipelines today with Spark jobs, Hudi writers or Hudi Streamer, and an external orchestrator. This integration removes much of that glue code while keeping the outputs as ordinary Hudi tables.

## Background

### Spark Declarative Pipelines

Apache Spark 4.1 introduced SDP for declarative batch and streaming ETL. SDP persists two main dataset types:

- A **materialized view**, which has exactly one batch flow that computes a table.
- A **streaming table**, which has one or more streaming flows that append their output to a table.

Users define pipelines in Python or SQL. SDP validates dataset references, builds the dataflow graph, runs independent flows in parallel, and stores Structured Streaming checkpoints in the pipeline storage location.

In the Spark 4.1 implementation, a streaming table flow uses a Structured Streaming append-mode write to `DataStreamWriter.toTable`, and a batch table flow uses append-mode `DataFrameWriter.saveAsTable`. For an existing materialized view, SDP issues `TRUNCATE TABLE`, calls `catalog.alterTable` to reconcile schema and properties, then runs the batch flow. See Spark's [`FlowExecution`](https://github.com/apache/spark/blob/branch-4.1/sql/pipelines/src/main/scala/org/apache/spark/sql/pipelines/graph/FlowExecution.scala) and [`DatasetManager`](https://github.com/apache/spark/blob/branch-4.1/sql/pipelines/src/main/scala/org/apache/spark/sql/pipelines/graph/DatasetManager.scala).

These table operations are the storage-format integration boundary; this RFC does not add a Hudi-specific execution engine.

### Relevant Hudi capabilities

Hudi already provides the required data-plane primitives:

- `HoodieCatalog` can create and load Hudi tables through Spark's catalog APIs.
- The Hudi batch writer supports bulk insert, insert, upsert, insert overwrite, and table insert overwrite operations. An upsert can carry delete-marker records.
- `HoodieStreamingSink` writes Structured Streaming micro-batches and records checkpoint metadata used to avoid recommitting an already committed batch after retry.
- Hudi's streaming source and incremental query modes can expose records changed since a prior instant.

The integration exposes these capabilities through SDP's existing table and flow abstractions, reusing Hudi's writer semantics. The shared truncate, catalog, and streaming-sink fixes described below also affect non-SDP callers and require regression coverage.

### Current gaps

`format="hudi"` is not yet an end-to-end supported SDP contract. Some operations may already work, but table creation, refresh, restart, upsert configuration, and Hudi-to-Hudi chaining are neither documented nor covered by an integration suite.

Materialized-view refresh needs end-to-end validation. SDP 4.1 truncates the target before reconciling its schema and writing the recomputed result. Hudi's current full-table `TRUNCATE TABLE` deletes the table path, including the timeline, and reinitializes its properties. This RFC requires replacing that destructive default with a timeline-preserving replace commit, shipped together with checkpoint-generation isolation. The truncate–alter–append sequence still is not atomic.

The integration must also address:

- SDP table properties and flow-scoped write options must be resolved and passed to the Hudi writer.
- Streaming restart must coordinate the SDP/Spark checkpoint with Hudi's sink checkpoint metadata.
- A Hudi source used through `readStream.table` must preserve incremental offset semantics.
- SDP must carry Hudi's persisted record-key, precombine, and record-merger settings into the existing upsert path. Deletes remain upsert input rows marked by `_hoodie_is_deleted`; Spark append output mode does not replace this contract.

The initial integration depends on these shared Hudi fixes:

| Issue | Required behavior |
| --- | --- |
| [#20369](https://github.com/apache/hudi/issues/20369) | Append to an existing catalog table without reinitializing its location |
| [#20370](https://github.com/apache/hudi/issues/20370) | Propagate sink failure without exiting the shared Connect JVM |
| [#20371](https://github.com/apache/hudi/issues/20371) | Initialize Hudi tables through SDP's catalog create path and reconcile schema/properties idempotently |
| [#20400](https://github.com/apache/hudi/issues/20400) | Give each streaming query ownership of its embedded timeline service across micro-batches, with cleanup on termination |

Today `HoodieStreamingSink` disables the embedded timeline server by default (the HUDI-3636 workaround) and forces direct markers. Without async compaction or clustering, `HoodieSparkSqlWriter` closes the write client after a micro-batch, stopping the server it owns; the sink then retains that closed client. Explicitly enabling the server can therefore fail on the next batch with a refused remote-view connection ([#12652](https://github.com/apache/hudi/issues/12652)). With async services enabled, resources can instead outlive the query. Each SDP flow has its own sink on the shared Connect driver, so query-scoped ownership and cleanup are prerequisites, not JVM-shutdown housekeeping.

### Related work

- Hudi's Spark 4.1 support ([issue #17663](https://github.com/apache/hudi/issues/17663), [PR #17674](https://github.com/apache/hudi/pull/17674)) provides the runtime baseline, but not an SDP contract.
- DataSource V2 read work ([RFC-98](../rfc-98/rfc-98.md), [issue #15023](https://github.com/apache/hudi/issues/15023)) may improve the catalog read path but is not required for the initial integration.
- The [SQL insert-overwrite discussion](https://github.com/apache/hudi/discussions/13815) shows why refresh semantics must be explicit rather than inferred from an append call.
- [Issue #13973](https://github.com/apache/hudi/issues/13973) shows that a latest-state incremental read cannot fully propagate hard deletes. Flows that require complete delete propagation can use Hudi's existing CDC incremental format.
- [Issue #5537](https://github.com/apache/hudi/issues/5537) tracks named-catalog support. The first version uses `HoodieCatalog` as `spark_catalog`.

## Motivation

### Representative use case

A typical order pipeline looks like this:

```text
MySQL/PostgreSQL CDC or Kafka
              |
              v
     bronze_order_events (Hudi)
              |
              v
     current_orders (Hudi)
              |
              v
   daily_order_metrics (Hudi)
```

The bronze table stores incoming events. The current-state table uses a record key and precombine field to reconcile duplicates and out-of-order events, including delete-marker records. Downstream streaming tables consume changed records incrementally, while batch aggregates can be materialized as views.

Today this usually means several Spark applications plus custom handling for table creation, write options, checkpoints, dependencies, and restarts. With SDP, the graph lives in one project and the persisted datasets remain regular Hudi tables that other engines can query.

Related user request issues include:

- #19281: [multi-dataset incremental processing](https://github.com/apache/hudi/issues/19281)
- #5189: [chained incremental Hudi tables](https://github.com/apache/hudi/issues/5189)
- #13973: [downstream delete propagation](https://github.com/apache/hudi/issues/13973).

### User value

1. **Declarative pipelines.** Users define datasets as SQL or DataFrame transformations; SDP manages dependencies, checkpoints, and Hudi writes.
2. **Managed incremental composition.** Hudi already provides incremental reads; SDP composes them into a dependency-aware pipeline, managing execution order, checkpoints, and recovery without separate Spark jobs or hand-written orchestration.
3. **Open outputs.** Each dataset remains a standard Hudi table that can be queried independently of SDP by any Hudi-compatible engine.

SDP does not make arbitrary joins or aggregates incremental; performance benefits apply only to flows that can process changes incrementally.

## Goals

1. Create Hudi tables from SDP datasets through `HoodieCatalog`.
2. Write materialized views with Hudi `bulk_insert` or `insert`, following SDP's truncate-and-recompute refresh sequence.
3. Write SDP streaming tables through Hudi's Structured Streaming sink.
4. Support a basic incremental Hudi-to-Hudi streaming-table chain.
5. Expose Hudi's existing keyed upsert path through SDP, including record-key, precombine, record-merger, and delete-marker handling.
6. Preserve ordinary Hudi write semantics while explicitly documenting and testing the shared catalog, truncate, session-configuration, and sink-failure behavior changes.

## Non-Goals

The first version excludes:

- A complete Hudi DataSource V2 read or streaming-write implementation.
- Atomic materialized-view refresh across truncate, schema reconciliation, and the batch write.
- Automatic cascading full refresh across dependent tables; recovery of a streaming chain requires an explicit coordinated rebuild.
- Cross-table transactions across multiple SDP targets.
- End-to-end exactly-once delivery across an arbitrary external source and Hudi. Guarantees remain scoped to Spark/Hudi micro-batch retries at one target.
- Arbitrary named catalogs for `HoodieCatalog`; the first version uses Hudi as `spark_catalog`.

## Proposed User Experience

The examples below implement the representative order pipeline in dependency order, using Hudi's existing SQL table options and `SET` for flow-scoped write options.

### Pipeline configuration

#### Connect server prerequisites

The `spark-pipelines` CLI executes through Spark Connect. Install the matching Spark 4.1 Hudi bundle and configure the extension, catalog, serializer, Kryo registrator, warehouse, and storage credentials on the **Connect server at startup**. Static settings do not belong in the pipeline YAML's session `configuration` block. Passing them to `spark-pipelines run --conf` is not a substitute for configuring an automatically launched local server.

For example, with a compatible Hudi bundle and Spark Connect dependencies already installed on the server:

```sh
"$SPARK_HOME/sbin/start-connect-server.sh" \
  --jars /opt/hudi/hudi-spark4.1-bundle.jar \
  --conf spark.sql.extensions=org.apache.spark.sql.hudi.HoodieSparkSessionExtension \
  --conf spark.sql.catalog.spark_catalog=org.apache.spark.sql.hudi.catalog.HoodieCatalog \
  --conf spark.serializer=org.apache.spark.serializer.KryoSerializer \
  --conf spark.kryo.registrator=org.apache.spark.HoodieSparkKryoRegistrar \
  --conf spark.sql.warehouse.dir=/warehouse
```

Use a Python environment containing `pyspark[pipelines,connect]==4.1.1` on the client and connect to that server:

```sh
spark-pipelines run --remote sc://host:15002
```

The server also needs the source connector (for example, Kafka) used by the pipeline. The client must not call driver-local Hudi APIs. Paths and credentials in pipeline definitions must be accessible to the server and executors.

#### Pipeline project

The project specifies its datasets and checkpoint storage:

```yaml
name: hudi_orders_pipeline
libraries:
  - glob:
      include: transformations/**
storage: s3://pipelines/checkpoints/hudi_orders_pipeline
catalog: spark_catalog
database: lakehouse
```

These examples describe the proposed contract and require the implementation changes below, including streaming session-option forwarding; they are not claimed to work unchanged on released Hudi versions.

The SQL below assumes that `order_events_source` is an external streaming source containing parsed Kafka or database CDC events. Each `CREATE ... AS SELECT` statement defines both the target dataset and its single flow.

### Streaming table with an append flow

```sql
SET spark.hoodie.datasource.write.operation = insert;

CREATE STREAMING TABLE bronze_order_events
USING hudi
PARTITIONED BY (event_date)
TBLPROPERTIES (
  'type' = 'mor'
)
AS
SELECT *
FROM STREAM order_events_source;
```

SDP owns the checkpoint location and trigger; Hudi commits each micro-batch.

### Streaming table with keyed upserts

```sql
SET spark.hoodie.datasource.write.operation = upsert;

CREATE STREAMING TABLE current_orders
USING hudi
PARTITIONED BY (event_date)
TBLPROPERTIES (
  'type' = 'mor',
  'primaryKey' = 'order_id',
  'preCombineField' = 'event_sequence'
)
AS
SELECT
  order_id, event_sequence, event_date, order_date, state,
  operation = 'DELETE' AS _hoodie_is_deleted
FROM STREAM bronze_order_events;
```

Spark append output mode only controls how each micro-batch reaches the sink; it does not make the Hudi target append-only. `HoodieStreamingSink` still runs the configured Hudi operation, which defaults to `upsert`.

For an existing Hudi table, SDP loads the record key, precombine field, partition fields, and record-merger settings from the table configuration. For a new SDP table, these settings are declared as table properties and persisted by Hudi. SDP does not implement its own deduplication, ordering, merge, or delete path. It validates the schema and configuration, then passes each micro-batch to the existing Hudi writer.

### Batch materialized view

```sql
SET spark.hoodie.datasource.write.operation = bulk_insert;

CREATE MATERIALIZED VIEW daily_order_metrics
USING hudi
PARTITIONED BY (order_date)
TBLPROPERTIES (
  'type' = 'cow'
)
AS
SELECT
  order_date,
  state,
  COUNT(*) AS order_count
FROM current_orders
GROUP BY order_date, state;
```

The first run creates the table and writes the result using `bulk_insert`. Later runs truncate the target, reconcile its schema and properties, and write the recomputed result. The proposed truncate publishes an empty snapshot through a replace commit while preserving timeline history, savepoints, and metadata-table consistency, subject to normal retention.

## Semantics

### Dataset-to-Hudi operation mapping

| SDP dataset/flow                    | Spark 4.1 execution shape                     | Proposed Hudi semantics                                  |
| ----------------------------------- | --------------------------------------------- | -------------------------------------------------------- |
| New materialized view               | Batch append to newly created table           | Hudi `bulk_insert` or `insert`                            |
| Existing materialized view          | Truncate, alter, then batch append            | Replace-commit truncate, then `bulk_insert` or `insert`    |
| Streaming table with an append flow | Append-mode micro-batches                     | Hudi `insert` or `bulk_insert`, configured per flow       |
| Hudi upsert target                  | Append-mode micro-batches                     | Existing Hudi `upsert`                                   |
| Hudi streaming source               | Structured Streaming read with SDP checkpoint | Basic Hudi latest-state incremental source               |

### Materialized-view write mapping

Initial materialization uses Hudi `bulk_insert` or `insert`. For an existing materialized view, Spark 4.1 executes `TRUNCATE TABLE`, reconciles schema and properties through `catalog.alterTable`, then writes the recomputed result through append-mode `saveAsTable`. Hudi uses the same configured write operation after truncate. An empty result leaves the target empty.

These steps are not a single transaction. Readers may see an empty target during refresh. If schema reconciliation or the batch flow fails after truncate, the previous result is not restored, and completed catalog changes remain in effect.

Full-table `TRUNCATE TABLE` must publish one replace commit using `insert_overwrite_table` with an empty dataset. It must replace all existing file groups even with no input rows; an empty-input optimization must not skip the truncate. This retains history and savepoints and updates the metadata table through normal Hudi commit handling. Replaced files remain governed by cleaner retention. An empty recomputation therefore leaves a committed empty snapshot.

This is a shared SQL behavior change, not an SDP-only no-op truncate. The old physical purge may remain an explicit advanced compatibility option, disabled for supported SDP pipelines. Its option name and migration documentation must be defined by the implementation PR. A truncate failure before commit leaves the previous snapshot visible; a failure after commit leaves the committed empty snapshot. History retention does not automatically restore the pre-refresh result.

Materialized views are supported as batch outputs, but not as incremental sources in the initial scope.

### Streaming commit and restart behavior

SDP manages each flow's checkpoint location and uses `Trigger.AvailableNow` for triggered runs. The initial milestone permits one writer per target; fan-in requires the additional concurrency validation in Phase 2.

At sink creation, derive `hoodie.datasource.write.streaming.checkpoint.identifier` from a versioned, deterministic hash of the fully qualified target, flow `queryName`, and normalized absolute `checkpointLocation`. Spark supplies the latter two on the `toTable` writer. Capture them before constructing the sink and use the resulting identifier for both `canSkipBatch` and committed batch metadata. Never use a run ID that changes on ordinary restart, or a flow name alone that survives checkpoint reset. Missing identity inputs must fail initialization for SDP rather than fall back to `default_single_writer`.

Normal restarts retain the identifier and skip only batches already committed for that checkpoint generation. A streaming full refresh creates a new SDP checkpoint directory and performs the replace-commit truncate before rebuilding. The new directory yields a new identifier, so batch 0 is not compared with the old generation's high-water mark. Deleting or replacing checkpoint contents in place is unsupported: resets must allocate a new generation directory. Moving checkpoint storage while retaining a target can replay records, so it requires an explicit rebuild or migration. Ship identifier derivation and timeline-preserving truncate together. Existing direct streaming users with explicit identifiers retain them; upgrading an existing checkpoint from the legacy default requires an explicit migration decision, not a silent identifier change and replay.

A new generation for the same stopped flow is not a second concurrent writer. Distinct flows targeting the same table require OCC and a valid lock provider. Reject a second writer before its first write if these are absent; historical checkpoint entries alone cannot establish whether a writer is active. Phase 2 must implement race-safe writer registration under the table lock and lifecycle cleanup, including crash recovery, before allowing fan-in. Pipeline validation rejects duplicate targets in Phase 1; users must also stop external writers during refresh.

### Full refresh of an upstream streaming source

Refreshing an upstream Hudi table does not propagate row removals to downstream latest-state incremental readers. Retaining the timeline prevents its deletion but does not turn a replace commit into row-level CDC. Therefore, refreshing a source table requires stopping its consumers and explicitly rebuilding all affected downstream tables with fresh checkpoints in dependency order. Spark's selected-table full refresh must not be assumed to cascade automatically.

The source must detect a full-table truncate/overwrite boundary after its saved offset and fail with a rebuild-required error, rather than replay the rebuilt source into an unchanged downstream target. Store and validate table-generation identity in source checkpoint metadata to detect a physical drop/recreation as well. These checks precede returning a batch; if retained history cannot prove continuity, fail closed. Normal clustering replace commits must be distinguished from logical table replacement. Materialized views remain unsupported as streaming sources in the initial scope.

### Configuration ownership and precedence

Configuration is split by ownership:

- **Table identity:** table type, record key, precombine field, partition fields, key generator, and record-merger settings. Hudi persists these values; SDP loads them for existing tables, and a pipeline run cannot silently change them.
- **Write behavior:** operation and writer tuning, supplied through SQL `SET spark.hoodie.*` as flow-scoped write options.
- **Flow execution:** checkpoint location, trigger, retry, and flow identity. SDP owns these values; the Hudi integration maps each flow to a distinct sink checkpoint identifier.

The selected transport is to extend `DefaultSource.createSink` to call `DataSourceOptionsHelper.collectSparkHoodieConfs`, as the batch `createRelation` path already does, and pass the resulting canonical option map to both multi-writer validation and `HoodieStreamingSink`. Capture the active flow SQLConf at sink creation; do not reread mutable session settings on each batch. Explicit writer/storage options take precedence over session `spark.hoodie.*`; session values override Hudi defaults. Table identity remains immutable regardless of precedence. Do not forward bare `hoodie.*` session keys.

This intentionally changes direct `writeStream` behavior when a session carries `spark.hoodie.*`: those settings will now take effect. Document the change and test both ambient session settings and explicit overrides. Keep operation and writer tuning out of shared table properties for new SDP tables; legacy conflicting storage options must be reported rather than letting examples silently use a different operation. The same resolved operation must reach the writer and `canSkipBatch`.

SDP captures the active `SET` values at each flow definition; a `SET` remains in effect for subsequent definitions until overridden. Flow session settings override pipeline session settings and Hudi defaults, subject to the explicit-option precedence above, and must be compatible with the persisted table configuration. The integration strips the `spark.` prefix from write options and reuses `HoodieOptionConfig` to normalize table options. Flows writing to the same target must use compatible concurrency and lock settings. The sink checkpoint identifier is resolved per flow, not shared as a table property.

Invalid properties should fail during SDP `dry-run` when possible, and otherwise before the first write.

### Table services

For triggered SDP runs, recommend inline compaction/clustering, or inline scheduling with execution by a separately managed table-service job. AvailableNow drains and stops, so background services cannot rely on a long-lived query or on JVM shutdown hooks in the shared Connect server. Pipeline completion must wait for configured inline work; externally scheduled work follows its own lifecycle. Test stop/restart cleanup and service recovery without terminating other flows.

Keep Hudi's normal cleaner and archival policies; size retention for the maximum reader lag and refresh frequency. Frequent refreshes accumulate replaced file groups until cleaning. Preserved history is not indefinite retention, and savepoint protection must remain effective. Embedded asynchronous services are not the recommended initial mode until their completion and cancellation lifecycle is validated under SDP.

### Schema and partition evolution

SDP follows Hudi's existing schema and partition evolution rules.

- Hudi-supported additive schema changes may be accepted for streaming tables.
- The initial contract rejects user-column drops, renames, nullability tightening, and unsupported type changes with actionable errors; broader evolution is follow-up work.
- Record-key, precombine, and partition columns must exist in the target schema.
- Partitioning changes fail; SDP does not turn them into an implicit table replacement.

`HoodieCatalog.alterTable` validates the complete set of requested schema and property changes before applying supported changes. The supported change matrix is:

| Change | Initial contract |
| --- | --- |
| `SetProperty` / `RemoveProperty` | Idempotent for unchanged values / absent keys; allow mutable user properties, reject changes or removal of table identity and required reserved properties |
| `AddColumn` | Accept Hudi-supported nullable additions; validate the full request first |
| `UpdateColumnType` | Accept only Hudi-supported compatible widening |
| `UpdateColumnComment` | Apply to user columns |
| `UpdateColumnNullability` | Accept loosening as a no-op where Hudi already treats fields as nullable; reject tightening |
| `DeleteColumn` / `RenameColumn` | Reject user-column changes in the initial scope; ignore reconciliation-only deletion of Hudi system metadata columns |
| Other changes | Reject explicitly, never fail with a pattern-match error |

Normalize aliases through `HoodieOptionConfig` and compare canonical values. Expose declared user properties plus required Spark catalog properties, not internal storage bookkeeping as mutable declaration keys; repeated identical `SetProperty` calls must have no side effects. Do not expose internal Hudi properties as removal candidates.

For the initial V1 fallback, keep metadata-column visibility for ordinary Hudi reads. Ignore `DeleteColumn` requests for the fixed Hudi system metadata columns during reconciliation, so SDP's business-only schema does not remove them. Reject target declarations that include these reserved fields at creation; users must explicitly project business fields as in `current_orders`. Do not indiscriminately strip every `_hoodie_*` name: `_hoodie_is_deleted` is a supported boolean input marker. This makes unchanged reconciliation a semantic no-op without changing ordinary `SELECT *` behavior. The Hudi writer validates the actual input schema against the persisted table configuration using its existing schema reconciliation rules.

For materialized views, Spark invokes `alterTable` after truncate. A schema validation failure can therefore leave the target empty; it does not preserve the previous result. If metadata changes succeed but the batch write fails, those changes remain in effect.

## Implementation

### 1. Catalog integration

Extend and test [HoodieCatalog](../../hudi-spark-datasource/hudi-spark-common/src/main/scala/org/apache/spark/sql/hudi/catalog/HoodieCatalog.scala) so SDP can:

- Handle `createTable(Identifier, TableInfo)` and its `Column[]` delegation explicitly, routing both to Hudi initialization rather than the session-catalog default. A catalog entry with `provider=hudi` is insufficient: `hoodie.properties` and the correct table identity must exist before a sink starts ([#20371](https://github.com/apache/hudi/issues/20371)).
- Persist schema, location, partition transforms, comments, and Hudi table properties.
- Load the created table for both batch and streaming execution.
- Validate the complete alter request before applying supported property and schema changes, preserving Hudi table identity and accepting unchanged properties.
- Reject unsupported partition transforms and incompatible property changes with actionable errors.

The first version configures `HoodieCatalog` as `spark_catalog`; named catalogs are follow-up work.

This path may continue to use Hudi's V1 fallback. Full DataSource V2 support is not required as long as the SDP table contract is met.

### 2. Materialized-view write path

Use Hudi `bulk_insert` or `insert` for the batch result. Update [TruncateHoodieTableCommand](../../hudi-spark-datasource/hudi-spark-common/src/main/scala/org/apache/spark/sql/hudi/command/TruncateHoodieTableCommand.scala) to use the replace-commit contract above and ship it with checkpoint-generation isolation.

Fix existing-table `saveAsTable(..., Append)` in `CreateHoodieTableAsSelectCommand` to insert into the existing Hudi table, respecting the resolved Hudi operation, without reinitializing its location ([#20369](https://github.com/apache/hudi/issues/20369)). Test both managed and external tables. This shared catalog fix is necessary even on a first SDP materialization because SDP creates the target before invoking the batch write.

### 3. Streaming target integration

Route SDP's append-mode `toTable` call through [HoodieStreamingSink](../../hudi-spark-datasource/hudi-spark-common/src/main/scala/org/apache/hudi/HoodieStreamingSink.scala), including table properties supplied by `HoodieCatalog`.

The sink integration will:

- Pass the flow's write operation and persisted keyed-write settings to the existing Hudi writer.
- Preserve the SDP checkpoint location rather than creating a competing checkpoint tree.
- Resolve a stable, per-flow `hoodie.datasource.write.streaming.checkpoint.identifier` and use it for both retry checks and commit metadata.
- Pass through and validate Hudi's existing multi-writer and lock configuration for concurrent flows sharing a target.
- Retain committed-batch deduplication, but throw after bounded sink retries instead of calling `System.exit(1)` ([#20370](https://github.com/apache/hudi/issues/20370)). Let SDP apply `spark.sql.pipelines.maxFlowRetryAttempts`; a failed flow must not kill the shared Connect server or hang other client sessions.

No SDP-specific upsert writer, merge logic, or delete path is introduced.

#### Embedded timeline server and write-client lifecycle

Implement [#20400](https://github.com/apache/hudi/issues/20400) using the ownership pattern in `HoodieStreamer`'s [StreamSync](../../hudi-utilities/src/main/java/org/apache/hudi/utilities/streamer/StreamSync.java):

- Each sink owns one embedded timeline service for its streaming query, initialized lazily from the first batch's resolved write configuration when enabled. Reuse it across commits and pass it to write clients as an externally owned service; replacing a client, for example after a schema change, must not stop the query's service.
- In streaming mode, the sink owns the write client's lifetime. The batch writer must not close it after each micro-batch, and the sink must never reuse a closed client. Keep ordinary batch-writer cleanup unchanged. Any embedded async compaction/clustering shares the sink-managed client and participates in its cleanup.
- A V1 `Sink` has no close hook. Register a `StreamingQueryListener` associated with the query ID and current run ID, not just the flow name, to release resources on normal AvailableNow completion, explicit stop, and failure. Also clean up on sink reset and partial initialization failure. Coordinate async-service shutdown before closing the client and releasing the timeline service; make cleanup idempotent and remove the listener when the query ends. A retry after reset must initialize fresh resources. Neither reset nor a delayed termination event may close another query's resources, including a restarted flow's new sink.
- Release the service's base-path registration using its ownership API (`stopForBasePath`), respecting any underlying service reuse. Stopping one flow must leave other flows and the Connect server usable; JVM shutdown hooks alone are insufficient.
- Once this lifecycle is implemented, remove the sink-specific forced disable and forced `DIRECT` marker overrides. Honor the normal Hudi defaults and explicit user choices, including `hoodie.embed.timeline.server=false` and `hoodie.write.markers.type=DIRECT`. Document this change for direct Structured Streaming users as well as SDP users.

This embedded timeline service supplies file-system views and marker handling; it is distinct from the compaction/clustering scheduling policy in the table-services section.

### 4. Incremental source integration

Validate both catalog-table and explicit Hudi sources in SDP streaming flows. Source progress is restored from the SDP-managed checkpoint and advances with the downstream flow.

Document:

- Initial position behavior (`earliest`, `latest`, or an explicit instant).
- The basic `latest-state` incremental output contract.
- Behavior when required source instants have been archived or cleaned.
- COW and MOR differences, if any, in supported streaming query modes.
- Explicit business-column projection and reserved-field rejection as defined above.
- Reader options through SQL `FROM STREAM table WITH (...)` or Python `readStream.option(...)`; validate propagation through the catalog's V1 fallback. Conflicts with table storage options must produce Spark's normal error rather than promise a per-flow override.
- AvailableNow backlog sizing: the current source lacks `SupportsAdmissionControl` and `SupportsTriggerAvailableNow`. A backlog can be consumed in one large micro-batch. Document this limit and prioritize bounded admission control in the DSv2 source work before streaming-write optimization.

If the checkpoint refers to source history that is no longer available, fail with a recovery error rather than skipping data.

### 5. Upsert configuration and validation

For an upsert target, validate that:

- At least one record-key field is configured and present.
- All partition fields are present.
- Configured precombine fields are present and type-compatible.
- `_hoodie_is_deleted`, when present, is boolean.

These checks only validate the input contract. Hudi's existing writer, precombine, and record-merger logic perform the upsert.

## Failure and Consistency Model

| Failure point                                          | Required outcome                                                               |
| ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Validation fails before truncate starts                 | Existing target remains unchanged                                              |
| Full-table truncate fails before its replace commit completes | Previous committed snapshot remains visible; retry/recover the incomplete operation |
| Schema reconciliation or MV computation fails after truncate | Previous result is not restored; completed metadata changes remain in effect |
| MV batch write fails before commit                     | No completed commit for that write; prior data removed by truncate is not restored |
| Streaming task fails before Hudi commit                 | Spark retries the micro-batch                                                  |
| Streaming flow retries or restarts with its existing checkpoint | Already committed batches for that checkpoint generation are skipped             |
| Source checkpoint crosses a reset or points to expired Hudi history        | Flow fails with an explicit recovery error                                     |
| Pipeline definition changes record key or partitioning  | Validation fails; no implicit migration occurs, but an earlier truncate is not undone |

Hudi writes and the proposed full-table truncate retain per-commit atomicity. A completed truncate followed by failure leaves an empty snapshot with retained history, not an automatically restored prior result. The refresh sequence has no transaction or rollback spanning truncate, catalog changes, and the batch write. Commits from independent SDP flows are not atomic as a group.

## Rollout/Adoption Plan

### Phase 1: Catalog and write contracts with a Connect harness

- Support Spark 4.1.x with `HoodieCatalog` as `spark_catalog`, including the `TableInfo`/`Column[]` create path, idempotent property updates, and schema reconciliation rules.
- Fix existing-table append routing, forward flow session options into the sink, and replace JVM exit with propagated failure.
- Complete the query-scoped timeline-service and write-client lifecycle in #20400, including cleanup on AvailableNow completion, stop, failure, and reset, before declaring the streaming-table path supported.
- Ship replace-commit truncate and per-checkpoint/per-flow identifiers together; validate initial writes, repeat MV refreshes, streaming restarts, full refresh, and keyed upserts/deletes.
- Permit one writer per target; reject unsupported fan-in. Add source reset detection before declaring basic Hudi-to-Hudi chaining supported.
- Enable a Spark 4.1 CI lane in `.github/workflows/bot.yml` (currently commented out) and require the real Connect harness to pass. These are implementation prerequisites, not changes made by this documentation PR.

### Phase 2: Fan-in and source hardening

- Support multiple flows only after OCC/lock validation and race-safe writer registration are implemented and tested.
- Harden incremental reads, expired-history errors, upstream reset detection, explicit downstream rebuilds, and table-service lifecycle handling.

### Phase 3: DataSource V2 streaming read/write

Prioritize admission control and AvailableNow support so backlogs can be split into bounded batches. Add streaming writes when justified; initial support continues through the V1 fallback.

### Phase 4: Row-level operations for Auto CDC

Evaluate Spark's evolving Auto CDC APIs separately from the Spark 4.1 baseline. The [Auto CDC path identified in review](https://github.com/apache/hudi/pull/19997#discussion_r4291597685) uses DataFrame `mergeInto(...).merge()` in `foreachBatch`; supporting that path requires DSv2 row-level operations (`SupportsRowLevelOperations`). Hudi's SQL-rule `MergeIntoHoodieTableCommand` alone does not implement that API. SCD1/2 support is follow-up work, not an initial keyed-upsert guarantee.

Each phase is independently testable. Shared fixes require non-SDP regression tests as well as the pipeline suite.

## Alternatives Considered

### Reuse destructive truncate

Not selected as the supported default. Deleting the table directory loses history and savepoints and couples sink deduplication reset to destructive storage cleanup. Keep physical purge only as an explicit compatibility opt-in outside supported SDP refreshes.

### Timeline-preserving truncate followed by append

Selected. An empty `insert_overwrite_table` replace commit preserves ordinary SQL truncate's empty-table semantics without refresh detection. A subsequent append materializes the new result. This retains history but leaves an empty window and no cross-step rollback; checkpoint-generation isolation is a mandatory companion change.

### Treat truncate as a no-op and overwrite on append

Not adopted. This requires distinguishing SDP refresh from ordinary SQL truncate, handling empty results in the overwrite path, and coordinating separately applied catalog changes. The selected replace-commit truncate preserves SQL truncate semantics without introducing a refresh-specific protocol. A DataSource V2 writer's `truncate()` hook does not by itself replace SDP's preceding SQL `TRUNCATE TABLE` call.

### Wait for complete DataSource V2 support

Full DataSource V2 read and write support is not required for the initial integration. SDP can use `HoodieCatalog` for table management while Hudi batch and streaming writes continue through the existing V1 writer and `HoodieStreamingSink`. The roadmap prioritizes source admission control, then streaming writes and row-level operations needed by Auto CDC.
