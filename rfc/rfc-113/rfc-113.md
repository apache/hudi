## Abstract

A Spark query over a Hudi table runs entirely on the JVM today: Parquet decode, merge-on-read log
merging, and every operator above the scan. Apache DataFusion Comet makes the operators native but
cannot read Hudi tables, and hudi-rs can read Hudi tables natively but is not wired into Spark. This
RFC packages Comet with Hudi as `hudi-native-spark-bundle` and adds a Comet scan operator that
reads Hudi file slices through hudi-rs, so that a Spark query over a Hudi table executes natively
end to end, with the existing JVM read path as the fallback for anything the native scan does not
support.

## Background

### Where Comet stops today

[Apache DataFusion Comet](https://datafusion.apache.org/comet/) replaces Spark's physical operators
with native DataFusion operators, converting a plan operator by operator and falling back per
operator. Its own Parquet scan is native; every other `FileFormat` is left to Spark and bridged. A
Hudi read plans as `FileSourceScanExec` over `HoodieFileGroupReaderBasedFileFormat`, which Comet
rejects (`Unsupported file format`). With `spark.comet.convert.parquet.enabled=true` everything
above the scan converts, so a join of two CoW tables plans as `CometSortMergeJoin` over
`CometNativeShuffle` feeding `CometHashAggregate`, with the two Hudi scans on the JVM underneath.
The scan output has to be bridged into native memory: copy-on-write tables go through
`CometSparkColumnarToColumnar`, merge-on-read tables read row by row (`Batched: false`) and go
through `CometSparkRowToColumnar`, a per-cell conversion that dominates the read.

Hudi users on Spark get none of this without a jar swap they have to assemble and version-match
themselves, and even then the scan, the part of the plan that is Hudi's, stays on the JVM.

### What hudi-rs provides

[hudi-rs](https://github.com/apache/hudi-rs) 0.5.0 ships a file group reader with Java-parity
merge semantics: MOR log merge with commit-time and event-time ordering, delete blocks, custom
payload synthesis, schema evolution, and table versions 6/8/9. `FileGroupReader::new_with_options
(base_uri, options)` opens the table from `hoodie.properties` (merge mode, ordering field, payload
class, table version) and `read_file_slice_from_paths(base, logs, ReadOptions)` merges one slice
with projection and filters, given nothing but the table base path and the slice's file paths. The
log scan honors an instant upper bound (`hoodie.read.end.timestamp`), the same rule the Java file
group reader uses to admit log records for snapshot and time-travel reads. It also exposes a C ABI.
hudi-rs 0.5.0 and Comet 1.0.0 pin the same Arrow, DataFusion, and object_store majors; the design
does not depend on that (see "Version boundary"), it only benefits from it.

### The Iceberg precedent inside Comet

Comet 1.0.0 already carries one complete non-Parquet native table scan. `CometIcebergNativeScanExec`
recognizes an Iceberg scan on the JVM, serializes a `*Common` message shared across partitions plus
a per-partition task list, and a native `iceberg_scan.rs` operator reads through iceberg-rust,
pinned by git rev in Comet's `Cargo.toml`. Per-partition data injection is pluggable through a
`ServiceLoader`-discovered `PlanDataInjector`, added upstream for out-of-tree contributions. The
Hudi scan follows this shape exactly. The one thing Comet lacks is a hook for an external jar to
contribute a scan conversion for a `FileFormat` it does not recognize. Details in
[Appendix D](#d-comet-100-internals-relied-on).

## Implementation

Two deliverables, both opt-in: `hudi-native-spark-bundle`, which packages Comet next to Hudi so the
operators above the scan run natively (PR #19674), and the native Hudi scan, a Comet operator that
reads file slices through hudi-rs (PR #20170). The Comet-side changes for the scan (a proto
message, a native operator, a `ServiceLoader` hook) ship as a changed-files-only overlay on a
pinned Comet commit, built from source into the bundle and verified against the pinned upstream on
every build; hudi-rs enters the artifact only as a statically linked crate inside Comet's native
library.

### Architecture

```
Spark driver (JVM)                                   Spark executor: Comet native block (Rust)
─────────────────────────────────────────────        ─────────────────────────────────────────────
spark.read.format("hudi")                            CometHashAggregate / CometSortMergeJoin / ...
  │ Hudi file index, pruning, slice grouping                        ▲ Arrow batches (DataFusion 54)
  ▼                                                                 │
FileSourceScanExec(HoodieFileGroupReaderBasedFileFormat)            │ FFI_ArrowArray / FFI_ArrowSchema
  │ CometScanRule: unsupported format ──► CometExternalV1ScanProvider (overlay hook, ServiceLoader)
  ▼                                                                 │
HudiCometScanProvider (hudi-spark-comet)                  HudiScanExec (overlay, hudi_scan.rs)
  gates ► extract slices ► HudiScanCommon + per-task HudiScan       │ one FileGroupReader per task
  ▼                                                                 │ per slice: Parquet decode,
CometHudiNativeScanExec (CometLeafExec + CometScanWithPlanData)     │ log merge, deletes, projection
  commonData / perPartitionData bytes ───► HudiPlanDataInjector ───►│ (hudi-rs, statically linked)
                                          (splices this task's slices into the serialized plan)
```

Planning stays on the JVM, reading moves native. Spark's plan already knows, per task, the exact
file slices as of the query instant; the native operator needs only the table base URI, the read
options, the projected schema, and each slice's base and log paths relative to the base URI. There
is no table config mirroring and no schema negotiation: hudi-rs reads `hoodie.properties` itself
and the operator aligns its output to the schema Spark asked for.

|---|---|

Compiled only under `-Dcomet.hudi.build`. |

| `packaging/hudi-native-spark-bundle/comet/` (native scan, Comet overlay) | `COMET_PIN`, `OVERLAY_MANIFEST`, `build_comet.sh`, and `overlay/` holding the `HudiScan` protos, `hudi_scan.rs`, the planner match arm, the `hudi` crate dependency, and the `CometExternalV1ScanProvider` hook in `CometScanRule`. Layout in [Appendix C](#c-overlay-layout-and-build). |

### Comet is packaged, not relocated

Comet's native library binds through JNI symbols (`Java_org_apache_comet_Native_*`) and loads its
shared objects from classpath resources under `org/apache/comet/<os>/<arch>/`. A relocated Comet
builds cleanly and fails on the first native call, so the bundle keeps Comet's packages as they
are. Two consequences the bundle README documents: a cluster-provided `comet-spark-*.jar` at
another version resolves class by class, first jar wins; and the bundle needs Java 17 (Comet ships
class file version 61 bytecode) and Linux (Comet ships `linux/aarch64` and `linux/amd64` natives
only). The module produces one bundle per Spark version Comet publishes for (3.4, 3.5, 4.0, 4.1)
and produces nothing, rather than a "native" jar with no native code, for the others.

### Version boundary

Comet and hudi-rs compile into one native library, but their Arrow and DataFusion majors are
allowed to differ. Batches cross from hudi-rs to Comet over the Arrow C data interface
(`FFI_ArrowArray` / `FFI_ArrowSchema`), which is ABI-stable across Arrow majors: zero-copy, the
same mechanism hudi-rs's `jvm-ffi` crate uses to hand batches to a JVM. Tokio is version-unified,
so hudi-rs futures run on Comet's global runtime directly. When the majors match, as they do for
Comet 1.0.0 and hudi-rs 0.5.0, cargo unifies the crates and the crossing is a same-crate round
trip.

This independence is already needed. Comet `main` has moved to arrow 59 / DataFusion 55, while
hudi-rs stays on arrow 58 until its Lance dependency has an arrow 59 release. A Comet pin bump
does not wait for hudi-rs: the two Arrow stacks coexist in `libcomet` at the cost of binary size.
hudi-rs's own DataFusion adapter (`hudi-datafusion`, a `TableProvider`) is deliberately not used,
because DataFusion traits do not share across DataFusion majors. The compatibility contract is the
`FileGroupReader` API and the C ABI.

### Eligibility gates and fallback

`HudiCometScanProvider` converts only what the native path is known to read identically to the
JVM path, and otherwise returns the plan untouched so the JVM scan runs. In v1 that means
snapshot queries on Parquet-based tables at table versions 6, 8, and 9 (MOR at 8 and above),
non-nested output types, partition columns stored in the data files, and partition-column
projection only under identity key generators. Data filters are not pushed natively: Spark's
`FilterExec` stays above the scan and Comet converts it, so correctness never depends on native
filtering. The full list and the reason behind each gate are in [Appendix B](#b-eligibility-gates).

The provider passes `hoodie.read.end.timestamp=<queryTimestamp>` so hudi-rs bounds log-record
admission the way the Java reader does. This is what makes time travel exact and protects snapshot
reads from log files appended by concurrent writers.

Runtime gate: `spark.comet.scan.hudi.enabled=true` (off by default), plus Comet's usual configs and
`spark.memory.offHeap.enabled=true`.

### Build and pinning

The overlay couples Hudi to Comet internals at one commit, so drift has to fail loudly:

- **Pinned base.** `COMET_PIN` names the upstream commit (the `1.0.0` tag) and the hudi-rs rev the
  overlay's `Cargo.toml` pins, so "what exactly is in this bundle" has one answer.
- **Manifest check.** `OVERLAY_MANIFEST` records the upstream blob SHA of every file the overlay
  replaces. `build_comet.sh` verifies them before overlaying, so a pin bump that touched one of
  those files fails with the file name instead of clobbering upstream changes.
- **Distinct coordinates.** The source build is versioned `1.0.0-hudi-<n>`, so the bundle can never
  silently resolve the unmodified Central artifact, and `~/.m2` holds both side by side. Without
  `-Dcomet.hudi.build` the bundle is byte-identical to the one PR #19674 produces.
- **hudi-rs pin.** By git rev today, the pattern Comet uses for iceberg-rust; a crates.io version
  pin once the bundle moves to a released hudi-rs.

The overlay is the "not yet upstreamed" vehicle. The exit is upstreaming the
`CometExternalV1ScanProvider` hook (68 generic lines), after which the Hudi operator can stay an
overlay or move into Comet the way the Iceberg scan did.

### Risks & caveats

- **Pre-v8 MOR log appends.** On table version 6 a log file can receive blocks after the planned
  instant, so the path set no longer determines the data. v1 gates native MOR to version 8 and
  above; relaxing it needs the reader's instant filtering verified on appended blocks.
- **Table version 10.** `master` writes version 10 and hudi-rs reads up to 9, so the native scan
  only serves tables written at 9 or below until hudi-rs catches up.
- **DataSource V2.** The hook sits in Comet's V1 dispatch. If Hudi's Spark read moves to DSv2
  (RFC-98), recognition and slice extraction move to Comet's V2 dispatch, as the Iceberg scan does;
  the proto, operator, and injector are unaffected.
- **Overlay format.** Full copies of modified Comet files (thousands of lines for a few dozen
  changed) versus patches. Copies survive offset drift and are what the manifest checks; patches
  are what a reviewer wants to read. To be settled before the code PR leaves draft.
- **Binary size and licensing.** hudi-rs's crate graph joins Comet's inside `libcomet` (the Spark
  3.5 jar grew from 45 MB to 51 MB). The bundle's LICENSE and NOTICE have to enumerate that graph,
  which the bundle PR already flags for Comet's own crates.
- **Pin bumps re-run the matrix.** Every Comet or hudi-rs bump is a full end-to-end re-validation,
  not a compile.

## Rollout/Adoption Plan

**Step 1, the bundle lands.** `hudi-native-spark-bundle` ships as new coordinates only; no existing
artifact, module, or code path changes behavior. Adoption is a jar swap plus Comet's configs, on
Java 17 and Linux.

**Step 2, the native scan lands behind two gates.** The `hudi-spark-comet` module compiles only under
`-Dcomet.hudi.build` and the scan conversion runs only under `spark.comet.scan.hudi.enabled`. The
default build of the bundle keeps consuming the published Comet, so the bundle's behavior is
unchanged until the native scan is ready to become the default.

**Step 3, the source-built Comet becomes the bundle default** once CI builds it (Rust toolchain
and caching in the bundle-validation lane), the S3 storage option passthrough, nested types, and
streaming per-slice reads land, and the Spark 4.x wiring is validated. The bundle validation
keeps running against the default build as the non-regression guard.

Nothing is removed. Users without Comet are unaffected. Website docs cover the bundle, the build
flag, and the runtime config.

## Test Plan

The RFC is validated when:

- [ ] Bundle validation writes CoW and MOR tables with deterministic rows and asserts exact
      join and aggregate results plus `CometSortMergeJoin` in the plan, so it fails both on a wrong
      value and on Comet being packaged but not executing. MOR coverage that catches a scan
      ignoring log files, and a columnar-versus-row bridge assertion on the CoW path, are added per
      review.
- [ ] Native scan validation, gated on `NATIVE_HUDI_SCAN=1`, reads the same CoW and MOR tables
      (multiple commits, updates, and deletes, so MOR has real log files) through the native scan
      and asserts row-level equality with the JVM read, `CometHudiNativeScan` in the plan, Comet
      operators above it, and zero `CometSparkRowToColumnar` on the MOR path.
- [ ] Time travel through the native scan is identical to the JVM time-travel read and native.
- [ ] A CoW-join-MOR probe runs `CometSortMergeJoin` with both sides through the native scan.
- [ ] Disabling `spark.comet.scan.hudi.enabled` leaves the JVM plan untouched, and the bundle
      validation passes without `-Dcomet.hudi.build`.
- [ ] The validation counts executed checks, not only failures (`spark-shell` swallows
      per-statement exceptions).
- [ ] CI builds Comet from the pinned commit with the overlay and runs the above on Linux.

## Appendix

### A. Proto shape

Much smaller than Iceberg's, because hudi-rs self-configures from `hoodie.properties`:

```
HudiScanCommon: table_base_uri, map<string,string> options (storage + hoodie.* read options,
                including hoodie.read.end.timestamp), required_schema (SparkStructField list,
                drives ReadOptions.projection), session_timezone,
                scan_hash (canonicalized plan hash, disambiguates self-joins)
HudiFileSlice:  base_file_path, repeated log_file_paths      // relative to table_base_uri
HudiScan:       common + repeated file_slices                // this partition's slices, injected per task
```

The plan carries a placeholder `HudiScan` (URI and hash, zero slices). Per task, the injector
splices the common bytes and that partition's slice bytes, keyed by `(uri, scan_hash)`. One Spark
partition per file slice, taken from `scanExec.selectedPartitions` before Spark's file splitting so
no slice is duplicated.

### B. Eligibility gates

Any failure leaves the plan untouched.

| Gate | Reason |
|---|---|
| Snapshot query only (no incremental, CDC, bootstrap) | The slice mapping differs (`HoodiePartitionCDCFileGroupMapping`) or the read is not a slice read. |
| No dynamic partition pruning | The partition set is not final at conversion time. |
| Non-empty required schema | Count-star has no columns to project. |
| Output types Comet can serialize; no nested types in v1 | `serializeDataType` rejects them or alignment is unverified. |
| Table version in {6, 8, 9} | hudi-rs reads these; `master` writes 10. |
| MOR at table version 8 or above | Pre-v8 log files can receive appends after the planned instant. |
| Parquet base files, no multiple base formats | hudi-rs decodes Parquet. |
| Partition columns stored in data files | `hoodie.datasource.write.drop.partition.columns=true` leaves the base file without values Spark expects; literal append is a follow-up. |
| Log-bearing slice only under a MOR format | Read-optimized safety. |
| Every slice has a base file; every path under the base URI | hudi-rs joins relative paths onto its storage root. |
| Partition-column projection only under Simple, Complex, Nonpartitioned key generators | The JVM appends path-parsed values, the native scan reads stored columns; they agree only for identity generators. |

### C. Overlay layout and build

```
packaging/hudi-native-spark-bundle/comet/
  COMET_PIN            # upstream repo + commit + version suffix; hudi-rs commit
  OVERLAY_MANIFEST     # for each modified upstream file: path + expected upstream blob SHA
  build_comet.sh       # clone @ commit -> verify manifest -> copy overlay -> versions:set -> make release -> mvn install
  README.md
  overlay/
    native/Cargo.toml, native/core/Cargo.toml, native/Cargo.lock      # hudi crate dependency
    native/proto/src/proto/operator.proto                             # HudiScan messages
    native/core/src/execution/operators/hudi_scan.rs                  # new operator (about 250 lines)
    native/core/src/execution/operators/mod.rs, planner.rs, jni_api.rs, planner/operator_registry.rs
    spark/.../comet/rules/CometScanRule.scala                         # provider dispatch before the fallback
    spark/.../comet/rules/CometExternalV1ScanProvider.scala           # new trait + ServiceLoader registry
```

Build order, local and CI:

```
mvn install -DskipTests -Dspark3.5                                   # Hudi artifacts
packaging/hudi-native-spark-bundle/comet/build_comet.sh              # JDK 17 + Rust toolchain
mvn package -DskipTests -Dspark3.5 -Dcomet.hudi.build \
    -Ddatafusion.comet.version=1.0.0-hudi-<n> -pl packaging/hudi-native-spark-bundle
```

The native operator: `HudiScanExec` implements DataFusion's `ExecutionPlan`, opens one
`FileGroupReader` per partition on Comet's runtime, reads each assigned slice eagerly
(`read_file_slice_from_paths` with the projection), exports the batch through the Arrow C
interface, casts and reorders columns to Spark's output schema, and yields through a
`RecordBatchStreamAdapter`. The streaming variant (`read_file_slice_from_paths_stream`) is a
follow-up.

### D. Comet 1.0.0 internals relied on

- `CometScanRule.transformV1Scan` dispatches `FileSourceScanExec`; the "Unsupported file format"
  fallback is the `CometScanExec.isFileFormatSupported` check in its `HadoopFsRelation` arm. The
  overlay consults the external provider immediately before that fallback.
- `PlanDataInjector` (`spark/.../comet/operators.scala`) is discovered through `ServiceLoader`
  (`META-INF/services/org.apache.spark.sql.comet.PlanDataInjector`). The trait is
  `private[comet]`, so the Hudi implementation lives in an `org.apache.spark.sql.comet` package,
  the same arrangement any out-of-tree contribution uses.
- `CometScanWithPlanData` is Comet's marker trait for leaf scans carrying `commonData` and
  `perPartitionData`; `findAllPlanData` collects them generically and `CometExecRDD` ships them to
  tasks keyed by injector key. Leaf scans are self-serializing (`nativeOp`), so `QueryPlanSerde`
  needs no registry change.
- The fused native block takes its partition count from the leaf's `outputPartitioning`; the exec
  overrides it with `UnknownPartitioning(perPartitionData.length)` or execution fails with
  "All per-partition arrays must have length 0".
- `HadoopFsRelation.dataSchema` excludes partition columns; availability checks union
  `partitionSchema`.
- Comet's `rust-toolchain.toml` pins channel stable, above hudi-rs's MSRV.

### E. Validation evidence

18 of 18 end-to-end checks on the current pins (Spark 3.5.5 local, macOS arm64, Corretto 17,
`spark.comet.scan.hudi.enabled=true`, off-heap 2g, tables written at table version 8):

- CoW (300 rows, 2 commits with updates): snapshot rows and aggregate identical to the JVM read;
  plan shows `CometHudiNativeScan`; disabled config leaves the JVM plan untouched.
- MOR (300 rows, 150 log-file updates, 20 deletes, 280 surviving): identical rows and aggregate;
  no `CometSparkRowToColumnar`; the aggregate runs as `CometHashAggregate` over
  `CometNativeShuffle` directly on the scan.
- Time travel at the first commit: identical to the JVM time-travel read and native.
- CoW join MOR: `CometSortMergeJoin` with both sides through `CometHudiNativeScan`, zero row
  bridges (assertions count within the AQE plan's final section, since the plan string repeats
  the tree in its initial section).

Executed plan for the MOR aggregate, fully native, projection pushed to two columns:

```
CometColumnarToRow
+- CometSort
   +- CometExchange rangepartitioning(...), CometNativeShuffle
      +- CometHashAggregate [Final]
         +- CometExchange hashpartitioning(...), CometNativeShuffle
            +- CometHashAggregate [Partial]
               +- CometHudiNativeScan [fare, partitionpath], file:/.../native_scan_mor, 3
```

Baseline Comet source build verified on macOS arm64 (`make release PROFILES="-Pspark-3.5"`
produces `comet-spark-spark3.5_2.12` with the platform native embedded); the same flow in CI
produces the Linux natives.

### F. Version landscape

| Component | arrow | DataFusion | object_store | Note |
|---|---|---|---|---|
| Comet 1.0.0 (pinned, tag `3a7a2c437cc7`) | 58.4 | 54.1 | 0.13.2 | latest release |
| Comet `main` | 59.2 | 55.1 | 0.13.x | next pin target |
| hudi-rs 0.5.0 (pinned rev `eb95599c`, released 2026-09-10) | 58 | 54.1 (optional feature, not enabled here) | 0.13.2 | Lance blocks arrow 59 |

The Comet build pulls the `hudi` crate with default features, which exclude `hudi-datafusion`, so
`libcomet` contains Comet's DataFusion only. hudi-rs's Arrow is core-wide (Parquet decode, merge
kernels, Avro to Arrow), but every integration boundary it exposes (this operator, the C++ bridge,
`jvm-ffi`, Python) is the Arrow C interface, so its Arrow major never leaks.
