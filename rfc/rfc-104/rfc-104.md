# RFC-104: Unify schema evolution on schema-on-read

## Proposers

- @voonhous

## Approvers

- @<TBD>
- @<TBD>

## Abstract

Hudi today supports two parallel schema-evolution paths:

1. **Schema-on-read** — gated by `hoodie.schema.on.read.enable=true`. Hudi tracks schema changes itself in `.hoodie/.schema/<instant>.schema_commit` using a versioned, field-ID-based `InternalSchema`. Supports add, drop, rename, and type-promote without rewriting data files.
2. **Schema-on-write** (the default) — relies on Spark/Avro to reconcile schemas implicitly during the write. No Hudi-side schema metadata is produced. Effectively limited to add-column and Avro-compatible type promotions; rename and drop are not safely supported.

Two paths impose costs on both sides of the system. Users have to learn which knob produces which behavior and discover that the default path silently fails to track renames and drops. Developers maintain parallel branches in every write entry point (`if (schemaOnReadEnabled) ... else ...`) and a large Avro-based reconciliation surface (`HoodieAvroUtils.rewriteRecordWithNewSchema` and friends, referenced from ~74 files) whose semantics are weaker than the schema-on-read alternative.

This RFC proposes:

- **End state**: schema-on-read is the only schema evolution path. The schema-on-write code path is removed.
- **Mechanism**: a staged migration — close engine gaps under all four supported readers (Spark, Flink, Hive MR, Trino), make schema-on-read silently correct as a non-default in 1.x, lazy-bootstrap an `InternalSchema` for legacy tables on first write under the new default, then delete the schema-on-write branches in the next major (2.0).
- **Type plane** (Workstream D): one mapper per boundary between `HoodieSchema` and each engine, format and catalog, each declaring per type whether it maps natively, lossily or not at all, with shared tests, and the logical types RFC-99 left open. It moved here from RFC-88 so it does not wait on RFC-88's reader / writer design; it decides which schema each boundary sees, not how readers and writers are built.
- **Scope boundary**: this RFC removes the *schema-evolution semantics* layered on top of Avro. It does not remove Avro as a serialization format. The broader Avro removal is addressed by RFC-46, RFC-87, and RFC-99 — RFC-104 stacks on those without re-litigating their scope.

## Background

> **Code references**: this RFC names classes and methods rather than file/line locations, since line numbers go stale quickly. Symbol references survive line shifts and are stable to grep against any branch. Where the RFC was drafted against a specific snapshot, the master commit at the time of writing is recorded in the PR that introduced the RFC.

### The two paths today

Configuration entry point — `HoodieCommonConfig.SCHEMA_EVOLUTION_ENABLE` (the `hoodie.schema.on.read.enable` config, default `false`):

```
hoodie.schema.on.read.enable = false  // default
```

The two paths diverge at well-defined points in the write pipeline:

- **Write client**: `BaseHoodieWriteClient#commit` invokes `BaseHoodieWriteClient#saveInternalSchema` when schema-on-read is enabled. That method reconciles incoming and previous `InternalSchema` via `AvroSchemaEvolutionUtils.reconcileSchema`, persists schema history via `FileBasedInternalSchemaStorageManager#persistHistorySchemaStr`, and stamps `SerDeHelper.LATEST_SCHEMA` into commit metadata. When schema-on-read is disabled, only `SCHEMA_KEY` (Avro schema string) is set; no Hudi-side schema metadata is produced.
- **Spark writer**: `HoodieSchemaUtils#deduceWriterSchema` is the entry; it dispatches to `deduceWriterSchemaWithReconcile` or `deduceWriterSchemaWithoutReconcile` based on `shouldReconcileSchema` and on whether an `InternalSchema` was injected upstream by `HoodieSparkSqlWriter`.
- **Write handle**: in the `HoodieWriteHandle` constructor, `schemaOnReadEnabled = !isNullOrEmpty(config.getInternalSchema())`. Many downstream branches hang off this flag.
- **Reader**: `HoodieFileGroupReader` plus `FileGroupReaderSchemaHandler` consume `Option<InternalSchema>` if present and project records by field ID via `InternalSchemaMerger`; otherwise they fall back to Avro projection.

Schema-on-read uses a versioned `InternalSchema` tree (`org.apache.hudi.internal.schema.InternalSchema`) where each field has a stable integer ID. Renames are name-only changes preserving the ID; drops are tombstones. Field-ID projection at read time fills missing columns with nulls and applies safe type promotions per `SchemaChangeUtils`.

|-----------------------------------|------------------------------------------------------------|-------------------------------------------------------------------------------------------|

### Surface area to remove

- The `HoodieAvroUtils#rewriteRecordWithNewSchema` family plus `HoodieAvroUtils#reconcileSchemas` — referenced from a wide range of call sites across writers, log readers, merge handles, the Hive reader, and HiveSync. Many of these uses are *serialization* (still needed for Hive serde and similar); this RFC removes only the *evolution semantics* uses.
- `if (schemaOnReadEnabled)` / `!isNullOrEmpty(internalSchema)` branches across the write client, write handle, and Spark writer (the `schemaOnReadEnabled` field on `HoodieWriteHandle` and its propagation through subclasses).
- Configs subsumed by the unified path: `hoodie.write.schema.allow.auto.evolution.column.drop`, `hoodie.avro.schema.validate`, `hoodie.datasource.write.reconcile.schema` (already deprecated in 0.14.1).

### Schema conversions are duplicated per boundary

`HoodieSchema` is Hudi's schema API (RFC-99), but the code that maps it to other systems is spread across engines and
formats, and the copies disagree:

* **Parquet `MessageType` is produced three ways**: by Spark's row writer from `StructType`
  (`HoodieRowParquetWriteSupport`), by Flink's `ParquetSchemaConverter`, and by the parquet-avro path through Hudi's copy
  of the Avro converter. Lance's Arrow schema is produced two ways (Spark from `StructType` with a BLOB patch, Flink from
  `HoodieSchema`).
* **Three Hive mappings**: `HiveTypeUtils` (hadoop-mr), `HiveSchemaUtil` (Hive sync) and the Flink catalog's
  `HiveSchemaUtils`. Trino builds its column types from the Hive type strings in the metastore rather than from
  `HoodieSchema`.
* **No loss is declared anywhere.** Examples, all on master:
  * Flink TINYINT / SMALLINT and Spark `ByteType` / `ShortType` map to `HoodieSchemaType.INT`, so the width is lost
    from the table schema and what reaches the file depends on the write path: Spark's `bulk_insert` writes INT32 +
    `INT(16)` (Lance `Int16`), Spark's other paths write plain INT32 (Lance `Int32`), Spark's row writer throws on
    `ByteType`, and Flink cannot write the column at all
    ([apache/hudi#18974](https://github.com/apache/hudi/issues/18974)). RFC-99's mapping table says SMALLINT is
    `INT32 + INTEGER(16)`. The case study in Workstream D traces it end to end.
  * UUID is declared `binary` by Hive sync and `STRING` by BigQuery sync.
  * BigQuery sync maps every DECIMAL to `NUMERIC`, which holds at most scale 9.
  * Hive sync stores VECTOR as `binary`.

### Relationship with related RFCs

- **RFC-33** (completed) introduced `InternalSchema` and the schema-on-read read/write semantics. RFC-104 builds on RFC-33 by making it the only path.
- **RFC-46** (completed) decoupled the record-merge API from Avro. RFC-104 is the schema-side counterpart: it removes the Avro-based *schema-evolution* semantics, leaving Avro as a pure serialization format on the way out.
- **RFC-78** (in progress, 1.0 migration) defines the upgrade contract for legacy tables. RFC-104's lazy-bootstrap behavior plugs into the same upgrade machinery.
- **RFC-87** (in progress, Flink Avro elimination in writer) is a hard prerequisite for closing the Flink-writer engine gap.
- **RFC-99** (completed with a reduced scope, [#20488](https://github.com/apache/hudi/pull/20488)) defines `HoodieSchema`, the type set and the interoperability table that Workstream D's mappers are tested against.
- **RFC-88** (under review) owns the data plane: one reader and one writer per file format over a row type each engine wraps. Its readers and writers take their physical schema from Workstream D's `FormatSchemaMapper`; Workstream D does not depend on RFC-88.

**Layering decision**: RFC-104 keeps `InternalSchema` as the on-disk schema-evolution format under `.hoodie/.schema/`. Moving its in-memory shape onto `HoodieSchema` builds on Workstream D's mappers and comes later. RFC-104 must not lock in Avro-shaped serialization choices in `InternalSchema` that this later step would then have to undo.

## Implementation

The migration is split into three orthogonal workstreams (A to C). They can run in parallel; the default flip and the deletion are sequenced after all three are green. Workstream D, the type plane, is independent of the default flip and ships on its own schedule.

### Workstream A — Engine parity

All four reader/writer paths must read and write through `InternalSchema` before the default flips.

1. **Spark** — already supported; tighten test coverage to also exercise schema-on-read CI for the full suite, not just schema-evolution tests.
2. **Flink writer** — track and land RFC-87. Wire `OptionsResolver` and `InternalSchemaManager` into the post-RFC-87 `HoodieFlinkInternalRow` write path so the writer can reconcile and persist `InternalSchema` exactly as the Spark client does.
3. **Hive MR reader** — close the input-format gap. Wire `FileGroupReaderSchemaHandler` into the path used by `HoodieInputFormatUtils`. The recent BLOB/ArrayWritable fixes (commits `07a7410452`, `7c2c56ec31`) opened up this module and are a useful template for how to thread the Hudi reader through the legacy Hive serde.
4. **Trino plugin** — net-new work. The plugin must read `.hoodie/.schema/` and project Parquet/ORC records by field ID. Two concrete options are:
   - Reuse the Spark `FileGroupReaderSchemaHandler` semantics by extracting the field-ID projection logic into an engine-neutral helper in `hudi-common` and consuming it from the Trino plugin.
   - Re-implement field-ID projection inside the Trino plugin against Trino's native page-source API, mirroring (but not sharing) the Spark code.
   The RFC discussion must pick one before Trino implementation starts. **Open question**.
5. **HFile base files** — HFile lacks any schema-evolution support and one disabled test in `TestHoodieHFileReaderWriter` documents this. Two options:
   - Add field-ID projection on the HFile reader.
   - Formally exclude HFile base files from schema evolution and surface a clear runtime error when the user tries to evolve a schema on an HFile-base table.
   The RFC discussion must pick one. **Open question**.

### Workstream B — Metadata table and indexes

The metadata table currently disables some functionality when schema-on-read is on (the `HoodieMetadataConfig` TODO). Before the default flip:

- Audit the column-stats index against schema-on-read tables with renamed and dropped columns. Stats must continue to be queryable (and possibly invalidated) when a column's name changes or a column is dropped.
- Audit record index and secondary index for the same scenarios.
- Add metadata-table integration tests that mutate schema (add/drop/rename) and assert that all indexes remain consistent with the latest table schema and that point lookups continue to work.

### Workstream C — Lazy bootstrap

For tables created before the default flip, schema-on-read history does not exist. On the first write under the new default:

1. Resolve the latest commit's Avro schema via `TableSchemaResolver`.
2. Synthesize an `InternalSchema` from it via `InternalSchemaConverter` (Avro → InternalSchema).
3. Persist via `FileBasedInternalSchemaStorageManager#persistHistorySchemaStr` (the same path the schema-on-read writer already uses).

Rules:

- Bootstrap is lazy: a read on a legacy table without schema history continues to use Avro projection until the next write.
- Bootstrap is one-shot: subsequent commits write incremental `InternalSchema` versions normally.
- Bootstrap discards no data; field IDs are assigned freshly on bootstrap. **Pre-bootstrap rename and drop history is not recoverable** — schema-on-write never tracked it. The RFC's release notes must state this explicitly.
- Bootstrap reuses `AvroSchemaEvolutionUtils.reconcileSchema` and `InternalSchemaConverter`; no new conversion logic is introduced.

### Workstream D - Type plane: mapping `HoodieSchema` to every boundary

Every engine, format and catalog maps to and from `HoodieSchema` through exactly one mapper, which declares what it loses, so a type behaves the same everywhere and a new type or boundary is added once. Today each schema-on-read engine also carries its own `InternalSchema` converter (`SparkInternalSchemaConverter`, `InternalSchemaConverter` for Avro); with one mapper per boundary, field ids have one place to cross each boundary.

Ownership:

| Piece | Owner |
|---|---|
| `HoodieSchema`, the type set and RFC-99's interoperability table (the spec) | RFC-99 |
| Mappers, `TypeSupport`, catalog renderers, shared tests; the types RFC-99 left open; Avro-free internals | Workstream D |
| Reader / writer, `HoodieRecord` / `KeyGenerator` | RFC-88 |

Scope:

- No existing file is rewritten. Where today's write paths differ (the `INT(16)` label, list structure, `bytes`-backed decimals), a converged mapper only emits layouts that a current writer already emits and keeps today's knobs as `PhysicalOptions` with today's defaults, so supported readers already read every file it writes. A layout no current writer produces waits for a table-version bump.
- The persisted schema does not change. It stays Avro JSON plus Hudi logical-type properties, read and written through `HoodieSchema.parse` / `toString` (RFC-99).

![Proposed: type plane](type-plane-proposal.svg)

Every mapper converts between `HoodieSchema` and exactly one other type system. Rules:

1. Engines, formats and catalogs never map to each other directly; everything goes through `HoodieSchema`.
2. Every mapper declares, per `HoodieSchemaType` and options, whether it maps `NATIVE`, `LOSSY` (with a reason) or
   `UNSUPPORTED`. Writing an unsupported type fails fast. `LOSSY` may drop type identity, never values; a format that
   cannot store a type's values exactly declares it `UNSUPPORTED`.
3. `fromX(toX(s))` equals `s` for every `NATIVE` type. For `LOSSY` types, the hint (the table schema) or a marker
   stored in the target restores the type, as described below.
4. Every mapper passes the same shared test kit, and RFC-99's interoperability table is its expected output.
5. Types are added to `HoodieSchema` first, then to every mapper. This rule is not negotiable. Two tiers:
   * Anything that affects values, physical layout, comparison or ordering (integer width, signedness, decimal
     precision and scale, timestamp unit, time zone semantics, collation, CHAR padding) is a `HoodieSchemaType`, which
     every mapper must declare. An engine type that needs one and has none fails fast in `fromTypeSystem` instead of
     widening.
   * Details that affect none of these (VARCHAR length, a timestamp's declared precision within its unit such as Flink
     TIMESTAMP(4) stored as micros, engine column options) are per-field properties on `HoodieSchema`
     (`HoodieSchemaField.getProp` / `addProp`). Every mapper preserves them and may ignore them.
     VARCHAR(n) qualifies because its values, bytes and ordering are those of STRING; only the write-time length check
     is engine-specific. CHAR(n) does not: Spark and Hive pad it and compare it ignoring trailing spaces.

   Storing a semantic distinction in a property of a wider type (SMALLINT as INT32 plus an engine annotation) is not
   allowed: a property one mapper reads and another ignores is how Spark and Flink write the same SMALLINT column
   differently today, and every such property becomes an unwritten type that each new mapper must rediscover. With this
   rule, nothing is lost on the way in and writers never need the engine schema.

**Why writers take two schemas today.** Each carries something the other lacks. The engine schema has integer width:
Spark's `ByteType` and `ShortType` become INT in `HoodieSchema`, so only a writer that still holds the DataFrame's
`StructType` (Spark's `bulk_insert`) writes INT(16); every path that rebuilds its schema from `HoodieSchema` writes plain
INT32 (case study below). `HoodieSchema` has timestamp millis,
decimal byte width, VECTOR, VARIANT and BLOB, which the Spark writer reads from it. Rule 5 moves the first group into
`HoodieSchema`; the second is already there, and only the mappers read it. Writers then take `HoodieSchema` alone.

**Where identity is lost.** Values are never lost (rule 2). Type identity is, and only on arrows that leave
`HoodieSchema`:

```
Write:  Engine --(1)--> HoodieSchema --(2)--> Format
Read:   Format --(3)--> HoodieSchema --(4)--> Engine
Sync:                   HoodieSchema --(5)--> Catalog
```

| Arrow | Lossy | Cases on master |
|---|---|---|
| (1) Engine to `HoodieSchema` | never (rule 5) | restores what (4) dropped |
| (2) `HoodieSchema` to format | a few types | Parquet: VECTOR as FIXED_LEN_BYTE_ARRAY, BLOB as a plain group, UUID as string (the UUID annotation is off by default). Avro: INT16 as `int` once INT16 lands |
| (3) Format to `HoodieSchema` | never | restores what (2) dropped |
| (4) `HoodieSchema` to engine | most cases | Spark: TIMESTAMP(3) as micros, TIME as int / long, UUID and ENUM as string, FIXED as binary, VECTOR as array, BLOB as struct. Flink: the same, except timestamps and TIME keep their precision |
| (5) `HoodieSchema` to catalog | some types | Hive: VECTOR, UUID and FIXED as binary, ENUM as string, BLOB as struct. Never read back, so nothing to restore |

**How identity comes back.** On (1) and (3), `fromTypeSystem(x, hint)` and `fromPhysicalSchema(x, hint)` resolve each
column in this order:

1. `NATIVE`: the target's own type is exact, such as Parquet INT(16) or TIMESTAMP(MILLIS).
2. `LOSSY` with a hint: the hint is the table schema, including its per-field properties, which Hudi already persists
   as `HoodieSchema` JSON: `schema` in
   each commit's metadata, `hoodie.table.create.schema` in `hoodie.properties`, the `SCHEMA` header of each log block,
   and `hoodie.avro.schema` in the write config during a write. It never crosses a lossy arrow, so it restores the
   exact type. Every Hudi read and write has one.
3. `LOSSY` without a hint, as in `CREATE TABLE` from engine DDL or a reader without the timeline: a per-column
   `hudi_type` marker stored in the target. Today Spark keeps it in `StructField` metadata (VECTOR, BLOB), and Parquet
   and Lance keep `hoodie.vector.columns` in the file footer (VECTOR only). Every `LOSSY` declaration names its marker,
   and targets with field or file metadata write one for every `LOSSY` column. Flink types have no metadata, so Flink
   relies on the hint.

The shared test kit checks `from(to(s))` equals `s` for every `LOSSY` type, once with the hint and once with the marker
alone.

**Example: VECTOR(128, FLOAT), written and read by Spark.**

1. (1) Spark hands over `emb array<float>`. The hint says `emb` is VECTOR(128, FLOAT), so `SparkTypeMapper` returns
   VECTOR. On `CREATE TABLE`, before any hint exists, the `hudi_type` marker on the `StructField` says the same.
2. (2) `ParquetSchemaMapper` writes FIXED_LEN_BYTE_ARRAY(512) and the footer marker `emb:VECTOR(128)` (FLOAT is the
   default). `LOSSY`: Parquet has no vector type, but all 512 bytes are kept.
3. (3) `ParquetSchemaMapper` sees FIXED_LEN_BYTE_ARRAY(512) and returns VECTOR(128, FLOAT) from the hint, or from the
   footer marker for a reader without the timeline. With neither, the column reads as FIXED(512), values intact.
4. (4) `SparkTypeMapper` returns `array<float>` with the `hudi_type` marker in the field metadata. `LOSSY`: Spark has no
   vector type, and the next write restores it in step 1.

A few more types, written and read back by Spark:

| Type | (1) Spark to `HoodieSchema` | (2) `HoodieSchema` to Parquet | (4) Spark reads back |
|---|---|---|---|
| SMALLINT | `ShortType` to INT16 (today INT) | INT32 + INT(16), the same from Flink | `ShortType`, `NATIVE` |
| TIMESTAMP(3) | `TimestampType`; the hint keeps millis | INT64 + TIMESTAMP(MILLIS), `NATIVE` | `TimestampType` (micros), `LOSSY` |
| DECIMAL(10,2) as fixed(8) | `DecimalType(10,2)`; the hint keeps the declared width | FIXED_LEN_BYTE_ARRAY(8), `NATIVE` | `DecimalType(10,2)`, `NATIVE` |
| Flink TIMESTAMP(9) | no `HoodieSchema` type: fails fast, as today | n/a until nanosecond TIMESTAMP lands | n/a |

Narrowing a value to the declared column type on write (Spark micros into a millis column) is a cast to the table
schema, as today, not a mapper loss.

```java
public final class TypeSupport {
  public enum Level { NATIVE, LOSSY, UNSUPPORTED }
  Level level();
  String reason();                  // required for LOSSY, e.g. "VECTOR stored as Hive binary"
}

/** Engines and catalogs that have their own type system: Spark, Flink, Trino, Hive, BigQuery. */
public interface TypeSystemMapper<T> {
  String typeSystem();
  T toTypeSystem(HoodieSchema schema, MappingOptions opts);
  HoodieSchema fromTypeSystem(T type, Option<HoodieSchema> hint);
  TypeSupport support(HoodieSchemaType type, MappingOptions opts);
}

/** File formats: the only place a physical schema is decided. */
public interface FormatSchemaMapper<P> {
  HoodieFileFormat format();
  P toPhysicalSchema(HoodieSchema schema, PhysicalOptions opts);   // legacy list / decimal, NTZ, shredding, blob encoding
  HoodieSchema fromPhysicalSchema(P physical, Option<HoodieSchema> hint);   // HoodieSchemaRepair folds in here
  TypeSupport support(HoodieSchemaType type, PhysicalOptions opts);
}

/** Catalog sync: table-level rules on top of a TypeSystemMapper. Types turn lossy only inside the mapper. */
public interface CatalogSchemaRenderer<C> {
  String catalog();
  C render(HoodieSchema schema, List<String> partitionFields, SyncOptions opts);
  SchemaDifference diff(HoodieSchema tableSchema, C current);
}
```

Mappers are discovered with `ServiceLoader` through a `SchemaMappers` registry, so engine and sync modules plug in
without `hudi-common` depending on them.

The logical types RFC-99 specified but did not implement (TINYINT, SMALLINT, unsigned integers, FLOAT16, nanosecond
TIMESTAMP, LARGE_STRING, LARGE_BINARY, DATE64, DURATION, DICTIONARY) land here, each together with its declaration in
every mapper and its rows in the shared tests. CHAR(n) is added the same way, though RFC-99 did not specify it. Until a
type lands, engines keep today's mapping for it (CHAR to STRING with padded values, TINYINT and SMALLINT to INT); rule
5's fail-fast applies to a type only once its `HoodieSchemaType` exists (Workstream D rollout, step 2). A type is not
done until every mapper declares it. Each new type also specifies how it persists in the Avro JSON schema (a
logical-type property old readers ignore) so older readers degrade to the base type.

#### Case study: one SMALLINT column

One `SMALLINT` column, traced through master
([b0d16f9](https://github.com/apache/hudi/tree/b0d16f94b3b5f4ce790a9a09e41ebf891b35a53e)) and through this design.

**Today.** What lands in the file for the same column, by engine, operation and format:

| Engine, operation | Parquet | Lance | ORC | Vortex | Avro log block (write version < 10) | Native log file (version 10) |
|---|---|---|---|---|---|---|
| Spark `bulk_insert` (row writer, the default) | INT32 + `INT(16)` | `Int16` | unsupported | unsupported | n/a | n/a |
| Spark upsert, insert, compaction, clustering (SPARK record type) | INT32 | `Int32` | throws | 32-bit | Avro `int` | INT32 |
| Spark upsert, insert, compaction, clustering (AVRO record type, the default) | INT32 | unsupported | `int` | unsupported | Avro `int` | INT32 |
| Flink, any operation | fails | fails | unsupported | unsupported | fails | fails |

Why each row differs:

* `bulk_insert` keeps the DataFrame's own `StructType` (`HoodieDatasetBulkInsertHelper`), and
  `HoodieInternalRowFileWriterFactory` passes it to the writers, so they see `ShortType`. That factory only writes
  Parquet and Lance.
* Every other Spark path rebuilds the `StructType` from `HoodieSchema` (`HoodieSparkFileWriterFactory`), after
  `HoodieCreateRecordUtils` widens short to int, so the writers see `IntegerType`. That factory throws for ORC and HFile.
* The AVRO record type converts rows to `GenericRecord` against the `HoodieSchema` Avro schema, where the column is
  `int`; `HoodieAvroFileWriterFactory` writes Parquet, ORC and HFile, not Lance or Vortex.
* Flink rebuilds a `RowType` from `HoodieSchema` (column `INT`) for every writer, and `ParquetRowDataWriter`,
  `LanceRowDataWriter` and the Avro converter behind `HoodieFlinkRecord.getAvroBytes` call `getInt` on a field the row
  holds as a short. `HoodieRowDataFileWriterFactory` writes only Parquet and Lance.
* Clustering reads with the table schema (`int`), so it rewrites `bulk_insert`'s `INT(16)` files as plain INT32.

Every path reads the column back as `int`. The production classes that decide what a SMALLINT becomes, each making
part of the decision:

Spark: schema conversion and row preparation

1. `HoodieSparkSchemaConverters` (hudi-spark-client): maps `ByteType` / `ShortType` to INT, and INT back to
   `IntegerType`.
2. `HoodieInternalRowUtils` (hudi-spark-client): caches the `StructType` rebuilt from `HoodieSchema` that writers are
   built with, and the row writer that rewrites short to int.
3. `HoodieCreateRecordUtils` (hudi-spark-common): rewrites upsert and insert rows to that `StructType`, widening short
   to int.
4. `HoodieDatasetBulkInsertHelper` (hudi-spark-client): keeps the DataFrame's own `StructType` for `bulk_insert`.

Spark: writer selection

5. `HoodieSparkFileWriterFactory` (hudi-spark-client): rebuilds the `StructType` from `HoodieSchema` for Parquet,
   Lance and Vortex; throws for ORC and HFile.
6. `HoodieInternalRowFileWriterFactory` (hudi-spark-client): passes the DataFrame's `StructType` through; Parquet and
   Lance only.

Spark: format writers

7. `HoodieRowParquetWriteSupport` (hudi-spark-client): `ShortType` to INT32 + `INT(16)` with `getShort`, `IntegerType`
   to plain INT32, `ByteType` to `Unsupported type`.
8. `HoodieSparkLanceWriter` (hudi-spark-client): hands its `StructType` to lance-spark.
9. `LanceArrowUtils` (lance-spark): `ShortType` to Arrow `Int16`, `IntegerType` to `Int32`.
10. `LanceArrowWriter` (lance-spark): writes the values into those vectors.
11. `HoodieSparkVortexWriter` (hudi-spark-client, JDK 17 sources): writes from the rebuilt `StructType`.

Spark: AVRO record type and Avro log blocks

12. `HoodieSparkUtils` (hudi-spark-client): `createRdd` turns rows into `GenericRecord`s for the AVRO record type.
13. `AvroConversionUtils` (hudi-spark-client): builds the row-to-Avro converter against the `HoodieSchema` Avro schema.
14. `AvroSerializer` (four copies: hudi-spark3-common, hudi-spark4.0.x, hudi-spark4.1.x, hudi-spark4.2.x), reached
    through `SparkAdapter.createAvroSerializer`: `ShortType` to Avro `int`.
15. `HoodieSparkRecord` (hudi-spark-client): `getAvroBytes` for Avro log blocks under the SPARK record type.

Shared Avro writers

16. `HoodieAvroFileWriterFactory` (hudi-hadoop-common): Parquet, ORC and HFile; not Lance or Vortex.
17. `HoodieAvroWriteSupport` (hudi-hadoop-common): the parquet-avro write support.
18. `AvroSchemaConverterWithTimestampNTZ` (hudi-hadoop-common): Avro `int` to Parquet INT32.
19. `AvroOrcUtils` (hudi-hadoop-common): Avro `int` to ORC `int`.

Flink

20. `HoodieSchemaConverter` (hudi-flink-client): maps `TINYINT` / `SMALLINT` to INT, and INT back to `INT`.
21. `HoodieRowDataFileWriterFactory` (hudi-flink-client): Parquet and Lance only.
22. `RowDataParquetWriteSupport` (hudi-flink-client): builds the file schema from `HoodieSchema`.
23. `ParquetSchemaConverter` (hudi-flink-client): converts through a `RowType`, so plain INT32; its SMALLINT branch is
    unreachable.
24. `ParquetRowDataWriter` (hudi-flink-client): its `IntWriter` calls `getInt` on a field the row holds as a short.
25. `HoodieFlinkLanceArrowUtils` (hudi-flink-client): converts through a `RowType`, so `Int32`; its SMALLINT branch is
    unreachable.
26. `LanceRowDataWriter` (hudi-flink-client): `getInt` on a short; its `SmallIntWriter` is unreachable.
27. `HoodieFlinkRecord` (hudi-flink-client): `getAvroBytes` for Avro log blocks.
28. `RowDataQueryContexts` (hudi-flink-client): builds the row-to-Avro converter from a `RowType` rebuilt from
    `HoodieSchema`.
29. `RowDataToAvroConverters` (hudi-flink-client): `getInt` on a short.

Catalog

30. `HiveSchemaUtil` (hudi-hive-sync): INT to `int`.

That is 30 classes in nine Hudi modules plus lance-spark, three of them with unreachable SMALLINT branches, and the
answer also depends on which `StructType` each Spark operation hands down. `TestParquetSchemaConverter` normalizes
SMALLINT to INT before comparing, so the tests encode the loss.
[apache/hudi#18974](https://github.com/apache/hudi/issues/18974) tracks it and names adding the type to `HoodieSchema`
as the fix consistent with RFC-99.

**With this design.**

1. Write, (1) engine to `HoodieSchema`: `SparkTypeMapper` maps `ShortType`, and `FlinkTypeMapper` maps `SMALLINT`, to
   INT16 (rule 5). The table schema persists it as Avro `int` with an `int16` logical-type property; older readers see
   `int`.
2. Every write operation builds the file schema from the table schema through `FormatSchemaMapper`, so `bulk_insert`,
   upsert, compaction and clustering write the same layout.
3. Write, (2) `HoodieSchema` to format: `ParquetSchemaMapper` maps INT16 to INT32 + `INT(16)`, `ArrowSchemaMapper` to
   `Int16`, `OrcSchemaMapper` to `short`. One case in each mapper.
4. Values: the engine row type each writer rebuilds from `HoodieSchema` now has `ShortType` / `SMALLINT`, so the
   writers take the short branches they already have (`HoodieRowParquetWriteSupport` in Spark; `ParquetRowDataWriter`,
   `LanceRowDataWriter` and `RowDataToAvroConverters` in Flink, unreachable today). No path calls `getInt` on a short.
5. Read, (3) format to `HoodieSchema`: `ParquetSchemaMapper.fromPhysicalSchema` maps INT32 + `INT(16)` to INT16; plain
   INT32 files written before INT16 resolve through the hint.
6. Read, (4) `HoodieSchema` to engine and catalog: Spark gets `ShortType`, Flink `SMALLINT`, Hive sync `smallint`.

Existing tables keep their INT columns as INT, since an INT in an old schema may be a real INT or a widened SMALLINT
(#18974); every path then writes plain INT32 for them, `bulk_insert` included, because every path writes the table's
type. Tables created after INT16 lands get INT16.

"What is a SMALLINT on disk" then has one answer per format, in one place: the INT16 case of each `FormatSchemaMapper`,
checked for every engine by the shared test kit with RFC-99's table as the expected output. The schema decisions spread
over the 30 classes above become one INT16 case in each of:

1. `SparkTypeMapper`: `ShortType` to and from INT16.
2. `FlinkTypeMapper`: `SMALLINT` to and from INT16.
3. `HiveTypeMapper`: INT16 to `smallint`, used by `HiveCatalogRenderer`.
4. `ParquetSchemaMapper`: INT16 to and from INT32 + `INT(16)`.
5. `ArrowSchemaMapper`: INT16 to and from `Int16` (Lance, Vortex).
6. `OrcSchemaMapper`: INT16 to and from `short`.
7. `AvroSchemaMapper`: INT16 to Avro `int` with the `int16` property.

The engine writers keep their own short branches until RFC-88 replaces them with one row wrapper per engine.

### Deletion targets (for the 2.0 cut)

Inventory of what gets removed once schema-on-read is the only path:

- `if (schemaOnReadEnabled)` / `!isNullOrEmpty(internalSchema)` branches in:
  - `BaseHoodieWriteClient#commit` and `BaseHoodieWriteClient#saveInternalSchema` (the schema-on-read leg becomes unconditional; the schema-on-write leg is removed)
  - The `schemaOnReadEnabled` field on `HoodieWriteHandle` and every conditional that consumes it in subclasses
  - `HoodieSparkSqlWriter` and `HoodieSchemaUtils#deduceWriterSchema` (collapse `deduceWriterSchemaWithReconcile` and `deduceWriterSchemaWithoutReconcile` into a single path)
- The Avro-based schema-evolution overloads of `HoodieAvroUtils#rewriteRecordWithNewSchema`. Keep only the serialization-compatibility uses (Hive serde and similar); the *evolution* logic lives entirely in `SchemaChangeUtils` plus `FileGroupReaderSchemaHandler`.
- Config `hoodie.schema.on.read.enable` becomes a no-op. **Open question**: keep as no-op for one major after 2.0, or remove immediately.

## Rollout/Adoption Plan

### Workstream D rollout

Independent of the stages below; each step ships on its own.

1. **Mappers.** Add `TypeSupport`, the mapper interfaces and the registry, with implementations that wrap today's
   converters. No behaviour or on-disk change. Shared-test failures (INT16, UUID, DECIMAL, VECTOR) become the bug list.
2. **Converge mappings.** First the missing types (INT8, INT16, CHAR and the remaining RFC-99 types) land in
   `HoodieSchema` and every mapper. Then callers switch to the mappers, one path at a time; the duplicated converters
   are deleted; repair moves into the format mappers; Trino takes its columns from `HoodieSchema`. A path keeps today's
   converter, and its writer keeps the engine schema, until the types it relies on have landed, so no engine schema
   accepted on master is rejected and no writer loses information it uses today.

### Stage 1 — Close gaps, default still off (1–2 minor releases of 1.x)

- Land Workstreams A, B, C above.
- Add a deprecation warning when `hoodie.schema.on.read.enable=false` is explicitly set; default remains `false`.
- Schema-on-read CI runs the full test suite, not just schema-evolution tests, on every PR.

### Stage 2 — Flip the default (one minor release of 1.x)

- Default `hoodie.schema.on.read.enable=true`.
- Existing tables auto-bootstrap on first write (Workstream C).
- Soak for one full minor-release cycle before Stage 3 is allowed to merge. Any schema-on-read regression during the soak is release-blocking.

### Stage 3 — Delete schema-on-write code (2.0)

- Remove the deletion targets listed above.
- Update the user-facing docs to describe a single schema-evolution model.
- Deprecated configs (`hoodie.write.schema.allow.auto.evolution.column.drop`, `hoodie.avro.schema.validate`, `hoodie.datasource.write.reconcile.schema`) are removed or re-implemented as `InternalSchema`-aware checks.

### User impact

- **Existing schema-on-read users**: no impact; their tables continue to work.
- **Existing schema-on-write users**: from Stage 2, their next write triggers a one-time bootstrap. They gain support for safe drops, renames, and richer type promotion. They lose nothing in terms of data; they do not retroactively recover rename/drop history they never had.
- **Engine integrators outside Spark/Flink/Hive/Trino**: third-party readers that only consume the Avro schema in commit metadata will continue to work for add-column scenarios; they need to adopt field-ID projection from `.hoodie/.schema/` to support drops and renames. The RFC ships a checklist for this.

### Discussion items the RFC must resolve before Stage 1

These are the explicit open questions the community must close in review:

1. Trino field-ID projection ownership: shared helper in `hudi-common` vs. plugin-local re-implementation.
2. HFile schema evolution: add support vs. formally exclude.
3. `hoodie.schema.on.read.enable` lifetime after 2.0: keep as no-op for one major vs. remove immediately.
4. Whether deprecation warnings ride with a 1.x minor or wait for 2.0 release notes.

## Test Plan

The RFC is testable by running the full Hudi test suite under both the legacy default (`hoodie.schema.on.read.enable=false`, removed in Stage 3) and the new default (`true`, on by default in Stage 2). Specific additions:

- **Default-on suite**: re-run existing tests including `TestHiveTableSchemaEvolution`, Flink `ITTestSchemaEvolution` / `ITTestSchemaEvolutionBySQL`, MOR/COW round-trips, clustering, compaction, metadata-table tests, and bulk_insert under `SCHEMA_EVOLUTION_ENABLE=true`. Failures are the gating signal for whether Stage 2 is ready.
- **Lazy-bootstrap test**: write a table with the legacy writer (no `.hoodie/.schema/`); upgrade to a build with the new default; verify that the next write produces a `.hoodie/.schema/<instant>.schema_commit` file and that subsequent reads use field-ID projection.
- **Cross-engine read-after-write matrix**: Spark writes a table that goes through add → rename → drop → type-promote in its history. All of Spark, Flink, Hive MR, and Trino must read the resulting table and reconcile to the latest schema. This is the Stage 1 exit criterion for Workstream A.
- **Metadata-table consistency**: with column-stats / record index / secondary index enabled, schema-on-read add/rename/drop sequences must leave indexes queryable and consistent with the latest schema. Stage 1 exit criterion for Workstream B.
- **Backward compatibility**: a 0.x-written table must be readable under the new default and must bootstrap transparently on first write. No operator action permitted in this test.
- **Mapper contract tests (Workstream D)**: one abstract suite per mapper interface that every implementation extends; round-trips every type x nullability x nesting x options; `support()` must match behaviour; RFC-99's interoperability table is the expected output.
- **Type compatibility (Workstream D)**: every engine schema master accepts (Spark `ByteType` / `ShortType` / CHAR / VARCHAR, Flink TINYINT / SMALLINT / CHAR / VARCHAR / TIMESTAMP(0-6)) is still accepted after each Workstream D step, and tables written by master read back with the same values and file layouts.
- **Deletion validation (Stage 3)**: after the schema-on-write branches are removed, the `if (schemaOnReadEnabled)` grep over the codebase must return no hits in production code (test fixtures may keep them).
