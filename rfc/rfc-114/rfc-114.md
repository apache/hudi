# RFC-114: Update as Delete and Insert Operation Mode for Storage Interoperability

## Proposers

- @yihua

## Approvers

- @vinothchandar
- @bvaradar
- @danny0405

## Status

Issue: [#20175](https://github.com/apache/hudi/issues/20175)

> Please keep the status updated in `rfc/README.md`.

## Abstract

A merge-on-read update appends the new version of a record to the log of its file group, which an
external table format (RFC-93) built on immutable data files plus positional deletes cannot represent
until the next compaction, so merge-on-read tables under such a format read stale data between
compactions. This RFC adds an operation mode in which a merge-on-read update becomes a positional
delete of the current version plus an insert into a new file slice, so every live record sits in a
base file and log files carry only positional deletes, which maps each deltacommit one to one onto
new data files plus deletion bitmaps.

## Background

### Merge-on-read under an external table format

The external table format plugin of RFC-93 records every completed Hudi instant in the external
table format's metadata. Copy-on-write tables map directly: a commit adds and removes whole base
files. A merge-on-read deltacommit does not: its updates live in log data blocks that only Hudi's
merge-on-read reader can apply, so the plugin can record nothing useful for it, and readers of the
external table format see the table as of the last compaction.

Positional deletes, on the other hand, map exactly. A delete of row `n` of base file `f` is a
deletion bitmap entry for `f` in the external table format. If updates were expressed as deletes of
the old version plus inserts of the new one, every deltacommit would map to new data files plus
deletion bitmaps, with no merge left for the reader.

### Why the insert has to move to another file group

Writing the delete and the insert into the same file group does not work: within a file slice the
delete is applied after the data block, so a reader would see a pure delete. The insert must go to a
different file group, as Hudi already does for an update that changes a record's partition under a
global index. This RFC generalizes that move to updates within a partition.

### Positions already exist

`hoodie.write.record.positions` (default `true`) records, in the delete block, the base-file row
position of each deleted record and the base file instant the positions refer to. Native Parquet logs
(RFC-103, table version 10) carry the same information in their delete files. No storage format
change is needed; the mode only has to guarantee that every delete carries a position.

## Implementation

The deliverables are the write mode with its guards, the table service rules that keep its layout,
the Spark SQL statements running through it, and recording the mode as a table property.

### Architecture

```
  upsert batch
       |
       v
  index lookup ------------------------------+
       |                                     |
       v                                     v
  located record (key in file group F,   new key
  base file B, row position n)               |
       |                                     |
       +--> delete of (B, n), in F's log      |
       |                                     |
       +--> insert of the new version ----+--+
                                          |
                                          v
                              new base file in a new file slice
                              (insert routing, no small-file packing)

  Layout invariant: live rows are in base files only; logs hold positional deletes only.
  External table format view of a deltacommit: new data files + one deletion bitmap per touched base file.
```

### What lives where

| Concern | Hudi | External table format plugin |
|---|---|---|
| Splitting an update into a delete and an insert | write path, after the index lookup | none |
| Locating the current version and its row position | index, plus a read of the base file when the index has no position | none |
| Keeping the layout invariant | guards on writes and table services | none |
| Deletion bitmaps | positional deletes in log files | one bitmap per base file, merged with the previous one |
| Compaction and clustering | rewrite base files and drop their deletes | record the rewrite and drop the replaced files' bitmaps |
| Turning the mode on | table property | supplies it at table creation (RFC-93 table defaults) |

### Splitting an update

With the mode on, an upsert on a merge-on-read table splits each located record into two: a delete
that keeps the record's current location and row position, and the incoming record with no location,
which the write routes as a fresh insert. The record index treats the delete as the "before" half of
an update, so it is repointed to the new location instead of losing the key.

- **A key found more than once.** Once a key has moved, an index that scans base files (bloom,
  simple) finds it in the old base file, where it is deleted, and in the new one. The write resolves
  such a record to its latest location before splitting it.
- **Deletes** keep their location and need no split.
- **New keys** pass through as inserts.

### Locating the current version

Every delete must carry a row position; a single delete without one would make the whole block
positionless, which the external table format cannot apply.

- The bloom and simple indexes return positions from their lookup.
- When an index locates a record without a position (the global indexes, the record index), the
  write reads the key's position from the latest base file of the located file group, and fails if
  the key is not there.
- Base file formats that give no row positions (HFile) are refused.

Storing positions in the record index removes that read; see [Appendix B](#appendix-b-index-and-metadata-table-interplay).

### Guards that keep the layout

With the mode on, the following are refused up front with a message naming the setting:

- **Event-time ordering.** The split removes the old version unconditionally, while event-time
  ordering would keep it when the incoming version is older. Only commit-time ordering is supported.
- **Writes without positions:** record positions off, table versions below 8, base files without row
  positions.
- **Indexes that cannot locate a single current version with a position:** a bucket index would route
  the delete and the insert to the same file group, and a custom index gives no such guarantee.
- **Partial updates,** which need the old version merged into the new one.
- **Updates and deletes on a table without a record key,** since a generated key cannot find the
  current version of a row.
- **Log compaction,** which rewrites delete blocks for no gain.
- **Writers that cannot split updates** (Flink log writes today).

Small-file packing is also off: an insert never lands in an existing file slice, so it can never land
in the file group whose row it just deleted.

### Table services

- **Compaction and clustering** rewrite base files and drop the positional deletes of the files they
  replace. Under the external table format they are file rewrites.
- **A write that locates a record in a file group with a pending compaction is refused.** Its
  positional delete would land in the compaction's file slice with positions in the base file being
  compacted. The writer retries after the compaction completes.
- **Compaction is not scheduled while an earlier deltacommit is pending,** because the compacted base
  file would keep rows that the pending deltacommit deletes, under a later instant than their new
  copies.

Both rules serialize ingestion and compaction on the touched file groups; lifting them is a follow-up
(see Risks & caveats).

### Spark SQL statements

`UPDATE`, `DELETE` and `MERGE INTO` on merge-on-read tables run through the same split. A `MERGE INTO`
record that matches a target row is first resolved against the statement's matched clauses (update,
delete, or no change), then split.

### The mode is a table property

The mode changes the table's layout, so every writer and every table service job of the table has to
agree on it: a writer without it would append an update to a log as a data block, and its compaction
scheduling would skip the pending deltacommit rule.

- The mode is stored in the table config when the table is created. An external table format supplies
  it through the table defaults of RFC-93, and a user can set it on a native table.
- Every writer and table service client reads it from the table config. A write config that disagrees
  with the table property is refused.
- The write config `hoodie.write.updates.as.deletes.and.inserts` (default `false`) remains for tables
  created before the table property exists, and is validated against it once it is set.

### Format meta columns across a move

A table format can declare format meta columns (RFC-93), such as row lineage, whose value a changed
row keeps. An update in this mode moves the row to another file group, so today the new version is
written as a new row and gets a new value. Carrying the value across the move needs the old value at
split time; the index lookup already reads the base file for bloom and simple indexes and can project
the columns, while the other indexes need a separate read. Until then, the mode refuses a table format
that declares format meta columns whose value must survive an update.

### Risks & caveats

- **Read-optimized queries see both versions.** The old version is deleted only by a positional delete
  in the log, so a read-optimized query (including the `_ro` table that catalog sync registers) returns
  the old and the new version of every updated key until compaction.
- **Compaction is held off by any pending deltacommit,** including the inflight commit of a crashed
  writer until it is rolled back.
- **Ingestion and compaction serialize on touched file groups.** Allowing writes during a pending
  compaction needs the compaction to carry the deletes of later deltacommits onto the new base file, by
  key, when it completes.
- **More, smaller base files.** Every update writes a new base file and small-file packing is off, so
  clustering has more to do. Registering pure-insert native log files (table version 10) as data files
  of the external table format would restore packing.
- **Index probes.** Indexes without positions pay a base file read per located record.

### Open questions

1. Name and migration of the table property, and whether an existing table can turn the mode on
   in place (it can, once no deltacommit is pending and the next compaction has run).
2. Event-time ordering through a merge at lookup time instead of a refusal.
3. Carrying format meta columns across a move: projection in the index lookup versus a separate read.

## Rollout/Adoption Plan

- **No breaking change and no impact on existing users.** The mode is off by default and only applies
  to merge-on-read upserts and deletes. The table format notifications it relies on (RFC-93) are no-ops
  for the native format.

**Step 1, 1.3.0.** The write mode, its guards, the table service rules and the Spark SQL statements,
turned on by the write config, explicitly or through an external table format plugin.

**Step 2.** The table property, supplied by the external table format at table creation, and the
refusal of a format that declares format meta columns that must survive an update.

**Step 3.** Positions in the record index; format meta columns across moves; writes during a pending
compaction.

**Step 4.** Event-time ordering, the Flink writer, and pure-insert native log files as external data
files.

No phase-out or migration tool is needed: the mode is additive, and a table can turn it off at any
time, since its files are valid merge-on-read files.

## Test Plan

The RFC is validated when:

- [ ] At table versions 8, 9 and 10, every positional delete written in the mode points at the base
  file row holding the deleted key, for repeated updates of the same keys, inserts, deletes and
  compaction, with the Java and Spark writers.
- [ ] Every guard refuses its setup before a write starts.
- [ ] Spark SQL `UPDATE`, `DELETE` and `MERGE INTO` on merge-on-read tables give the same rows as on a
  table without the mode.
- [ ] Writes into a file group with a pending compaction are refused, and compaction is not scheduled
  over a pending deltacommit.
- [ ] A merge-on-read table under an external table format reads the same rows through the external
  table format and through Hudi after inserts, updates, deletes, compaction, clustering, cleaning,
  archival and rollback.
- [ ] Existing merge-on-read suites stay green with the mode off.

## Appendix

### Appendix A: Constraints found by the proof of concept

- Merge-on-read small-file routing merges updates into base files through the merge path, bypassing
  the log, so the mode has to keep it off for both inserts and updates.
- Bloom and simple indexes find a moved key twice; without resolving to the latest location, a second
  update of the same keys deleted both copies.
- One positionless delete strips the positions of its whole delete block, so a located record without
  a position has to fail rather than fall back.
- Compaction completion did not notify the table format; the notification is part of RFC-93's revision.

### Appendix B: Index and metadata table interplay

After an update, a key exists physically in the old base file (deleted by the log) and in the new base
file (live). The record index is repointed on commit. Indexes that scan base files find both copies
and resolve to the latest location at the cost of a probe. The end state is for the record index to
store each key's base file row position, written with the base file, so it becomes the single source of
location and position and the probe goes away. RFC-93's revision keeps the Hudi metadata table
alongside the external table format's metadata, so the record index is available under an external
table format.

### Appendix C: Mapping onto an external table format

The first consumer is the external table format plugin in Apache XTable. Base files are data files. A
deltacommit adds the new base files and, for each base file with new positional deletes, one deletion
bitmap merged with the previous one. Compaction and clustering remove the replaced base files with
their bitmaps and add the new base files. One Hudi instant is one snapshot of the external table
format, which keeps the timeline fencing of RFC-93.
