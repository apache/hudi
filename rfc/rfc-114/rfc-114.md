# RFC-114: Update as Delete and Insert Operation Mode for Storage Interoperability

## Proposers

- @yihua

## Approvers

- @vinothchandar
- @bvaradar
- @danny0405

## Status

Issue: [#20175](https://github.com/apache/hudi/issues/20175)

> Please keep the status updated in `rfc/README.md`.

## Abstract

A merge-on-read update appends the new version of the record to the log of its current file group.
Hudi's own readers merge that on read and compaction folds the log back into the base file later,
but an external table format (RFC-93) whose storage model is immutable data files plus positional
delete files cannot represent such a log until the next compaction. The external table format plugin
therefore records every deltacommit as an empty change, and external table format readers see stale
data between compactions. Compaction and merge-on-read rollback also complete without notifying the
plugin, and a table shared with an external table format holds files Hudi did not name, which the
file-system view rejects.

This RFC adds an operation mode in which a merge-on-read update becomes **a positional delete
against the record's current file group plus an insert into a new file slice**, with the record key
moving file groups within its partition. The invariant that results is that **every live record
resides in a base file and log files carry positional deletes only**, so a deltacommit maps one to
one onto the data-file-plus-positional-delete model: new data files, plus one delete bitmap per
touched base file merged with the file's previous bitmap. Compaction and clustering are file
rewrites that drop the positional deletes of the files they replace.

The changes are: a write config `hoodie.write.updates.as.deletes.and.inserts` (default `false`) with
the decomposition applied after index tagging, fail-fast guards for the setups the mode cannot
support, the external table format completion hook on compaction, log compaction and rollback, and
two robustness fixes for tables that share a directory with an external table format. Everything is
off unless a user or an external table format plugin turns the mode on. The first consumer is the
external table format plugin maintained in Apache XTable; its mapping and a working end-to-end proof
of concept are summarized in Appendix D.

## Background

### The external table format plugin today

The external table format plugin (`HoodieTableFormat`, RFC-93) records every completed Hudi instant
in the external table format's metadata, in the same table directory, without a separate sync job. `commit()` fires for commits, deltacommits and clustering, but
`CompactHelpers.completeInflightCompaction` and `MergeOnReadRollbackActionExecutor` complete without
it, so the plugin never learns that base files were rewritten, which is exactly when positional
deletes must be dropped, or that a deltacommit was undone. Copy-on-write tables work end to end;
merge-on-read tables do not.

### Why a merge-on-read update cannot stay in its own file group

If the update were written as a delete plus an insert **inside the same file group**, the delete
block would always land after the data block (the append handle flushes deletes last, and native
logs order `.deletes` after `.log`), so a reader would see a pure delete: data loss. Moving the insert
to a different file group is what the global-index path already does for cross-partition updates;
this RFC generalizes it to same-partition moves under a flag.

### Positions already exist in Hudi

`hoodie.write.record.positions` (default `true`) records the base-file row position of each deleted
record in the delete block, along with the base file instant the positions refer to, and
`PositionBasedFileGroupRecordBuffer` uses them on read. Bloom and simple indexes produce positions
at tagging time; the record index does not yet (Appendix B). Native parquet logs (RFC-103, table
version 10) carry the same information in a `.deletes.parquet` footer. No storage format change is
needed.

## Implementation

### Update decomposition in the writer

New write config `hoodie.write.updates.as.deletes.and.inserts` (`HoodieWriteConfig`, default
`false`, since 1.3.0). When it is on and the operation is an upsert on a merge-on-read table,
`BaseWriteHelper` applies a transform after `tagLocation`:

- every tagged update record becomes two records: a **delete** carrying the old location
  (`HoodieIndexUtils.tagRecord(deleteRecord, currentLocation)`) with `setIgnoreIndexUpdate(true)`, so
  the record index treats it as the "before" half of an update and does not erase the repointed
  entry, and the incoming record **untagged**, so the partitioner routes it as a fresh insert;
- records tagged to more than one location (bloom and simple indexes scan base files, so after a
  key has moved once they find it in the tombstoned file and the live file) are first reduced to
  their latest location by base file instant time (`latestLocation`);
- deletes and records without a known location pass through unchanged.

`HoodieWriteHelper` (Spark, `HoodieData` map-reduce) and `JavaWriteHelper` implement the transform;
Flink is out of scope for v1 because its write path does not tag through `BaseWriteHelper`.

### Guards that keep the invariant

With the flag on:

- **Inserts never route to log files.** `SparkUpsertDeltaCommitPartitioner.getSmallFiles` and
  `JavaUpsertPartitioner` return no small files, and the delta commit executors skip the merge-handle
  update path, so both halves of the invariant hold and an insert cannot land in the file group it
  just tombstoned.
- **Commit-time ordering only.** Under event-time ordering a late update with a lower ordering value
  must lose, but the decomposition removes the old copy unconditionally. `BaseWriteHelper` rejects
  `EVENT_TIME_ORDERING` with `HoodieNotSupportedException`; merge-at-tag support is future work.
- **An index that yields positions, with positions enabled.** Bucket, in-memory and record-index
  tagging carry no base-file position; a bucket index would also route the delete and the insert
  into the same log by key hash, which reads back as a pure delete. The mode accepts only the bloom
  and simple index families and requires `hoodie.write.record.positions=true`.
- **No log compaction.** `ScheduleCompactionActionExecutor` rejects log compaction scheduling, since
  it rewrites delete blocks for no benefit to the external table format.

### External table format hooks on compaction and rollback

- `HoodieActiveTimeline` gains `transitionCompactionInflightToComplete` and
  `transitionLogCompactionInflightToComplete` overloads that take a `TableFormatCompletionAction`,
  mirroring `saveAsComplete`; `CompactHelpers.completeInflightCompaction` passes
  `metaClient.getTableFormat().commit(...)`. The V2 transitions return the completed instant with
  its completion time, which the hook needs.
- `BaseRollbackActionExecutor.unpublishInstant()` hoists the table format `rollback` call and the
  revert-to-inflight step out of `CopyOnWriteRollbackActionExecutor` so that
  `MergeOnReadRollbackActionExecutor` runs it too.

### Robustness for a shared table directory

- `HoodieTableMetaClient.TableBuilder.set` keeps `hoodie.table.format.*` keys, so an external table
  format plugin receives its settings from the first commit on rather than through a pre-initialization step.
- `AbstractTableFileSystemView` ignores base files whose names Hudi did not produce instead of
  failing on a null file id. This part is open for discussion: Apache XTable's Hudi conversion
  target registers source-named data files as Hudi base files and relies on the view listing them,
  so the better shape is for the external table format plugin to hide foreign files through its own
  `HoodieTableMetadata`, with the view routed through the plugin's metadata factory (Appendix C).

## Rollout/Adoption Plan

- **No change for existing users.** The mode is off by default and only reachable on merge-on-read
  upserts. The compaction and rollback hooks call the native table format, which is a no-op.
- **Phase 1 (this RFC).** Land the writer changes and the SPI hooks in Hudi 1.3.0. The flag is set
  explicitly by the user or by the external table format plugin's write configuration.
- **Phase 2.** Derive the flag from `hoodie.table.format` (an external table format on a merge-on-read
  table turns it on); store base-file positions in the record index so it can feed positional
  deletes without a base file probe; allow the metadata table under an external table format
  (Appendix B).
- **Phase 3.** Register pure-insert native log files (table version 10) as data files of the
  external table format to restore small-file-friendly insert routing; event-time ordering through
  merge-at-tag; Flink writer; multi-writer.
- **Deprecation.** None; the mode is additive.

## Test Plan

- **Hudi unit and functional tests** (in the companion PR): `TestHoodieJavaClientUpdatesAsDeletesAndInserts`
  (decomposition, key moves file group, repeated updates of the same keys, deletes, snapshot read
  correctness, compaction, every guard rejection), `TestHoodieJavaClientMergeOnReadForTestFormat`
  (compaction and rollback fire the external table format hooks, using the test table format) and
  `TestSparkUpdatesAsDeletesAndInserts` (Spark write path). Each was written red first against the
  unmodified code.
- **Plugin integration tests** run in the external table format plugin (Appendix D) and assert the
  row set through an external table format reader and through Hudi after inserts, repeated updates,
  deletes, compaction, clustering, cleaning, archival and rollback.
- **Regression.** The existing Hudi client suites stay green with the flag off.
- **Acceptance.** A merge-on-read table under an external table format reads correctly from at
  least two external engines between compactions, and every Hudi table service keeps the external
  table format's metadata consistent with the Hudi timeline.

## Appendix A: Constraints found by the proof of concept

- Merge-on-read small-file routing silently merges updates into base files through the merge
  handle, bypassing the log; the mode must gate it in both the partitioner and the executor.
- Bloom and simple indexes double-tag a key that has moved file groups; without the latest-location
  reduction a second update produced duplicates (200 deletes for 100 keys in the red test).
- The record index returns position `-1` at tagging time, so v1 needs the bloom or simple index.
- A single `-1` position strips the whole delete block's positions, so a positionless tagged update
  must be an error rather than a fallback.
- Compaction completion previously produced an instant without a completion time, which the external
  table format hook needs; the V2 transitions now return the completed instant.
- The file-system view change breaks `TestBaseFileUpdatesExtractor` in Apache XTable against a Hudi
  build carrying it (see Robustness above).

## Appendix B: Index and metadata table interplay

After an update, a key exists physically in the old base file (tombstoned by the log delete) and in
the new base file (live). The record index is repointed on commit, because the insert updates the
entry and the delete half is ignored for index updates. Bloom and simple indexes scan base files and
find both copies, which the latest-location reduction resolves at the cost of a probe. The intended
end state is for the record index to store the base-file row position of each key, written by the
base file writer, so it becomes the single source of location and position and the probe goes away.

Under the current external table format plugin the metadata table is disabled and the plugin's
`HoodieTableMetadata` lists the file system, so the record index is not available there today. This
RFC strengthens the case for keeping the Hudi metadata table alongside the external table format's metadata
(a hybrid rather than a replacement), which is a decision for the follow-up on metadata table
coexistence.

## Appendix C: Follow-ups on the external table format SPI

- Route `FileSystemViewManager` and the embedded timeline server's view through the plugin's
  `getMetadataFactory()` when the metadata table is off, so the external table format decides which
  files belong to the table.
- Thread catalog configuration into the external table format plugin and persist it in `hoodie.properties`, so
  Streamer, Flink and async table service jobs publish to the same place.
- Return positions from `HoodieDeleteBlock` as plain types; the current RoaringBitmap type is
  relocated by the Spark bundle, so a plugin compiled against `hudi-common` fails with
  `NoSuchMethodError` when only the bundle is on the classpath.
- Lock-provider and conflict-resolution hooks on `HoodieTableFormat` for multi-writer.

## Appendix D: First consumer, the external table format plugin in Apache XTable

The plugin (apache/incubator-xtable#894 and the stacked apache/incubator-xtable#954) maps the mode
as follows. Base parquet files are data files. Each log delete block becomes a positional delete
file for its base file, merged with the previous one so the newest supersedes it. Compaction is a
file rewrite that removes the old base file with its delete file and adds the new base file.
Clustering uses the existing overwrite path plus delete-file removal for replaced files. One Hudi
instant is one snapshot, which keeps the plugin's timeline fencing invariant. Snapshot expiry moves
from age-based on every commit to Hudi archival, since a completed Hudi instant without a snapshot is
reported as inflight; time travel through the external table format is therefore bounded by the Hudi cleaner
retention.

Proof of concept status: the Hudi branch in the companion PR plus 12 plugin commits; integration
tests cover inserts, repeated updates of the same keys with delete-file supersede, pure deletes,
compaction, rollback, partitioned tables, the Spark write client, clustering, cleaning and archival,
with rows asserted through an external reader and through Hudi. Still open: orphan delete files
after a failed publish (Hudi rollback removes data and log files only), event-time ordering, record
index positions, catalog configuration and locking, Flink writer support.
