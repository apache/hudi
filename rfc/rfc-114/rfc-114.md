# RFC-114: Iceberg V3 Deletion Vectors and Table Services under the Pluggable Table Format

## Proposers

- @yihua

## Approvers

> Please keep the status updated in `rfc/README.md`.

## Motivation

RFC-93 made the table format pluggable: a `HoodieTableFormat` implementation is notified when a Hudi
instant completes and publishes the equivalent metadata for another format. The Iceberg
implementation lives in Apache XTable
([apache/incubator-xtable#894](https://github.com/apache/incubator-xtable/pull/894)) and gives a
Hudi-written table a standard Iceberg metadata tree in the same directory, with no sync job and no
second copy of the data. The goal behind it is "Iceberg outside, Hudi inside": any Iceberg engine
reads the table, while Hudi's write path, indexes and table services operate it.

Today that only holds for copy-on-write tables. Three gaps stop merge-on-read tables, which is where
Hudi's write-side advantage lives:

- **A deltacommit is invisible to Iceberg.** Log files have no Iceberg representation, so the
  Iceberg plugin publishes an empty snapshot for every deltacommit and an Iceberg reader sees stale
  data until the next compaction. Iceberg V3 has the right primitive for exactly this, the deletion
  vector (a Puffin `deletion-vector-v1` blob of row positions per data file), but Hudi has no write
  mode that produces only positional deletes.
- **The SPI is blind to compaction and to merge-on-read rollback.** `HoodieTableFormat.commit()` fires
  for commits, deltacommits and clustering, but `CompactHelpers.completeInflightCompaction` and
  `MergeOnReadRollbackActionExecutor` complete without it. The plugin never learns that base files were
  rewritten (when deletion vectors must be dropped) or that a deltacommit was undone.
- **Retention is not aligned.** XTable expires Iceberg snapshots by age on every commit, while the
  plugin's timeline fencing treats a Hudi instant without an Iceberg snapshot as incomplete. On any
  table older than the retention window, completed instants get demoted and reads break.

This RFC closes those gaps. The Hudi-side changes are small and additive; the Iceberg-side changes
land in XTable on top of PR #894.

## Abstract

Under a non-native table format, a merge-on-read update becomes **a positional delete against the
record's current file group plus an insert into a new file slice**, with the record key moving file
groups within its partition. The resulting invariant is that **Iceberg data files are exactly Hudi
base files and Hudi log files carry only positional deletes**, so every deltacommit maps to one
Iceberg V3 snapshot: new data files plus one deletion vector per touched base file, merged with the
file's previous deletion vector. Compaction and clustering publish as file rewrites that drop the
deletion vectors of the files they replace. Snapshot expiry moves from "by age, on every commit" to
"at Hudi archival", which also removes superseded Puffin files.

The Hudi changes are: a write config `hoodie.write.updates.as.deletes.and.inserts` (default `false`)
with the decomposition applied after index tagging, fail-fast guards for the setups the mode cannot
support, the table format completion hook on compaction, log compaction and rollback, and two
robustness fixes for tables that share a directory with another format. The XTable changes are the
deltacommit-to-`RowDelta` path, deletion vector extraction from Hudi delete blocks, rollback to the
parent snapshot, and the retention change. A working end-to-end proof of concept on Iceberg 1.11
covers inserts, repeated updates of the same keys, deletes, compaction, clustering, cleaning,
archival and rollback for the Java and Spark write clients (Appendix C).

## Background

### What the pluggable table format does today

`HoodieTableFormat` (RFC-93) provides `commit`, `clean`, `archive`, `rollback`, `completedRollback`,
`savepoint` and `restore` hooks, a `TimelineFactory` and a `TableMetadataFactory`. The Iceberg
implementation translates each completed instant into Iceberg operations through XTable's existing
Hudi-to-Iceberg conversion, and reconstructs the Hudi timeline from Iceberg snapshot summaries so that
Iceberg is the authority on which commits are visible. A Hudi instant that completed natively but
has no Iceberg snapshot is reported as inflight (timeline fencing).

### Why a merge-on-read update cannot stay in its own file group

A Hudi update on a merge-on-read table appends the new version of the record to the log of its
current file group. If the update were instead written as a delete plus an insert **inside the same
file group**, the delete block would always land after the data block (the append handle flushes
deletes last, and native logs order `.deletes` after `.log`), so a reader would see a pure delete:
data loss. Moving the insert to a different file group is what the global-index path already does
for cross-partition updates; this RFC generalizes it to same-partition moves under a flag.

### Positions already exist in Hudi

`hoodie.write.record.positions` (default `true`) records the base-file row position of each deleted
record in the delete block, along with the base file instant the positions refer to, and
`PositionBasedFileGroupRecordBuffer` uses them on read. Bloom and simple indexes produce positions
at tagging time; the record index does not yet (Appendix B). Native parquet logs (RFC-103, table
version 10) carry the same information in a `.deletes.parquet` footer. No storage format change is
needed to extract deletion vectors.

## Implementation

### Storage model

| Hudi artifact | Iceberg V3 artifact | When |
|---|---|---|
| Base parquet file | Data file (`RowDelta.addRows`) | insert, compaction, clustering |
| Log delete block (positions + base file instant) | Deletion vector for that base file (`RowDelta.addDeletes`), merged with the previous one (`removeDeletes`) | update (delete half), delete |
| Log data block | Must not exist in this mode (v1) | n/a |
| Compaction commit | `RewriteFiles`: old base file and its deletion vector out, new base file in | compaction |
| Replace commit (clustering) | Existing overwrite path, plus deletion vector removal for replaced files | clustering |

One Hudi instant is one Iceberg snapshot, which keeps the timeline fencing invariant of PR #894.

### Update decomposition in the writer

New write config `hoodie.write.updates.as.deletes.and.inserts` (`HoodieWriteConfig`, default
`false`, since 1.3.0). When it is on and the operation is an upsert on a merge-on-read table,
`BaseWriteHelper` applies a transform after `tagLocation`:

- every tagged update record becomes two records: a **delete** carrying the old location
  (`HoodieIndexUtils.tagRecord(deleteRecord, currentLocation)`) with `setIgnoreIndexUpdate(true)`, so
  the record index treats it as the "before" half of an update and does not erase the repointed
  entry, and the incoming record **untagged**, so the partitioner routes it as a fresh insert;
- records tagged to more than one location (bloom and simple indexes scan base files, so after a
  key has moved once they find it in the tombstoned file and the live file) are first reduced to
  their latest location by base file instant time (`latestLocation`);
- deletes and records without a known location pass through unchanged.

`HoodieWriteHelper` (Spark, `HoodieData` map-reduce) and `JavaWriteHelper` implement the transform;
Flink is out of scope for v1 because its write path does not tag through `BaseWriteHelper`.

### Guards that keep the invariant

With the flag on:

- **Inserts never route to log files.** `SparkUpsertDeltaCommitPartitioner.getSmallFiles` and
  `JavaUpsertPartitioner` return no small files, and the delta commit executors skip the merge-handle
  update path, so both halves of the invariant hold and an insert cannot land in the file group it
  just tombstoned.
- **Commit-time ordering only.** Under event-time ordering a late update with a lower ordering value
  must lose, but the decomposition removes the old copy unconditionally. `BaseWriteHelper` rejects
  `EVENT_TIME_ORDERING` with `HoodieNotSupportedException`; merge-at-tag support is future work.
- **No log compaction.** `ScheduleCompactionActionExecutor` rejects log compaction scheduling, since
  it rewrites delete blocks for no Iceberg-visible benefit.
- **Positions are required.** The mode needs `hoodie.write.record.positions=true` and an index that
  yields positions; a tagged update without a position is an error, not a fallback.

### Table format hooks on compaction and rollback

- `HoodieActiveTimeline` gains `transitionCompactionInflightToComplete` and
  `transitionLogCompactionInflightToComplete` overloads that take a `TableFormatCompletionAction`,
  mirroring `saveAsComplete`; `CompactHelpers.completeInflightCompaction` passes
  `metaClient.getTableFormat().commit(...)`. The V2 transitions now return the completed instant
  carrying its completion time, which the hook needs.
- `BaseRollbackActionExecutor.unpublishInstant()` hoists the table format `rollback` call and the
  revert-to-inflight step out of `CopyOnWriteRollbackActionExecutor` so that
  `MergeOnReadRollbackActionExecutor` runs it too.

### Robustness for a shared table directory

- `AbstractTableFileSystemView` ignores base files whose names Hudi did not produce instead of
  failing on a null file id, so a directory that also holds Iceberg-written data files (an adopted
  table, or a foreign write) still builds file groups.
- `HoodieTableMetaClient.TableBuilder.set` keeps `hoodie.table.format.*` keys, so a table format
  receives its settings from the first commit on rather than through a pre-initialization step.

### Iceberg side (Apache XTable, on top of PR #894)

Kept brief here because the code lives in XTable; the upstreaming split is in Appendix D.

- `IcebergTableFormat.commit` stages positional deletes for a deltacommit through
  `HudiPositionalDeleteExtractor`, which reads each log file's delete blocks, takes the positions and
  the base file instant, and resolves the data file path through the file-system view (not
  `writeStat.getBaseFile()`, which is empty on table version 8 and above).
- `IcebergDataFileUpdatesSync.applyRowDelta` writes one Puffin deletion vector per data file with
  `BaseDVFileWriter`, loading the file's previous deletion vector so positions merge and the new
  vector supersedes the old one, then commits `addRows`, `addDeletes` and `removeDeletes` in one
  `RowDelta` with `validateFromSnapshot(currentSnapshotId)` (without it Iceberg rejects existing
  vectors as concurrently added).
- Rollback reverts to the parent snapshot rather than to the current one.
- Snapshot expiry by age is disabled for the table format (`TargetTable.NO_METADATA_EXPIRY`) and
  runs at Hudi archival, which now also deletes superseded `.puffin` files. Consequence: Iceberg
  time travel on such a table is valid within the Hudi cleaner retention window.
- Tables are created at Iceberg format version 3 (`xtable.iceberg.format-version`); Iceberg 1.11
  drops dangling deletion vectors when their data file is removed.

## Rollout/Adoption Plan

- **No change for existing users.** The write mode is off by default and only reachable on
  merge-on-read upserts. The compaction and rollback hooks call the native table format, which is a
  no-op. The file-system view change only affects directories holding files Hudi never named, which
  previously failed.
- **Phase 1 (this RFC).** Land the writer changes and the SPI hooks in Hudi 1.3.0; land the XTable
  changes on top of PR #894 in the order of Appendix D. The flag is set explicitly by the user or by
  the Iceberg plugin's write configuration.
- **Phase 2.** Derive the flag from `hoodie.table.format` (a non-native format on a merge-on-read
  table turns it on), store base-file positions in the record index so it can feed positional
  deletes without a base file probe, and allow the metadata table under a non-native format
  (Appendix B).
- **Phase 3.** Register pure-insert native log files (table version 10) as Iceberg data files to
  restore small-file-friendly insert routing; event-time ordering through merge-at-tag; multi-writer.
- **Deprecation.** None; the mode is additive.

  (clustering, cleaning, archival deleting superseded Puffin files), each asserting the row set

- **Regression.** The existing pluggable table format module suite and the Hudi client suites stay

- **Acceptance for the RFC.** A merge-on-read table under the Iceberg table format reads correctly
  from at least two external Iceberg engines between compactions, and every Hudi table service keeps
  the Iceberg metadata consistent with the Hudi timeline.

## Appendix A: Constraints found by the proof of concept

- `RowDelta` needs `validateFromSnapshot(currentSnapshotId)` or a table with existing deletion
  vectors fails with "Found concurrently added DV".
- Merge-on-read small-file routing silently merges updates into base files through the merge
  handle, bypassing the log and the deletion vector path; the mode must gate it in both the
  partitioner and the executor.
- Bloom and simple indexes double-tag a key that has moved file groups; without the latest-location
  reduction a second update produced duplicates (200 deletes for 100 keys in the red test).
- The record index returns position `-1` at tagging time, so v1 needs the bloom or simple index.
- `TableFormatSync` in XTable swallows sync failures into `SyncResult`; the plugin has to inspect the
  result and throw, otherwise a failed Iceberg commit leaves a completed Hudi instant with no snapshot.
- Clustering registered data files with `file_size_in_bytes=0` in Iceberg (a path-only
  `HoodieBaseFile`), so Iceberg scans of clustered files returned no rows while `count()` looked
  correct because it is answered from metadata. Fixed on the XTable side by using the full path info.
- Age-based snapshot expiry cannot coexist with timeline fencing; expiry at archival is the only
  consistent point. Iceberg time travel is therefore bounded by the Hudi cleaner retention.
- Log file rollback in Hudi removes data and log files only, so a failed `RowDelta` can leave an
  orphan Puffin file; orphan cleanup is a follow-up.
- The file-system view change that ignores base files Hudi did not name breaks XTable's Hudi
  conversion target, which registers source-named data files as Hudi base files
  (`TestBaseFileUpdatesExtractor` fails against a Hudi build carrying it). The change is kept in the
  companion PR for discussion, but the shape is wrong: the right fix is for a non-native table format
  to hide foreign files through its own `HoodieTableMetadata`, with the file-system view routed
  through the format's metadata factory (RFC-115, prerequisite 5).
- Iceberg 1.11 requires JDK 17 to build and removes dangling deletion vectors itself; 1.9.2 already
  writes and reads V3 deletion vectors, so the Iceberg version bump is about lifecycle, not capability.

## Appendix B: Index and metadata table interplay

After an update, a key exists physically in the old base file (tombstoned by the log delete) and in
the new base file (live). The record index is repointed on commit, because the insert updates the
entry and the delete half is ignored for index updates. Bloom and simple indexes scan base files and
find both copies, which the latest-location reduction resolves at the cost of a probe. The intended
end state is for the record index to store the base-file row position of each key, written by the
base file writer, so it becomes the single source of location and position and the probe goes away.

Under PR #894 the plugin's `IcebergBackedTableMetadata` lists the file system and the metadata
table is disabled, so the record index is not available under the Iceberg format today. This RFC
strengthens the case for keeping the Hudi metadata table alongside Iceberg metadata (a hybrid rather
than a replacement), which is a decision for the follow-up on metadata table coexistence.

## Appendix C: Proof of concept status

- Hudi branch `mor-update-as-delete-insert` (companion PR), 8 commits over master; a 1.2-based
  bridge build of the same changes is what the XTable branch pins during the proof of concept.
- XTable branch stacked on PR #894, 12 commits: format version config, `RowDelta` and deletion
  vector path, positional delete extractor, rollback to parent, replace commit file size fix,
  clustering and cleaning coverage, Iceberg 1.11.0, no expiry by age, Puffin cleanup at archival,
  deletion vectors asserted gone after compaction and clustering, partitioned tables, Spark write
  client. Module suite: 33 tests green (1 pre-existing skip) on Iceberg 1.11 and JDK 17.
- Still open: orphan Puffin files after a failed `RowDelta`; event-time ordering; record index
  positions; catalog configuration and locking; Flink writer support; Avro version alignment between
  Hudi and Iceberg.

## Appendix D: Upstreaming order for the XTable side

In dependency order on top of PR #894:

1. Replace commit file size fix (xtable-core only, mergeable against main today; it also fixes
   the translation path).
2. Rollback to the parent snapshot (plugin module).
3. Configurable Iceberg format version (default stays 2).
4. Iceberg 1.11.0 upgrade (build moves to JDK 17).
5. No age-based expiry under the table format (adds `TargetTable.NO_METADATA_EXPIRY` to the public
   API).
6. Merge-on-read deletion vectors (depends on 2, 3, 5 and a Hudi release carrying the writer
   changes); can be split into the core `RowDelta` writer, the plugin extractor with integration
   tests, and the test harness overloads.
7. Puffin cleanup at archival (small, but its test needs deletion vectors).
