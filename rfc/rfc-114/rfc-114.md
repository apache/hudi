## Motivation

Hudi's Spark write path leaves the DataFrame world at the first step. `HoodieSparkSqlWriter` converts the input to
`RDD[HoodieRecord]` and everything after that is imperative RDD code over Kryo-serialized record wrappers. The cost
shows up in every upsert:

- **Five shuffles, two extra driver jobs and three persists** for a vanilla copy-on-write upsert with the simple
  index: precombine `reduceByKey`, index partition discovery (`distinct` plus collect), the index left-outer join,
  the `countByKey` workload profile, and the final `partitionBy`, plus a small-file listing and a stat collect.
- **A cache in the critical path.** The tagged RDD is persisted so `WorkloadProfile` can count records per
  partition before `UpsertPartitioner` routes them. The cache competes with execution memory; under pressure it is
  evicted and the whole lineage, including the source read, is recomputed. This is the classic Hudi write failure
  mode at scale.
- **Sizing by record count, not bytes.** Insert sizing multiplies a record count by an average record size from
  commit metadata, so skewed or wide rows produce wrong file sizes.
- **Serialization overhead everywhere.** `HoodieRecord` and Avro `GenericRecord` graphs are built, Kryo-serialized
  on every shuffle and spill, and converted again at the parquet writer. `HoodieSparkRecord` deferred some of these
  conversions but did not remove them.
- **The plan is invisible.** Nothing after `createRelation` shows up in the Spark SQL UI or benefits from the
  catalyst optimizer and AQE, and every new feature (a new index, MERGE INTO) is more RDD code.

Delta Lake's optimized writes show a better mechanism: the shuffle itself is the profiling pass. Hudi's file-group
model and indexes let the same mechanism go further than Delta can.

## Abstract

We add a DataFrame-native write path in a new module, `hudi-spark-datasource/hudi-spark-dataframe`, that keeps the
input as Dataset/`InternalRow` operations end to end and only becomes imperative at the record write:

1. **Key generation, precombine, index tagging and operation resolution are catalyst plans**: projections, a window
   dedup, and a join against the index (the base-file meta columns for the simple index, thin-key point lookups for
   the record-level index).
2. **One owned routing shuffle doubles as the workload profiler.** Updates are pinned to their file group by the
   index; inserts are bucketed and sized either from commit metadata or, with the shuffle-stats profiler, by
   materializing only the map stage (`submitMapStage`) and bin-packing per-block byte sizes from the
   `MapOutputTracker`. No cache, no count pass, `UnsafeRow` from the source scan to the writer.
3. **The existing row-native handles and the whole commit stack are reused.** One task per file group drives
   `HoodieRowCreateHandle`, `FileGroupReaderBasedMergeHandle` or the append handles, and the commit goes through
   `SparkRDDWriteClient`, so timeline, metadata table, table services and meta sync are untouched.

The path is gated by `hoodie.datasource.write.dataframe.path.enable` (default false), and every unsupported case
falls back to the legacy writer with the reason logged. The target is three shuffles (two once precombine folds into
the write task), zero persists, and eventually the retirement of `HoodieSparkSqlWriter`, `UpsertPartitioner` and
`ExpressionPayload`.

## Background

### Delta Lake's optimized writes

`DeltaOptimizedWriterExec` wraps the child plan in a hash shuffle, runs only the map stage through
`sparkContext.submitMapStage`, reads per-block byte sizes from the `MapOutputTracker` (metadata every shuffle
produces, accurate to within about ten percent below the ~2000-reducer `HighlyCompressedMapStatus` threshold),
bin-packs blocks into file-sized bins on the driver, and launches one reduce task per bin. Lost map output re-runs
only the affected map tasks, where a lost cache recomputes the full lineage. Delta can only shape new files: it has
no file-group concept, so it never routes inserts into existing small files and never pins updates to a target file.

### Why the write must own the physical plan

On the pure DataSource V2 write path the connector hands Spark a `BatchWrite` and is called per already materialized
partition; `RequiresDistributionAndOrdering` can request a repartition but gives no access to the map stage, block
statistics or reduce-side planning. Delta stays on the V1-style path even under DSv2 for this reason.
`DefaultSource.createRelation` already sits at that level with the full DataFrame in hand, so the new path wraps
`df.queryExecution.executedPlan` with its own exec nodes without changing the datasource registration. Hudi's own
DSv2 write was disabled in HUDI-4178 for related reasons.

## Implementation

### Architecture

```
Input DataFrame                                                    DRIVER
  1. Prepare      keygen as projections: _key, _partition, _ordering   init table, writer schema, startCommit
  2. Precombine   window dedup by key on _ordering
  3. Tag          SIMPLE join | RLI point lookup -> located file group (null = insert)
  4. Resolve      per-row operation: insert | update | delete (+ partition-move fan-out)
  ------------------------------------------------------------ catalyst above, imperative below
  5. Routing shuffle  u:<fileId> pinned | i:<partition,bucket> sized | s:<fileId> padding (MOR)   <-> profiler
  6. Write task       one task per bin or file group -> row write handle -> WriteStatus
  Commit          slim WriteStatus collect -> client.commit (validators, markers, MDT, table services, meta sync)
```

Stages 1 to 4 are ordinary catalyst plans, visible to the optimizer and AQE (in the PoC the precombine window is
optimized into `WindowGroupLimit`). Stage 5 is a plain repartition on the routing key with the metadata profiler,
or the one custom exec node, `HoodieRoutingShuffleExec`, with the shuffle-stats profiler. Stage 6 is an RDD
`mapPartitions` driving the write handles. Those two stages are the entire imperative surface.

### Principles

1. **One owner of the physical plan**: stay on the V1 `createRelation` entry and wrap the executed plan.
2. **`InternalRow` until the file writer**: no `HoodieRecord`, payload, Avro or Kryo above the handle seam.
3. **Control plane reused, not rebuilt**: everything driven off `WriteStatus` stays as is.
4. **The routing shuffle is the profiler**, and profiling is a pluggable strategy so the path works without Spark
   internals and on Spark versions where they drift.
5. **Narrow first, wide later**: insert and upsert on copy-on-write parquet with the simple and record-level indexes
   first; everything else is an expansion of a working spine.

### Module and dependency direction

`hudi-spark-dataframe` depends on `hudi-spark-client` (handles, key generators, write client). `DefaultSource` in
`hudi-spark-common` routes into it through a reflective call behind the config gate, so the dependency arrow never
points up. Spark-internal access (`submitMapStage`, `MapOutputTracker`, shuffle readers) is isolated under
`org.apache.spark.sql.hudi.execution`, with version drift absorbed by the per-version Spark modules where needed.

### Index tagging and routing

Tagging is a DataFrame-to-DataFrame function returning the located file group per row, null for inserts. The index
is the source of truth for update routing; profiling never touches it.

| Index | Mechanism | Shuffle cost |
|---|---|---|
| SIMPLE, GLOBAL_SIMPLE | Scan the latest base files' meta columns only, pruned by column stats on the key; left join input on key (plus partition path when non-global) | one join exchange |
| Record-level index | Thin-key point lookups per index file group, shard-aligned with `mapRecordKeyToFileGroupIndex`, then join located keys back (broadcast when small); the index never shuffles. See Appendix C | thin-key exchange + join-back |
| Bucket | Routing key computed by expression from the key hash | zero |
| Bloom (later) | Column-stats prune, bloom probe from the metadata table, verify against candidate base files | staged |

Out of tagging, rows carry a prefixed routing key: `u:` for an update pinned to its file group (each maps to exactly
one merge handle, no sizing needed), `i:` for an insert bucket (partition path plus coarse bucket), and on
merge-on-read `s:` for a small-file padding bucket pre-assigned to an existing small file group (on copy-on-write
padding shares `u:`, since both merge). Only insert reducers need block-size
precision, which keeps the ~2000-reducer `MapStatus` cap manageable. A fully DataFrame-native record-index join is
sketched in Appendix C.

### The handle seam

```
RowWriteHandle: (BucketDescriptor, Iterator[InternalRow]) -> WriteStatus
BucketDescriptor { type: CREATE | MERGE | APPEND, partitionPath, fileId, baseFileSlice, targetInstant }
```

| Bucket type | Backing implementation |
|---|---|
| CREATE | `HoodieRowCreateHandle` with `HoodieInternalRowParquetWriter` |
| MERGE | `FileGroupReaderBasedMergeHandle` with a Spark reader context created on the driver and shipped |
| APPEND (merge-on-read) | Bridge over the existing append handles; a row-native log block writer is a follow-up |

### Profiling as a strategy

The insert profiler is selected by `hoodie.datasource.write.dataframe.profiler`:

- **`metadata`** (default, no Spark internals; `MetadataSizingProfiler`): `insertsPerBucket = targetFileSize /
  avgRecordSize` with the average record size from commit metadata; small files are filled first. Sizing mistakes
  shift file counts, not correctness, because the rolling create handle still caps file size.
- **`shuffle_stats`** (the Delta mechanism; `HoodieRoutingShuffle`): the writer owns the `ShuffleDependency`,
  materializes only the map stage, bin-packs insert-reducer blocks to a byte target with one task per bin, and never
  bin-packs update reducers. Shuffle bytes are recorded in commit metadata so later writes calibrate the bin size as
  `targetFileSize x shuffleBytes / parquetBytes` from recent commits. Per commit, not a table property, so it
  self-corrects across schema and compression changes.

### Entry gate and fallback

`hoodie.datasource.write.dataframe.path.enable` (default false) plus a static eligibility check at entry. Anything
unsupported falls back wholesale to the legacy writer with the reason logged; after entry there is no mid-flight
fallback, only failure and rollback. There is no table format change, so no `HoodieTableVersion` implication. The
SQL commands call `HoodieSparkSqlWriter.write` directly and never reach `createRelation`, so they are unaffected
until phase 5 moves them onto the same entry; the gate still rejects SQL-internal option markers defensively.

### Risks

| Risk | Severity | Mitigation |
|---|---|---|
| Semantics parity with the legacy writer (schema evolution edges, custom payloads, dup policies) | high | Gate with wholesale fallback; default off until the existing datasource suites pass with the path force-enabled |
| Spark-internal APIs (`submitMapStage`, shuffle-reader churn) | medium | Profiler pluggable; internals isolated per Spark version; the `metadata` profiler is the floor everywhere |
| `MapStatus` precision above ~2000 reducers | medium | Update reducers need no sizing; hierarchical routing keys if insert reducers alone exceed the cap |
| Merge-on-read log sizing dynamics | medium | Appends tolerate approximate sizing; the slice-based plan never pads logged slices |
| Executor disk pressure from shuffle-to-disk profiling | low | Upserts already pay a shuffle; the shuffle replaces the cache |

## Rollout/Adoption Plan

The path is additive and opt-in. No existing behavior changes until the default flips, and the legacy writer stays
as the fallback throughout.

**Phase 1** (done in PR #20166): module skeleton, entry gate, prepare stage, copy-on-write insert with
`MetadataSizingProfiler` and small-file padding.

**Phase 2** (done): copy-on-write upsert with the simple and record-level index strategies, upfront precombine,
pinned update routing, the merge seam over `FileGroupReaderBasedMergeHandle`; GLOBAL_SIMPLE with
update-partition-path fan-out, commit-time ordering, `_hoodie_is_deleted` delete threading.

**Phase 3** (done): the `shuffle_stats` profiler with map-stage profiling, bin planner and per-commit calibration;
the routing shuffle as a physical-plan node under a SQL execution.

**Phase 4** (merge-on-read done, rest open): bloom and bucket indexes, bulk_insert (retiring the old row writer),
delete, insert_overwrite, delete_partition, the streaming sink.

**Phase 5** (not started): SQL DML on the same entry, including MERGE INTO without `ExpressionPayload`; flip the
default; deprecate `HoodieSparkSqlWriter`.

**Impact on existing users.** None until the default flips. When it does, writes that the gate cannot serve keep
using the legacy writer, so no migration tooling is needed.

## Test Plan

- [ ] The module's end-to-end suite (`TestHoodieDataFrameWriter`) writes through `df.write.format("hudi")` with
  the gate on and reads back through the regular datasource: multi-commit insert and upsert, small-file padding,
  record-index tagging, both profilers with calibration bytes asserted in commit metadata, global index partition
  moves, delete markers, merge-on-read appends. The suite asserts the gate is on the classpath so a stale jar cannot
  make it pass through the legacy writer.
- [ ] The existing datasource suites (`TestHoodieSparkSqlWriter`, `TestCOWDataSource`, `TestMORDataSource`) pass
  with `spark.hoodie.datasource.write.dataframe.path.enable=true`; every failure is a gap to close or a case the
  gate must fall back on. The default flips only when they are green (current tail in Appendix D).
- [ ] The Spark history server shows the write as one SQL execution that stays catalyst until the routing shuffle.
- [ ] A benchmark against the legacy writer on a skewed upsert workload confirms the shuffle and persist reduction
  translates to wall-clock and memory gains.

## Open questions

- Hierarchical routing-key scheme if insert reducers alone exceed the ~2000-reducer `MapStatus` precision cap.
- Spark version compatibility strategy for the shuffle-reader surface across Spark 3.3 to 4.x.
- Columnar shuffle on Spark 4: the stock exchange is row-based; a Comet or Gluten style columnar exchange needs a
  `ColumnarToRow` at the handle boundary or a columnar writer seam.
- Whether the record-index scan node (Appendix C) should serve reads beyond tagging, which argues for placing it
  below the write module.

| Operation | Tag | Route | Notes |
|---|---|---|---|
| insert | none | insert buckets + small-file padding | |
| upsert | index tag | pinned update reducers + insert buckets | copy-on-write merge; merge-on-read append |

## Appendix B: Proof-of-concept notes

Details from building phases 1 to 4 that sharpened the design.

- **Prepare is fully catalyst.** Key generation is `withColumn` expressions per key generator kind (simple, complex,
  timestamp, custom, non-partitioned, hive-style and URL-encoded partition paths); timestamp conversion is a small UDF
  replicating `TimestampBasedKeyGenerator`. Precombine is a window dedup matching `combineBeforeUpsert`; with
  commit-time ordering (no ordering field) an arbitrary in-batch winner is kept. Options backfill from the table
  config so repeat writes need only the path, and option-vs-table-config identity conflicts are rejected with the
  legacy errors. Because the routing shuffle also co-locates keys, a later flag folds the dedup into the write task
  and drops one exchange.
- **The gate is a fallback wall.** The PoC falls back on operations other than insert and upsert, non-append save
  modes on existing tables, insert dup policies, SQL-internal writes (prepped, MERGE INTO and SQL key generators),
  unknown key generators, bucket, global bloom, in-memory and HBase indexes, custom index classes, dropped partition
  columns, and auto-generated keys. Prepped writes are
  incompatible with the writer's drop-and-regenerate key handling and need their own treatment in phase 5.
- **Global semantics forced a resolve stage.** `_hoodie_is_deleted` threads through as delete records and unmatched
  deletes drop. With `hoodie.index.global.update.partition.path` on, a key that moved partitions fans out into a
  delete against the old file group plus an insert into the new partition; with it off, the row routes to the old
  location. A configured but uninitialized record index falls back to the global join, never the local one.
- **Routing prefixes carry the write mode.** The `s:` padding prefix exists because on merge-on-read `u:` means
  append while padding must still merge. Padding fills small files first without a count pass; the shuffle-stats
  profiler's measured bytes are the eventual budget. Sorted targets still need the UTF-8 key bytes added to the
  shuffle ordering (Appendix D).
- **Merge-on-read.** Deltacommits come from the table type, inserts land in base files for all supported indexes so
  the tagging join stays sound, and appends set the current location so delta write stats book updates correctly,
  with multi-`WriteStatus` closes (log rollover) handled. The sizing plan is slice-based: it never pads a slice that
  has log files (the write-path merge reads only the base file) and skips file groups under pending compaction. Log
  blocks default to parquet in this path so appended rows are consumed as `InternalRow` with no Avro hop.
- **The shuffle-stats profiler avoids Delta's private API surface.** Reduce tasks read contiguous map-output ranges
  through `shuffleManager.getReader`, the public seam AQE uses for skew splits, instead of
  `ShuffleBlockFetcherIterator`. The dependency's key ordering delivers each bucket as a contiguous sorted run.
  Calibration bytes land in commit metadata under `hoodie.dataframe.shuffle.bytes`.
- **The handle seam held.** The merge handle fully drains its incoming iterator before the next bucket, and
  buffered-iterator aliasing is safe. The table's engine context is unusable on executors, so the reader context is
  created on the driver and shipped.
- **Traps for the next implementer.** `HoodieTable.getFileSystemView()` mints a new file-listing view per call while
  `getHoodieView` is the cached one, and `loadAllPartitions()` must run on the instance you query. Avro log blocks
  cannot be read back as Spark records, hence the parquet default above.

## Appendix C: DataFrame-native record-index join

The thin-key lookup in the body is correct and wire-efficient, but the lookup step is RDD code invisible to
catalyst. The obvious rewrite, reading the `record_index` metadata partition as a relation and letting Spark plan a
join, scans the entire index on every write; for a batch touching one percent of keys it reads a hundred times more
index bytes. The DataFrame-native version has to keep two properties: the index side never shuffles, and per-shard
reads are seek-shaped when the batch is small and scan-shaped only when it is large.

- `RliIndexScan`: a leaf node producing N output partitions, one per record-index file group, each streaming
  `(key, partition, fileId)` from that shard's file slice through `HoodieFileGroupReader` in sorted key order.
- `HoodieShardPartitioning`: a catalyst `Partitioning` implementing Hudi's shard hash, so the input-key side is
  exchanged into the same N partitions with a thin projection. Spark's Murmur3 hash does not align with
  `mapRecordKeyToFileGroupIndex`, which is one more reason the write must own the plan.
- `RliShardJoinExec`: a binary node zipping the two sides shard by shard. Per shard it picks lookup mode (sorted
  input keys drive point seeks) or merge mode (one sequential pass over the sorted shard) by the ratio of input keys
  to shard cardinality. Per-shard key min/max prunes shards with no candidates before any read.

Join-back stays a Dataset join on the record key, broadcast when the located set is small. The thin-key lookup
remains the shipping implementation until phase 3 stabilizes; its strategy seam is exactly the seam the
shard-aligned join plugs into. Secondary-index tagging can reuse the same shape.

## Appendix D: Parity tail of the proof of concept

Running the existing suites with the path force-enabled went from 71 failing executions to 13 on the copy-on-write
suites over the gap-closure rounds. The remaining failures cluster as: timestamp key generator output parity, custom
key generator globbing, two option-conflict edge cases, schema evolution wiring (reuse `deduceWriterSchema` plus a
cast/reorder projection of the input), hive-style delete, OCC concurrent updates, table-creation fidelity for payload
class and merge mode (surfaced by the merge-on-read suite, but a copy-on-write hole too), and UTF-8 key ordering for
sorted targets. SQL DML is not covered at all yet.
