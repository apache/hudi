# RFC-110: Native Full-Text Search Index

## Approvers

## Status

State: UNDER REVIEW

## Abstract

Hudi tables often hold free-form text: log lines, support conversations, product descriptions,
audit events. Hudi's existing indexes (record, secondary, column stats, bloom, expression) answer
key lookups and range predicates, but cannot tell a query engine which files contain a word. A
query such as "rows whose `message` contains both `timeout` and `kubernetes`" today scans every
file of the table.

This RFC adds a **full-text index**: a metadata table (MDT) partition that maps each token of one
string column to the base files containing it, and to the row positions inside each file. Engines
use it to skip files and rows that cannot match a token predicate. The index never changes query
results. A lookup returns a **superset** of the files and rows that can match, and the engine
evaluates the predicate again on every row it reads. So a pruned query returns exactly what a full
scan returns.

The design covers both the Java client (Spark) and hudi-rs, which write byte-compatible
records. Delivery is phased (see Rollout). The design reuses the existing MDT machinery for storage, merging,
compaction, file-group routing, timeline and rollback. It adds no new file format.

## Background

### Why the metadata table

The index lives in the MDT for the same reasons the record and secondary indexes do:

- Index updates commit atomically with the data commit, on the same timeline, and roll back with
  it.
- MDT file groups store records as key-sorted HFiles, plus log blocks merged newest-wins. A token
  lookup becomes a sorted point or prefix read.
- MDT compaction, cleaning and archival already exist. The index needs no new table service.

### Relation to existing indexes

| Index | Key | Answers |
|---|---|---|
| Record index | record key | which file group holds a key |
| Secondary index | column value | which record keys hold a value |
| Column stats / expression index | column, file | min/max per file |
| **Full-text index** (this RFC) | token, base file | which base files, and which rows in them, hold a token |

The full-text index is keyed by **base file**, not by record key. A row position inside an
immutable base file is stable, so the index can hand the reader exact row ordinals. A record key
would need a second lookup to reach a row.

### Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Separate segment files beside the table (custom term dictionary, posting and doc files, ranked BM25 search), with the MDT tracking only coverage | A new file format with its own checksums, readers, caches, compaction and cleaning, in two languages. A full-text **filter** needs none of that, because the MDT already provides sorted keyed storage and merging. Ranked search is left out of scope (see Non-goals) and can come later without changing this layout. |
| Key the index by record key | Pruning would need a record-key → file lookup per match, and row positions would not be available. |
| One key per (token, file group) instead of per (token, base file) | A rewrite of one file in the group would have to read, modify and rewrite the shared entries. Keying by the immutable base file lets the writer retire exactly one file with blind writes. |
| Expose raw token lookups and let each engine decide which files are covered | Every engine would re-implement the coverage rule (below). Getting that rule wrong silently drops rows, so it lives in one lookup API per language instead. |
| Filter inside the generic file-slice listing call | It cannot return row sets, and it hides token semantics from the caller. |
| Pass row positions to readers as an `IN` list | Parquet readers prune an `IN` list by min/max only. Contiguous ranges or a native row selection are used instead (see Engine integrations). |

### Goals

- Skip files and rows for token predicates on one string column, on copy-on-write (COW) and
  merge-on-read (MOR) tables.
- Never change query results: pruned results equal a full scan.
- Identical on-disk format from the Java and Rust writers, so either can maintain an index the
  other reads.

### Non-goals

- Relevance ranking, scoring, fuzzy matching, stemming, stop words or language-specific analyzers.
- Pruning on log files of MOR slices (see "MOR: on-demand upkeep").
- Indexing more than one column per index. Create one index per column.

## Implementation

### User interface

Spark SQL:

```sql
CREATE INDEX idx_msg ON events USING full_text(message)
  OPTIONS (update_mode = 'inline', dense_ratio = '0.25', file_group_count = '4');

REFRESH INDEX idx_msg ON events;   -- on_demand indexes only

SELECT * FROM events
WHERE hudi_has_all_tokens(message, 'timeout kubernetes') AND level = 'ERROR';
```

Predicate functions. Each one tokenizes its query string with the index tokenizer:

| Function | True when the text holds… | Pruned by (Spark) | Pruned by (hudi-rs / DataFusion) |
|---|---|---|---|
| `hudi_has_all_tokens(col, q)` | every token of `q` | yes | yes |
| `hudi_has_token(col, t)` | the token `t` | yes | no |
| `hudi_has_any_tokens(col, q)` | at least one token of `q` | later phase | no |
| `hudi_has_token_prefix(col, p)` | a token starting with `p` | later phase | no |
| `hudi_has_phrase(col, q)` | the tokens of `q`, adjacent and in order | yes (as AND of its tokens, then the row check) | no |

Pruning applies to `hudi_has_all_tokens`, `hudi_has_token` and `hudi_has_phrase` (as the AND of
its tokens) when they appear as top-level AND conjuncts. hudi-rs prunes on
`hudi_has_all_tokens(<column>, '<literal>')` only. OR, NOT and prefix pruning is a later phase. Any
other shape is still evaluated correctly, just without the index.

hudi-rs:

```rust
// Create on an existing COW table.
table.create_full_text_index("idx_msg", "message", options).await?;

// Lookup: candidates for the given file slices.
let candidates: Option<Vec<FullTextCandidate>> = table
    .prune_by_full_text(file_slices, "message", &FullTextPredicate::AllTokens(q))
    .await?;
// None => no usable index; every candidate carries `rows: Option<RoaringBitmap>`,
// where None means "read every row of this slice".
```

### Index definition

The index is an entry in the table's index definitions file (by default under
`.hoodie/.index_defs/`), like other MDT-backed indexes:

| Field / option | Value |
|---|---|
| index type | `full_text_index` (SQL: `full_text`) |
| index name | `full_text_index_<user name>` (also the MDT partition name) |
| source field | exactly one column of type STRING |
| version | `2` (see Rollout) |
| `update_mode` | `inline` or `on_demand`. Default `inline` on COW, `on_demand` on MOR. `inline` is rejected on MOR. |
| `dense_ratio` | in (0, 1], default `0.25` |
| `file_group_count` | > 0. Default `ceil(total base file bytes of the table / 1 GiB)` clamped to [4, 64] |
| `tokenizer_version` | `1` |

Creation is rejected on tables using the CUSTOM merge mode.

### Tokenizer (version 1)

1. Split the text on every code point that is neither a letter nor a digit (Unicode, Java
   `Character.isLetter` / `isDigit`).
2. Lowercase each token with the root locale.
3. Drop tokens longer than 64 UTF-8 bytes.
4. Remove duplicates, keeping the first occurrence.

There is no minimum length, no stop words and no stemming. hudi-rs reproduces this exactly. It
carries a code-point table generated from the JDK's `isLetter || isDigit`, and golden tests compare
it with Java output. Any change to the tokenizer is a new `tokenizer_version` and requires a
rebuild.

### Storage layout

**Partition.** One MDT partition per index, `full_text_index_<name>`, with record type `8`
(`MetadataPartitionType.FULL_TEXT_INDEX`). The partition is never enabled by a config flag. It
exists only while an index definition with that prefix exists, and it is listed in
`hoodie.table.metadata.partitions` once built. File group ids are
`full-text-index-<name>-NNNN-0`.

**File unit.** The unit of indexing is one immutable base file, identified by
`<fileId>$b:<baseInstantTime>`. Only base files are indexed. Log files never are.

**Keys.** There are two key families (`$` separated):

| Key | Meaning |
|---|---|
| `U$<fileId>$b:<baseInstant>` | **Coverage marker.** The base file is indexed. Carries `rowCount`. |
| `B$<token>$<fileId>$b:<baseInstant>` | **Posting.** The token occurs in that base file. Carries the row positions. |

**Payload** (`HoodieFullTextIndexInfo`, field `FullTextIndexMetadata` of `HoodieMetadataRecord`):

| Field | Type | Meaning |
|---|---|---|
| `isDeleted` | boolean | tombstone |
| `rowCount` | long | rows in the base file |
| `cardinality` | long | rows holding the token (0 on a marker) |
| `dense` | boolean | `cardinality > rowCount × dense_ratio`. Positions are omitted and every row is treated as a possible match. |
| `positions` | bytes, nullable | portable-format Roaring bitmap of 0-based row ordinals in the base file. Null when dense or deleted. |

The `dense` flag bounds index size. A token present in most rows of a file prunes no rows, so its
positions are not worth storing.

**Routing.** A key is routed to an MDT file group by hashing its file unit, the text after the
second-to-last `$`. The group is `abs(abs(h) % n)`, where `h` is Java `String.hashCode` of the unit (UTF-16 code units, 32-bit wrapping arithmetic) and `n` is the group count, so the marker and
every posting of one base file land in the **same** file group. A lookup for a set of files then
reads only the groups that hold them. hudi-rs reproduces the hash bit-for-bit.

**Merging.** The default MDT newest-wins merge applies. A newer tombstone shadows older entries,
and compaction drops the key.

### Write path

#### Add and retire

Every index change is expressed per file unit:

- **Add** a base file: write its marker `U$…` (with `rowCount`) and one `B$<token>$…` per distinct
  token in the indexed column. A base file without the indexed column (for example, written before
  the column was added) gets **no marker**. It stays uncovered and is never pruned.
- **Retire** a base file: delete its marker and postings. If the old base file can no longer be
  read to enumerate its tokens, only the marker is deleted. That is sufficient, because readers
  ignore postings whose marker is absent (see Read path). The Java writer encodes deletes as
  `isDeleted = true` records. hudi-rs encodes them as delete-block keys. Both merge identically.

#### COW: inline upkeep (`update_mode = inline`)

On every data commit, the MDT writer turns the commit's write stats into index records in the
same MDT delta commit:

- each new or rewritten base file is added;
- the previous base file of each rewritten file group (`prevBaseFile`) is retired;
- for replace commits (clustering, insert overwrite, delete partition), the latest base file of
  each replaced file group is retired.

Compaction commits are skipped, because on COW there are none. On MOR they are handled by
refresh. The Java client and the hudi-rs writer both follow these rules.

#### MOR: on-demand upkeep (`update_mode = on_demand`)

On MOR, new data lands in log files, which are not indexed, so per-commit upkeep would add
nothing. Instead, the index is brought current by `CREATE INDEX` and `REFRESH INDEX`:

1. **Compact.** Schedule a compaction over every slice with log files (a fenced compaction owned by
   the refresh), and run it to completion. Creation fails if another compaction plan is already
   pending. Refresh skips other writers' pending plans and reports them.
2. **Snapshot.** Pick the covered instant: the latest completed instant before the earliest
   pending write.
3. **Diff.** For the latest merged file slices at that instant, add every base-only slice that has
   no live marker, and retire every live marker that is no longer a latest base file. Slices that
   still have log files are left uncovered and reported.
4. **Commit** the index records in one MDT delta commit, under an `indexing` instant. Before
   publishing, the refresh checks that its fence still holds (see Concurrency).

A COW table may also use `on_demand`. Writes then add nothing, and `REFRESH INDEX` brings the
index up to date.

#### Index creation on an existing table

Creation through Spark (`CREATE INDEX … USING full_text`) and through hudi-rs
(`create_full_text_index`, COW only) leave the same state, all at one completed `indexing`
instant:

- the definition in `index.json` (version 2, `tokenizer_version = 1`);
- the partition added to `hoodie.table.metadata.partitions` (inflight list first, then completed);
- `file_group_count` MDT file groups, each with an initial log and, if it holds any entries,
  one key-sorted base HFile.

### Concurrency

- **Inline upkeep** commits with the data commit, so it inherits the table's existing
  concurrency control.
- **CREATE / REFRESH on MOR (Java)** requires a lock provider shared across processes. A missing
  provider or an in-process one is rejected. Two refreshes of one index do not run together: a
  refresh fails if another refresh has a live heartbeat, and it rolls back refreshes whose
  heartbeat expired. The refresh's own compaction is protected by a fence (a nonce in the
  compaction's inflight file). Before publishing, the refresh fails if any of these happened:
  the compaction was completed by another process, a rollback targeted it, its inflight file was
  removed, or its nonce changed. A non-atomic fence (on storage without create-if-absent) must be
  allowed explicitly with `hoodie.index.full_text.refresh.allow.nonatomic.fence=true`.
- **Completed-compaction guard** (delivered with the MOR phase). Any compactor that tries to complete a compaction already
  completed by another process deletes only its own write-stat files and throws, under the table
  lock, before finalizing the write. Without this guard, a second compactor could finalize over
  base files the refresh had just indexed.
- **hudi-rs** has no cross-process lock. Its create (COW only) and its refresh (COW and MOR) require
  `hoodie.index.full_text.refresh.single.writer=true`, an explicit statement that no other writer is active.
  Its refresh checks its heartbeat, its compaction fence, the presence of its own MDT delta commit,
  and that its compaction produced exactly the base files it indexed.

### Read path

#### Lookup and the coverage rule

A lookup takes the file slices the query would read, an indexed column, and a predicate. It
returns the candidates: a subset of those slices, each with an optional row set.

A slice may be **pruned** only if **all** of the following hold:

1. it is base-only (no log files);
2. a live marker exists for exactly its current base file (`U$<fileId>$b:<baseInstant>`);
3. the predicate is false for every row according to the postings of that unit. For AND of
   tokens: some query token has no live `B$` entry for the unit.

Every other slice is kept whole: slices with log files, log-only slices, slices whose base file
has no current marker (not yet indexed, written between refreshes, or missing the column), and
slices whose index entries cannot be read.

For a kept, covered slice, the row set is the intersection of the token positions, where a dense
token counts as every row. It is returned only when it holds fewer rows than the file.

If the index cannot be read at all, the lookup returns "no usable index" and the engine reads every
slice.

The index is used only for snapshot queries at the latest completed instant. Time travel and
incremental queries read without it.

#### Soundness

Let `S` be the slices the engine would scan, and `match(s)` the rows of slice `s` that satisfy the
predicate.

- A slice is removed only under rule 1–3 above. Rule 2 guarantees that the postings consulted
  describe exactly the base file being read: the unit includes the base instant, and a rewritten
  file gets a new unit and a retired old one. Rule 1 guarantees no rows exist outside that base
  file. Rule 3 then implies `match(s)` is empty.
- A row set is a superset of `match(s)`. Every row containing all tokens appears in every token's
  positions (or the token is dense).
- The engine **re-evaluates the predicate on every row it reads**. The index only removes rows,
  so the filter stays in the plan (DataFusion: `Inexact` pushdown).

So `pruned(S) = full_scan(S)` for every query. A row ordinal at or past the base file's row count
means the index does not describe that file, and readers fail the query rather than read a subset.

#### Engine integrations

| Engine | Lookup | File pruning | Row skipping |
|---|---|---|---|
| Spark (Java) | `FullTextIndexSupport` in `HoodieFileIndex` data skipping. The lookup can optionally run on executors, one task per index file group (`hoodie.index.full_text.read.on.executors`). | candidate files | Parquet row skipping from the shipped row set, bounded by `hoodie.index.full_text.rowskip.max.kept.fraction` (0.9), `max.bytes` (1 MiB per file) and `max.total.bytes` (64 MiB per scan). Above the bounds, the whole file or row group is read. |
| DataFusion (hudi-rs `TableProvider`) | `prune_by_full_text` on the slices of the scan. Several all-token conjuncts on one column are joined into one query (a superset). Across columns, row sets are intersected. | candidate slices | a per-file `ParquetAccessPlan` selecting exactly the candidate rows, skipping row groups with none |
| Embedded engines via hudi-rs (e.g. DuckDB) | `prune_by_full_text` | candidate files; uncovered files read whole | `file_row_number` ranges from the row set (nearby ordinals merged). Small files are read whole. |

Engine guidance:

- Keep the token predicate in the query so every read row is re-checked.
- Read uncovered and dense candidates whole.
- When results are filtered per principal (row-level security), `EXPLAIN` should show the unpruned
  plan. A pruned plan reveals which files match a token, including files the caller cannot read.

### Configuration summary

All keys use the `hoodie.index.full_text.` prefix.

| Key / option | Default | Scope |
|---|---|---|
| index option `update_mode` | `inline` (COW), `on_demand` (MOR) | write |
| index option `dense_ratio` | `0.25` | write |
| index option `file_group_count` | `clamp(ceil(bytes / 1 GiB), 4, 64)` | create |
| `hoodie.index.full_text.refresh.allow.nonatomic.fence` | `false` | Java refresh |
| `hoodie.index.full_text.refresh.single.writer` | unset (required `true`) | hudi-rs create/refresh |
| `hoodie.index.full_text.read.on.executors` | `false` | Spark read |
| `hoodie.index.full_text.lookup.exact.keys.max.units` | `0` | Spark read: up to this many file units per lookup task are read by exact key; above it, by key prefix |
| `hoodie.index.full_text.lookup.shards.per.group` | `1` | Spark read: lookup tasks per index file group |
| `hoodie.index.full_text.rowskip.max.kept.fraction` | `0.9` | Spark read |
| `hoodie.index.full_text.rowskip.max.bytes` | `1 MiB` | Spark read |
| `hoodie.index.full_text.rowskip.max.total.bytes` | `64 MiB` | Spark read |

## Rollout/Adoption Plan

- **Phasing.**
  1. Index format, tokenizer, COW inline upkeep and Spark file pruning on
     `hudi_has_all_tokens` (apache/hudi#20054).
  2. MOR on-demand create and refresh, with the completed-compaction guard.
  3. Spark row skipping and the executor-side lookup.
  4. OR, NOT and prefix pruning, each with its soundness argument.

  hudi-rs reads and writes the same format at each phase.
- **Opt-in.** Nothing changes for tables without a full-text index definition. The partition is
  never auto-enabled.
- **Index version.** The layout above is index version 2. Version 1, an earlier layout, had a
  separate presence key family (`P$<token>$…`) beside the positions family, and routed by hashing
  the whole key, so one file's entries spread across all groups. Readers skip a version-1 index
  with a warning and read without it. Rebuild it with `DROP INDEX` / `CREATE INDEX`.
- **Table version.** The index relies on index definitions (`index.json`) and per-index MDT
  partitions, so it needs a table version that has them. On table version 9, the definition must
  carry its version attribute. The exact minimum table version is to be pinned in review.
- **On-demand rollout rule.** `update_mode = on_demand` must not be enabled on a table until
  every process that can compact that table runs a release containing the completed-compaction
  guard. An older compactor can finalize a compaction a refresh already completed, replacing base
  files under an index that claims to cover them. This is a deployment requirement, not enforced
  in code.
- **Mixed writers.** The Java and hudi-rs writers produce identical records and routing, so an
  index created by either is maintained by both on COW. hudi-rs does not yet compact the MDT (see
  Open issues). Tables written only by hudi-rs accumulate MDT log blocks until a Java writer, or
  future hudi-rs compaction, compacts them.
- **Removal.** `DROP INDEX` is expected to remove the definition and the partition through the
  generic MDT index path, as for other MDT indexes. No full-text-specific test covers it yet (see
  Open issues).

## Test Plan

The plan covers the following areas. The implementation PRs carry tests in each one; the review of
each PR confirms that its tests assert the behavior, not just name it.

1. **Tokenizer and record parity (Java ↔ Rust).** Golden cases for the tokenizer; a line-for-line
   comparison of the index records hudi-rs generates against a fixture the Java generator
   produced, including a file large enough to span several Roaring containers; and golden tests
   for the file-unit hash and file-group routing.
2. **Scan-oracle soundness.** For every supported predicate shape, the pruned query must return
   exactly the rows of the same query with the index disabled. This includes a property test over
   generated data asserting that no file with a matching row is ever pruned. Also a check that
   index row ordinals equal the engine's own row index (Spark's Parquet row index, DuckDB's
   `file_row_number`). That check should include a shifted-ordinal control, which must fail.
3. **Lifecycle.** COW upsert, delete, insert overwrite, clustering and rollback retire exactly the
   replaced units. A column added by schema evolution leaves older files uncovered. Time travel
   ignores the index. A reader whose file-slice view and index view sit at different instants
   ignores stale entries.
4. **MOR / on-demand.** CREATE fails while a compaction plan is pending. CREATE and REFRESH
   compact, then index. A lost fence fails without indexing. Recovery works after a failure at each
   step. A refresh fails while another refresh of the same index is running. Slices written
   between refreshes are never pruned. Other writers' pending compactions are skipped and
   reported.
5. **Engine row skipping.** Row sets across row groups. Uncovered files are read whole. An
   unreadable index falls back to a full read. An out-of-range ordinal fails the query. Row sets
   over the size caps fall back to whole files.
6. **Mutation checks (planned).** Remove each soundness rule in turn (marker check, log-file check,
   dense handling, row recheck) and confirm the scan-oracle tests fail. This shows the tests
   detect a broken rule.
7. **End-to-end check.** A table written and indexed by hudi-rs, queried through an embedded
   engine, returns identical rows pruned and unpruned for every query in the suite. This is a
   correctness check, not a benchmark; see Open issues.

## Open issues / future work

- **MDT compaction in hudi-rs.** hudi-rs writes MDT log blocks but does not compact any MDT
  partition, so MDT log blocks accumulate on tables written only by hudi-rs. A
  hudi-rs MDT compaction following the Java semantics is planned (compaction every
  `hoodie.metadata.compact.max.delta.commits`, at an instant below the earliest pending data
  instant).
- **MOR index creation in hudi-rs.** `create_full_text_index` supports COW only.
- **Insert-overwrite retirement across writers.** Verify that hudi-rs retirement of replaced file
  groups matches Java-written logs.
- **Later phases.** MOR on-demand upkeep, the executor-side lookup and Spark row skipping follow
  phase 1 (see Rollout).
- **Cached table properties.** Readers that cache table properties can miss an index created or
  dropped without a data commit.
- **OR, NOT and prefix pruning.** Needs its own soundness rule: NOT takes the complement of a
  superset, so a dense token or an uncovered file must block pruning.
- **Schema drift in embedded consumers.** When files differ in schema, a pruned read that unions
  files by name can expose different columns than the unpruned read. Planning and execution must
  use one schema.
- **Writer checks in hudi-rs.** The hudi-rs writer does not yet check the definition's `version`
  or `tokenizer_version`, and it indexes only `.parquet` base files.
- **DROP INDEX** for a full-text index needs a test covering removal of the definition, the
  partition and the table-config entry.
- **Older Hudi releases** have not been checked for how they treat a `full_text_index_` partition
  listed in `hoodie.table.metadata.partitions`.
- **Minimum table version** for the index is to be pinned in review.
- **Benchmarks.** Measure bytes read and latency, pruned vs unpruned, on tables with files large
  enough to exercise row-range reads.
- **Ranking and richer analyzers** are left for a future RFC, behind a new `tokenizer_version`.
