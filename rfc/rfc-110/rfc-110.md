# RFC-110: Native Full-Text Search Index

## Approvers

## Abstract

Hudi tables often hold free-form text: log lines, support tickets, product descriptions. A query
such as "rows whose `message` contains both `timeout` and `kubernetes`" today reads every file of
the table, because no existing Hudi index can say which files contain a word.

This RFC adds a **full-text index** on one string column of a copy-on-write table. For every word
(token) of that column, the index records which data files contain it and at which row positions.
A query engine uses it to skip whole files, and to skip rows inside the files it still reads.

The index is stored in Hudi's metadata table and is updated in the same transaction as every data
write. Its central invariant is that **the index always equals the table**: for every base file a
query can read, the index lists exactly that file's tokens. Lookups therefore return a superset of
the matching rows, and in a narrow, checked case exactly the matching rows. Pruned queries return
the same results as a full scan. The exact case relies on the vectorized Parquet reader; until a
known gap is closed, that guarantee holds only when the scan actually uses that reader (see Open
issues).

The design reuses existing metadata-table storage, merging and file-group routing. It adds no new
file format and no new table service.

## Background

### Primer: Hudi concepts this design depends on

**Table.** A directory of data files plus a `.hoodie/` directory that holds Hudi's own metadata.
Example: `/data/events/` with data under `/data/events/2026-11-01/` and metadata under
`/data/events/.hoodie/`.

**Base file and log file.** A *base file* is a Parquet file holding complete rows. A *log file*
holds later changes to some of those rows, appended instead of rewriting the base file. Example:
`a1b2c3d4-0_0-5-11_20261101090000000.parquet` is a base file; `.a1b2c3d4-0_..._1.log` is a log file
for the same rows.

**File group and file slice.** A *file group* is the set of files, identified by one *file id*
(`a1b2c3d4-0` above), that holds a fixed set of records over time. Each rewrite produces a new
base file in the same group. A *file slice* is one base file plus the log files written after it.
A query reads the latest slice of each group. Example: group `a1b2c3d4-0` has an old base file
from 09:00 and a newer one from 11:00; only the 11:00 one is in the latest slice. The instant time
in a base file's name (`20261101090000000` above) is its *base instant*: the commit that wrote it.

**Timeline and instants.** Every action on the table is an *instant*: a timestamp, an action type
and a state (requested, inflight, completed), stored under `.hoodie/`. The actions used here:

| Action | Meaning | Example |
|---|---|---|
| commit | a write to a copy-on-write table | an upsert at `20261101110000000` |
| delta commit | a write to a merge-on-read table, and every metadata-table write | |
| replace commit | a write that replaces whole file groups (clustering, insert overwrite, delete partition) | |
| rollback / restore | undo one commit / undo every commit after a point | |
| indexing | build of a new index on an existing table | |

**Copy-on-write (COW) vs merge-on-read (MOR).** On a COW table, an update rewrites the whole base
file that holds the row, so every latest slice is a single base file. On a MOR table, an update
appends a log file and a later *compaction* merges logs into a new base file. This index supports
COW tables only.

**Metadata table (MDT) and its partitions.** The MDT is an internal Hudi table under
`.hoodie/metadata/` that stores facts about the data table: the file listing, column statistics,
record-key locations. Each kind of fact is an MDT *partition* (`files`, `column_stats`, ...). Every
data commit also writes an MDT delta commit with the same instant time, so the MDT changes
atomically with the data. This index is one more MDT partition.

**MDT file groups and HFiles.** Each MDT partition is split into a fixed number of file groups. A
key is assigned to one group by hashing. MDT base files are *HFiles*: files of key-sorted records
that support a point lookup or a key-prefix scan without reading the whole file. Later updates
land in MDT log files and are merged newest-wins: the latest record for a key replaces older
ones, and a record flagged deleted removes the key.

**Table lock.** Hudi coordinates concurrent writers through a configured *lock provider*. Steps
that must not interleave with other writers run while holding this lock.

### Primer: full-text search concepts

**Token and tokenizer.** A *tokenizer* splits text into words called *tokens*. Example: the
tokenizer used here turns `"Timeout on node-7"` into `timeout`, `on`, `node`, `7`.

**Posting and inverted index.** An *inverted index* maps each token to the places it occurs; each
(token, place) entry is a *posting*. Example: `timeout -> {file A: rows 0 and 2}`. A book index
("timeout ... pages 12, 40") is the same idea.

**Row position.** The 0-based ordinal of a row inside one Parquet file. Row `2` of file A is its
third row. Because a base file is never modified after it is written, a position stays valid for
the file's lifetime.

**Superset, then re-check.** If the index returns *at least* every matching row (a superset), the
engine can read only those rows and apply the original predicate to each. Extra rows are filtered
out; no matching row is lost. Example: the index says rows `{0, 2}` may match; row `0` fails the
re-check, row `2` passes; the result equals a full scan.

### Why the metadata table

- Index updates commit atomically with the data commit, on the same timeline.
- HFile key order makes "all files containing `timeout`" a single prefix scan.
- MDT merging, compaction and cleaning already exist, so the index needs no new table service.

### Relation to existing indexes

| Index | Key | Answers |
|---|---|---|
| Record index | record key | which file group holds a key |
| Secondary index | column value | which record keys hold a value |
| Column stats / expression index | column, file | min/max per file |
| **Full-text index** | token, data file | which files, and which rows in them, hold a token |

The index is keyed by data file, not by record key, so it can hand the reader row positions
directly. A record key would need a second lookup to reach a row.

### Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Separate segment files beside the table (term dictionary, posting files, ranked search) | A new file format with its own readers, caches, compaction and cleaning. A token **filter** needs none of that; the MDT already provides sorted keyed storage and merging. |
| Key the index by record key | Pruning would need a record-key-to-file lookup per match, and no row positions. |
| Keep a coverage marker per indexed base file and let readers skip unmarked files | Every reader must then check markers, and keys must carry the base file's instant. Keeping the index exactly equal to the table instead removes both (see Soundness). |
| Pass row positions to readers as an `IN` list | Parquet readers prune an `IN` list only by min/max. Row ranges are used instead. |

### Goals

- Skip files and rows for token predicates on one string column of a COW table.
- Never change query results.
- A fully specified on-disk format (tokenizer, keys, routing hash, payload), so other
  implementations can read and write the same index.

### Non-goals

- Relevance ranking, fuzzy matching, stemming, stop words, language-specific analyzers.
- MOR tables.
- More than one column per index. Create one index per column.

## Implementation

### User interface

```sql
CREATE INDEX idx_msg ON events USING full_text(message)
  OPTIONS (dense_ratio = '0.25', file_group_count = '4');

SELECT id FROM events
WHERE hudi_has_all_tokens(message, 'timeout kubernetes') AND level = 'ERROR';

DROP INDEX idx_msg ON events;
```

(options are defined in Index definition below)

The index type is matched case-insensitively against `full_text` or `full_text_index`. There is no
refresh command: the index is always current. The generic `REFRESH INDEX` statement parses for any
index and does nothing.

#### Predicate functions

Each function takes the text column and a query string. Both sides are tokenized with the index
tokenizer. A null text gives a null result.

| Function | True when the text... | Index condition |
|---|---|---|
| `hudi_has_token(col, q)` | holds every token of `q` (same as below) | AND of tokens |
| `hudi_has_all_tokens(col, q)` | holds every token of `q`; false if `q` has no tokens | AND of tokens |
| `hudi_has_any_tokens(col, q)` | holds at least one token of `q` | OR of tokens |
| `hudi_has_token_prefix(col, p)` | has a token starting with `p`; `p` must be exactly one token | OR of the indexed terms starting with `p` |
| `hudi_has_phrase(col, q)` | holds the tokens of `q` adjacent and in order | AND of tokens, superset only (exact for a one-token phrase) |

The planner prunes with any nesting of AND, OR and NOT over these functions. A predicate is used
for pruning only when its text argument is a plain column reference to an indexed column and its
query argument is a constant string (a literal, or an expression the planner can compute once
before reading any row, such as `concat('time', 'out')`). Anything else, including
an OR branch with a non-indexed predicate, is treated as "may match every row": still evaluated
correctly, just without the index.

### Index definition

The index is an entry in the table's index definitions, like other MDT-backed indexes.

| Item | Value |
|---|---|
| index type | `full_text_index` (SQL `full_text`) |
| index name and MDT partition | `full_text_index_<user name>`, e.g. `full_text_index_idx_msg` |
| source column | exactly one column, type STRING (nested fields allowed) |
| table type | COPY_ON_WRITE only. MOR is rejected at CREATE. |
| merge mode | CUSTOM is rejected (below) |
| index version | `3` (below) |
| MDT record type | `9` (below) |
| option `tokenizer_version` | `1` (the only version) |
| option `dense_ratio` | in (0, 1], default `0.25` |
| option `file_group_count` | > 0; default `ceil(total base file bytes / 1 GiB)` clamped to [4, 64] |

CREATE fails if an index of that name already exists. The partition is never enabled by a config
flag: it exists only while an index definition with the `full_text_index_` prefix exists.

**CUSTOM merge mode.** A table's *merge mode* decides which value wins when two writes touch the
same record. In CUSTOM mode a user-supplied merger decides, and it may produce a value that no
write ever contained. CREATE rejects such a table; the reason given in the code is that the index
could then miss matches.

**Index version.** Every MDT index definition records a layout version, so a reader can tell
whether it understands the stored keys. This RFC defines version `3`; earlier versions are covered
under Rollout.

**MDT record type.** Every MDT record carries a small integer naming its kind, so one record schema
can hold every index. The full-text index uses `9`; `8` is the vector index.

### Tokenizer (version 1)

Example: `"Timeout waiting for kubernetes-API, timeout!"` becomes
`timeout, waiting, for, kubernetes, api`.

1. Split on every code point that is neither a letter nor a digit (Java `Character.isLetter` /
   `Character.isDigit` semantics, Unicode-aware).
2. Lowercase each token with the root locale.
3. Drop tokens longer than 64 UTF-8 bytes.
4. Remove duplicates, keeping the first occurrence.

There is no minimum length. Null or empty text has no tokens. Phrase matching uses a variant that
keeps order, duplicates and over-long tokens. Any change to these rules needs a new
`tokenizer_version` and a rebuild.

Another implementation must reproduce these rules exactly, including Java's
`String.toLowerCase(Locale.ROOT)` applied to each whole token (not code point by code point), and
`Character.isLetter` / `Character.isDigit` as defined by the JDK it is compared with. The code
pins no Unicode version, so two JDKs with different Unicode tables can tokenize rare characters
differently.

### Storage layout

Example: index `idx_msg` with `file_group_count = 2` on a table with data file ids `a1b2c3d4-0`,
`b5e6f7a9-0`, `c9d0e1f3-0`.

```
events/
  2026-11-01/
    a1b2c3d4-0_0-5-11_20261101090000000.parquet      data base files
    b5e6f7a9-0_1-5-12_20261101090000000.parquet
    c9d0e1f3-0_2-5-13_20261101090000000.parquet
  .hoodie/
    metadata/                                         the MDT
      files/ ...                                      other MDT partitions
      full_text_index_idx_msg/                        this index
        full-text-index-idx-msg-0000-0  (file group 0)
          base HFile, sorted by key:
            B\u0001kubernetes\u0001b5e6f7a9-0  -> {rowCount, cardinality, dense, positions}
            B\u0001pod\u0001b5e6f7a9-0         -> ...
            ...                                 (every entry of b5e6f7a9-0 and c9d0e1f3-0)
          log files (later updates, newest wins)
        full-text-index-idx-msg-0001-0  (file group 1)
            B\u0001kubernetes\u0001a1b2c3d4-0  -> ...
            B\u0001timeout\u0001a1b2c3d4-0     -> ...
            ...                                 (every entry of a1b2c3d4-0)
```

In the keys above, `\u0001` stands for one control byte (U+0001), not six characters. `B` is the
tag of the key family; the code names it the positions family. The key layout is defined in
`FullTextIndexUtils`, and the payload in the `HoodieFullTextIndexInfo` record of the MDT Avro
schema (`HoodieMetadata.avsc`).

#### Keys

There is one key family:

| Key | Example | Meaning |
|---|---|---|
| `B<SEP><term><SEP><fileId>` | `B\u0001timeout\u0001a1b2c3d4-0` | term occurs in the latest base file of that file group |

`SEP` is the control character `\u0001`, which the tokenizer never emits. Two derived scans:

| Lookup | Key prefix scanned |
|---|---|
| exact term in all files | `B\u0001timeout\u0001` |
| every term starting with `time` | `B\u0001time` |
| one term in one file | the full key |

The key carries no base-file instant and there is no "file is indexed" marker. A file group with
no entry for a term does not contain that term in its latest base file. This holds because every
commit writes the exact posting changes (see Write path).

#### Payload

Field `FullTextIndexMetadata` of the MDT record, of Avro type `HoodieFullTextIndexInfo`:

| Field | Type | Meaning |
|---|---|---|
| `isDeleted` | boolean | tombstone; the term no longer occurs in the file |
| `rowCount` | long | rows in the base file |
| `cardinality` | long | rows holding the term |
| `dense` | boolean | `cardinality > rowCount * dense_ratio`; positions are omitted |
| `positions` | bytes, nullable | Roaring bitmap (portable serialization) of 0-based row ordinals; null when dense or deleted |

Example: file `a1b2c3d4-0` has 1,000 rows and `timeout` occurs in rows 3, 17 and 950:
`{isDeleted: false, rowCount: 1000, cardinality: 3, dense: false, positions: {3,17,950}}`. If
`error` occurs in 600 rows, with `dense_ratio = 0.25` it is stored as `dense: true` with no
positions, and readers treat every row as a possible match. A term in most rows prunes no rows, so
storing its positions is not worth the space.

#### Routing

A key is routed by its **file id** only, so every entry of one data file lands in one MDT file
group, and a lookup for a set of files reads only the groups that hold them.

```
h = 0; for each UTF-16 code unit c of fileId: h = 31*h + c   (32-bit signed, wrapping)
group = abs(abs(h) % n)          n = file group count; n = 1 -> group 0
```

This is Java `String.hashCode`, written out so other implementations can reproduce it. Example:
`a1b2c3d4-0` hashes to `-1241215453`; with `n = 2` it goes to group 1.

MDT file group ids are `full-text-index-<name with _ replaced by ->-NNNN-0`, e.g.
`full-text-index-idx-msg-0000-0` for partition `full_text_index_idx_msg`.

### Write path

A *unit* is one (old, new) pair of base files to diff; either side may be missing.

```
 data commit (insert / upsert / delete / clustering / insert overwrite)
        |
        v
 write stats (one per file written; prevBaseFile = the base file it replaced)
   stat with prevBaseFile       -> REWRITE (old, new)
   stat without one             -> ADD (new)
   replaced file group          -> RETIRE (latest base)
        |
        v
 tokenize the files of each unit (parallel)
   ADD:     put every term of new
   REWRITE: put every term of new; delete terms of old that new lacks
   RETIRE:  delete every term of old
        |
        v
 index records written in the commit's own MDT delta commit
 (same instant time; data commit completes only after it)
```

Compaction commits are skipped (COW tables have none). Clean writes no index records.

#### Per-commit upkeep

Example: an upsert changes one row of file group `b5e6f7a9-0`. COW rewrites the group's base file.
The writer tokenizes the old and the new base file and writes:

```
put     B\u0001timeout\u0001b5e6f7a9-0   (new term in the rewritten row)
put     B\u0001kubernetes\u0001b5e6f7a9-0 (every term of the new file, with new positions)
delete  B\u0001user\u0001b5e6f7a9-0      (in old file, not in new file)
```

General rules:

- Units come from the commit's base-file write stats. A stat with a previous base file is a
  **rewrite**; otherwise an **add**. In a replace commit, the latest base file of every replaced
  file group is **retired**.
- Both files of a rewrite are tokenized, so the change is an exact diff, not "delete all, re-add".
  Unchanged terms are re-put, because their row positions or row count may have changed.
- Deletes are records with `isDeleted = true` and `rowCount = 0`; newest-wins merging hides the
  older entry.
- A base file without the indexed column (written before the column was added) gets no entries.
  Every term is absent, which is correct: the column is null in every row.
- A base file that cannot be read fails the commit. A retired base file that no longer exists also
  fails it. Silently skipping either would break the invariant.
- Compaction commits are skipped; COW tables have none. Clean removes only older file versions
  and writes no index records.
- Before each commit's MDT update, the writer reloads the table config and index definitions, so
  an index created after the write started still receives that write's entries.
- Parallelism is the number of units, capped by the metadata writer's secondary-index
  parallelism.

#### Creating the index on an existing table

CREATE runs as an `indexing` instant. Data writers may keep committing during the build. The build
path below runs only when the MDT `files` partition is available.

Terms used below:

- **Inflight vs available partition.** The table config lists MDT partitions in two states. An
  *inflight* partition is being built: writers already update it, but readers do not use it. An
  *available* partition is complete and readers may use it. The build ends by moving the partition
  from inflight to available.
- **The flip.** The moment, under the table lock, when the partition is marked inflight. Every
  commit that starts after the flip sees the partition and writes index entries for itself. The
  build records what was in progress at that moment, so it can check those commits later.
- **Catch-up.** The generic index-build step that runs after the initial build: for every instant
  that completed after the index's base instant in the index plan, it checks whether that instant
  updated the MDT, applies it if not, and waits for instants still inflight.

```
 1. size and initialize the MDT file groups of the new partition
 2. under the table lock:
      mark the partition inflight            (from now on every commit updates it)
      reload the data timeline
      capture the "flip": pending commits, completed restores, requested clustering plans
        (a pending restore refuses the build)
      snapshot the latest file slices
 3. outside the lock: tokenize the snapshot's base files, bulk-write them to the MDT
 4. verify the flip, then mark the partition available:
      fail if a commit pending at the flip is still pending
      fail if it completed without writing to this partition
      fail if any restore completed since the flip
```

Why the flip is needed: a commit that was already running when the partition became inflight
might have read the index definitions before the index existed, and so might write no entries.
The snapshot in step 2 cannot include its files either. Verification proves every such commit
did write entries; otherwise the build fails and leaves no usable index.

Rules that protect the build:

- While any full-text partition is inflight, a data commit on a writer without a lock provider is
  refused. With one, it updates the inflight partition like a completed one. Why: the flip and a
  commit are ordered only by the table lock. Without it, a commit could read the index definitions
  before the flip and finish after the snapshot, so neither the build nor the commit would index
  its files, and readers would then prune them.
- MDT compaction and log compaction are not scheduled while any full-text partition is inflight.
  Why: the build's initial entries sit in a pending MDT commit; a compaction scheduled now would
  write a newer base file from the log files alone, and that base file would hide those entries.
- A clustering plan that is only requested at the flip does not block the build; when it runs, it
  updates the index like any commit.
- A restore during the build fails the build; a restore completed before scheduling is skipped by
  catch-up.
- The generic MDT initialization at writer start skips this partition type; only the path above
  builds it.

#### Rollback and restore drop the index

Example: commit `20261101110000000` rewrote `b5e6f7a9-0`, and the user rolls it back. The data
group's latest base file reverts to the 09:00 file, but the index holds the 11:00 file's terms
under the same key `B\u0001<term>\u0001b5e6f7a9-0`. Keys carry no base instant, so the stale
entries cannot be told apart.

Rule: before a rollback of a **completed** commit, or a restore, changes any data, every full-text
index on the table is dropped (definition and table-config entry), under the table lock, and its
partition directories are deleted. The user re-runs CREATE INDEX afterwards. This requires a lock
provider, and it is refused while a full-text index build is pending. Rollback of an **inflight**
commit is not affected: the index has no entries for it.

#### Concurrency summary

The table lock is the only mechanism. There is no heartbeat, compaction fence or single-writer
flag. Per-commit upkeep inherits the table's existing concurrency control, because it is part of
the commit's MDT update.

### Read path

```
 SELECT ... WHERE <token predicates>
        |
        v
 file index lists latest file slices (via the MDT, at MDT instant M)
        |
        v
 index lookup, same MDT snapshot M ----------------------------------+
   slices with log files: kept whole                                 |  on the driver, or as
   base-only slices: evaluate condition per file                     |  one task per (index
     pass 1: presence of each term   -> prune files                  |  file group, shard)
     pass 2: positions               -> prune files, build row sets  |
        |                                                            |
        v                                                            |
 per kept file: row set (superset) or "read whole"  <----------------+
        |
        v
 Parquet reader: read only pages / row groups holding the rows
        |
        v
 Filter re-evaluates the predicate on every row read
 (dropped only on the exact path, below)
```

The *file index* is the engine component that lists the files a query must read (in Spark,
Hudi's `HoodieFileIndex`); index-based pruning runs inside it. *Per-file metadata* is a set of
constant key-value pairs the engine attaches to one file of the scan and hands to that file's
reader; the row set travels this way.

#### When the index is used

The lookup is used only when all of these hold:

- the MDT is enabled, the listing came from it, and at least one completed full-text index of
  version 3 exists;
- the query is a snapshot query. Time travel is allowed only when its as-of instant is at or
  after the latest completed commit; incremental queries and older time travel are not pruned;
- data skipping is enabled for the read (`hoodie.enable.data.skipping`).

Row sets are additionally computed only for COW tables, when the query has at least one data
filter (a filter on non-partition columns), the scan supports per-file metadata, and the session's
vectorized Parquet reader flag (`spark.sql.parquet.enableVectorizedReader`) is on. If the lookup for row sets fails, it logs a warning and the files are read whole.

#### Snapshot consistency

The index is read through the same MDT reader, at the same MDT instant, that produced the file
listing. If an index partition has no slices in that snapshot, there is no pruning. Lookup caches
are keyed by file id plus base instant, and by MDT instant, so a long-lived listing keeps using
the entries of its own snapshot.

#### Evaluation

Each condition node yields two row sets per file:

- `sup`: rows that **may** match (a superset);
- `sub`: rows that **certainly** match (a subset).

| Node | sup | sub |
|---|---|---|
| term absent in file | none | none |
| term with positions `P` | `P` | `P` |
| term present, positions not read or dense | all rows | all rows if `cardinality = rowCount`, else none |
| AND | intersection of sups | intersection of subs |
| OR | union of sups | union of subs |
| NOT x | all rows minus `sub(x)` | none |
| phrase (2+ tokens) | sup of AND of its tokens | none |
| not indexable (`Unknown`) | all rows | none |

A file is pruned when its `sup` is empty. Its row set is `sup`, sent only when it has fewer rows
than the file.

When positions are read depends on the step:

- **File pruning on the driver** reads positions only when they can prune more files than presence
  can: an AND of two or more indexed conjuncts, or a NOT over an indexed one. Otherwise pass 2 is
  skipped and each present term counts as "all rows". Consequence: a predicate with a single
  indexed term prunes files on presence alone.
- **Row sets** (and the executor lookup) read the positions of every non-dense term of the
  condition, so even a single-term predicate gets a row set when its positions are stored. Only
  dense terms, and prefixes matching more than 1,000 terms, are evaluated on presence alone; such
  a file is kept without a row set unless another term narrows it.

#### Where the lookup runs

| Mode | How |
|---|---|
| driver (default) | presence by key-prefix scan; positions by exact keys, as a distributed job when more than 10,000 keys |
| executors (`hoodie.fulltext.index.read.on.executors=true`) | one job; one task per (index file group, shard) that holds a requested data file; each task reads its slice as of the pin, by exact keys or by term prefix, evaluates its part of the condition, and the driver combines the parts |

Terms in this table:

- **Shard.** The requested data files that route to one index file group are split into
  `hoodie.fulltext.index.lookup.shards.per.group` roughly equal parts; each part is one task.
  Every shard of a group reads the same index file slice, so sharding helps mainly with exact-key
  reads.
- **Pin.** A serializable snapshot of the MDT state the driver listed files with (its valid
  instants and latest MDT instant). Tasks read as of the pin, so they ignore MDT commits made
  after planning.
- **Exact key vs prefix.** A task asking about at most
  `hoodie.fulltext.index.lookup.exact.keys.max.units` data files looks up each full key
  `B\u0001<term>\u0001<fileId>`; otherwise it scans every entry of the term (`B\u0001<term>\u0001`)
  in its file group and keeps the requested files.

In executor mode, a failed lookup is remembered for the query. File pruning retries it once and
fails the query if it fails again. Row sets treat it as "read whole" and clear it, so the next
query retries.

#### Row skipping in the Parquet reader

Example: file `a1b2c3d4-0` has 3 row groups of 100,000 rows; the row set is `{12, 250004}`. The
reader keeps the page of the indexed column that holds row 12 in group 0 and the page that holds
row 250004 in group 2, and skips group 1 entirely.

General rules (superset mode):

- The pages of the indexed column define the row ranges. Per row group, keep the pages of that
  column whose row range contains a row of the set, and intersect with any ranges from pushed
  Parquet filters. Every projected column, indexed or not, is then read only for the kept ranges.
  Groups with no kept rows are skipped.
- If the kept rows of a group exceed `hoodie.fulltext.rowskip.max.kept.fraction` of the group,
  the group is read whole.
- Files are sorted by name, so the same files win under the total cap on every planning of the
  same scan; a file whose serialized row set exceeds
  `hoodie.fulltext.rowskip.max.bytes`, or would push the scan total past
  `hoodie.fulltext.rowskip.max.total.bytes`, gets no row set and is read whole.
- If the reader cannot plan the skip (reader internals unavailable, a column without a Parquet
  offset index, any planning error), it logs a warning and reads the row group or file whole.

Row skipping is implemented for the vectorized readers of Spark 3.5 and 4.x. The Spark 3.3 and
3.4 readers are unchanged, so those versions get file pruning only. The Spark 4 reader has no
exact mode (below); that is harmless while the rule that relies on it is registered only on
Spark 3.5.1 and later.

The row set reaches the reader as per-file constant metadata under these keys. Their strings are
part of the format: another engine may consume the row set from file metadata keys
`hoodie.fulltext.rowset.*`.

| Key | Value |
|---|---|
| `hoodie.fulltext.rowset.rows` | serialized Roaring bitmap of the row set |
| `hoodie.fulltext.rowset.column` | the indexed column |
| `hoodie.fulltext.rowset.max.kept.fraction` | the kept-fraction threshold |
| `hoodie.fulltext.rowset.exact` | `true` when the set is exact (below) |

#### Exact row sets and dropping the re-check

Example: `SELECT id FROM events WHERE hudi_has_all_tokens(message, 'timeout kubernetes')`. If, for
every file the scan reads, the index alone gives `sup = sub`, the row set is exactly the matching
rows. Re-evaluating the predicate would only cost time, and `message` would not need to be read at
all.

A physical-plan rule (`hoodie.fulltext.exact.drop.recheck.enable`, default `true`) removes the
re-check Filter when all of these hold:

1. The table is COW, and every kept slice is base-only.
2. For each kept file, the conjunction of top-level conjuncts that contain no `Unknown` has
   `sup = sub`, and the file has a row set or every row may match.
3. No row set was dropped by a size cap.
4. The dropped conjuncts are scan data filters answered by the index alone; other conjuncts stay
   in a Filter.
5. The indexed column is read nowhere else (not projected, not used by remaining conjuncts). A
   query that selects `message` keeps the Filter.

On success the rule removes the indexed column from the scan, marks every row set
`hoodie.fulltext.rowset.exact=true`, and attaches the planned file list to the scan, so execution
reads exactly the files planned even if the index changes meanwhile. In exact mode the reader
builds row-level ranges from runs of consecutive ordinals, applies no kept-fraction cap, and
**fails** instead of widening when it cannot plan the skip.

The rule matches a Project, hash aggregate or top-N over a Filter over a Hudi file scan. It is
registered only on Spark 3.5.1 and later; on other versions the Filter always stays and readers
use superset mode.

#### Soundness

**Invariant.** For every file group whose latest slice is base-only and which a query lists, the
index entries `B\u0001*\u0001<fileId>` describe exactly the tokens and row positions of that
latest base file. It is maintained because every operation that changes a latest base file goes
through the commit's MDT update (add, exact diff, retire), creation proves via the flip that no
concurrent commit was missed, and rollback/restore, which would break it, drop the index instead.

**Why every listed base-only slice counts as covered.** Given the invariant, a missing entry
means a missing term. No marker or base-instant check is needed. Slices with log files, and
log-only slices, are always read whole. On COW none should exist.

**Why a superset is safe.** Every node's `sup` contains every row that satisfies it: a term's
positions list every row with the term; AND and OR preserve containment; NOT subtracts only rows
that certainly match the child; `Unknown` keeps everything. The engine then re-evaluates the
predicate with the same tokenizer on every row it reads. So a pruned query returns exactly the
rows of a full scan.

**When the re-check may be skipped.** Only when `sup = sub` for the index-only part on every file,
every row set reached the reader intact, and the reader enforces it at row granularity (or fails).
The remaining non-indexed conjuncts are still evaluated. Only the vectorized reader enforces
exactness. The current code gates the re-check drop only on the session's vectorized-reader flag,
while the scan can still fall back to row-based reading for some schemas, and the row-based reader
ignores the exact flag. Until that gap is closed, "pruned results equal a full scan" holds for an
exact plan only when the scan uses the vectorized reader (see Open issues).

#### Worked example

Table `events` (COW, non-partitioned), columns `id`, `message`. To keep a tiny example readable,
the index uses `dense_ratio = '1.0'`; at the default `0.25`, any term in a 3-row file would be
dense.

**Step 0: initial data (commit `t1 = 20261101090000000`).**

| File (base file of group) | Row | `id` | `message` |
|---|---|---|---|
| `a1b2c3d4-0_..._t1.parquet` | 0 | 1 | `disk timeout on node-7` |
| | 1 | 2 | `user login ok` |
| | 2 | 3 | `Timeout waiting for kubernetes api` |
| `b5e6f7a9-0_..._t1.parquet` | 0 | 4 | `kubernetes pod restarted` |
| | 1 | 5 | `user logout` |
| `c9d0e1f3-0_..._t1.parquet` | 0 | 6 | `cache warmed` |
| | 1 | 7 | `cache miss rate high` |

**Step 1: `CREATE INDEX idx_msg ON events USING full_text(message) OPTIONS (dense_ratio = '1.0',
file_group_count = '2')`.** The build tokenizes all three files. Selected entries:

```
group 1  B\u0001kubernetes\u0001a1b2c3d4-0  rowCount 3  card 1  positions {2}
group 1  B\u0001timeout\u0001a1b2c3d4-0     rowCount 3  card 2  positions {0,2}
group 0  B\u0001kubernetes\u0001b5e6f7a9-0  rowCount 2  card 1  positions {0}
group 0  B\u0001user\u0001b5e6f7a9-0        rowCount 2  card 1  positions {1}
group 0  B\u0001cache\u0001c9d0e1f3-0       rowCount 2  card 2  positions {0,1}
(no timeout or kubernetes entry for c9d0e1f3-0; no timeout entry for b5e6f7a9-0)
```

**Step 2: upsert at `t2 = 20261101110000000` sets `id = 5` to `logout after timeout`.** COW
rewrites group `b5e6f7a9-0` into `b5e6f7a9-0_..._t2.parquet` (rows: `kubernetes pod restarted`,
`logout after timeout`). The commit's MDT delta commit writes:

```
put     B\u0001kubernetes\u0001b5e6f7a9-0  rowCount 2  card 1  positions {0}
put     B\u0001timeout\u0001b5e6f7a9-0     rowCount 2  card 1  positions {1}   (new term)
put     B\u0001logout\u0001b5e6f7a9-0      ... positions {1}
put     B\u0001after\u0001b5e6f7a9-0       ... positions {1}
put     pod, restarted                     ... positions {0}
delete  B\u0001user\u0001b5e6f7a9-0        isDeleted true                     (term gone)
```

Files `a1b2c3d4-0` and `c9d0e1f3-0` are untouched; so are their entries.

**Step 3: `SELECT id FROM events WHERE hudi_has_all_tokens(message, 'timeout kubernetes')`.**
Condition: `timeout AND kubernetes`.

| File | Pass 1 (presence) | Pass 2 (positions) | Outcome |
|---|---|---|---|
| `a1b2c3d4-0` | both present | `{0,2} ∩ {2} = {2}` | read, row set `{2}` (1 of 3 rows) |
| `b5e6f7a9-0` | both present | `{1} ∩ {0} = {}` | pruned: no row holds both |
| `c9d0e1f3-0` | `timeout` absent | not needed | pruned |

For `a1b2c3d4-0`, `sup = sub = {2}`, so on Spark 3.5.1+ with the vectorized reader the plan is
exact: the Filter is dropped, `message` is not read, and the reader returns row 2 only. Result:
`id = 3`. A full scan agrees: only `Timeout waiting for kubernetes api` holds both tokens. Had the
query selected `message`, the Filter would stay; in superset mode the reader keeps whole pages, so
in this 3-row file it reads all three rows and the re-check keeps only row 2.

Pass 2 runs here because the condition has two indexed terms. With a single term, such as
`hudi_has_token(message, 'timeout')`, file pruning stops after pass 1, while the row set still
uses the term's positions: `a1b2c3d4-0` would get row set `{0,2}`, and `b5e6f7a9-0` would be kept
with row set `{1}`.

### Configuration

Index options (set in `CREATE INDEX ... OPTIONS`):

| Option | Default | Meaning |
|---|---|---|
| `dense_ratio` | `0.25` | a term in more than this fraction of a file's rows stores no positions |
| `file_group_count` | `clamp(ceil(base file bytes / 1 GiB), 4, 64)` | MDT file groups of the index |
| `tokenizer_version` | `1` | tokenizer rules |

Read configs (Spark session configs, since 1.3.0):

| Key | Default | Meaning |
|---|---|---|
| `hoodie.fulltext.index.read.on.executors` | `false` | run the lookup as a job, one task per (index file group, shard), instead of on the driver |
| `hoodie.fulltext.index.lookup.exact.keys.max.units` | `0` | a lookup task with at most N data files reads by exact key; above it, by term prefix. `0` = always prefix |
| `hoodie.fulltext.index.lookup.shards.per.group` | `1` | lookup tasks per index file group |
| `hoodie.fulltext.rowskip.max.kept.fraction` | `0.9` | above this kept fraction, a row group is read whole (superset mode) |
| `hoodie.fulltext.rowskip.max.bytes` | `1048576` (1 MiB) | max serialized row set per base file |
| `hoodie.fulltext.rowskip.max.total.bytes` | `536870912` (512 MiB) | max total row-set bytes per scan |
| `hoodie.fulltext.exact.drop.recheck.enable` | `true` | drop the re-check Filter and the indexed column when every file of a COW scan is served exactly |

Writers need a lock provider to commit while an index is being built, and to roll back or restore
a table that has a full-text index.

## Rollout/Adoption Plan

- **Opt-in.** Nothing changes for tables without a full-text index definition. The partition is
  never auto-enabled.
- **Index version.** The layout above is index version 3. Earlier versions used a different key
  layout and routed by hashing the whole key. Writers do not maintain a pre-V3 index and log a
  warning to rebuild it; readers skip it with a warning and read without it. Rebuild with
  `DROP INDEX` then `CREATE INDEX`.
- **No MOR.** CREATE rejects MOR tables. MOR support would need upkeep of log files or an
  on-demand refresh, neither of which is part of this design.
- **Operational impact.** Each commit tokenizes the base files it writes, plus the previous
  version of each rewritten file. Rollback of a completed commit and restore drop every full-text
  index, which must then be recreated. Index creation pauses MDT compaction until it completes.
- **Removal.** `DROP INDEX` removes the index through the generic MDT index path, and also clears
  an `indexing` instant that a crashed creation left pending.
- **Other implementations.** Any writer of the same table must apply the same tokenizer, keys,
  routing hash and payload, and the same per-commit diff rules, or the invariant breaks.

## Test Plan

Existing tests, by area:

1. **Format and tokenizer** (`TestFullTextIndexUtils`). Golden tokenizer cases; phrase token
   sequence keeps order, duplicates and long tokens; key and bitmap round trips; exact-term ranges
   exclude longer terms; V3 routes every entry of a data file to one file group by file id; V3 is
   the current version. `TestFullTextIndexRecordGenerator`: file-group count sizing.
2. **Invariant oracle** (`TestFullTextIndex`). After every COW write operation, and with streaming
   metadata writes, the index equals the tokenized table; an upsert removes exactly the terms the
   rewritten file dropped; clustering, insert overwrite and rollback; a column added by schema
   evolution; two indexes on different columns; index with 4 file groups behaves as with 1.
3. **Soundness.** A property test that no file with a matching row is ever pruned; row-level
   co-occurrence pruning; AND / OR / NOT, prefix and phrase pruning; constant-expression query
   strings; index ordinals equal Spark's Parquet row index across writes.
4. **Creation and concurrency.** Commits landing during a build are indexed by their own MDT
   commits; commits without a lock provider are refused while an index is inflight; creation fails
   and leaves no index when an instant pending at the flip is still pending; a requested-only
   clustering plan does not block creation; restore drops the index before rolling back data;
   DROP INDEX clears a pending indexing instant; catch-up task behaviour
   (`TestIndexingCatchupTask`). Eligibility and keyless tables (`TestFullTextIndex`): CREATE
   rejects CUSTOM merge mode, a non-STRING column and invalid `dense_ratio` / `file_group_count`
   values; a table without record keys is indexed and pruned.
5. **Snapshot consistency.** Reader file slices and index view at different instants; a long-lived
   listing prunes with its own snapshot; a refreshed file index sees new base files; time travel
   to an older instant does not use the index.
6. **Row skipping.** Only pages that may match are read; files or row groups are read whole over
   the size or fraction caps; whole-file fallback when the skip cannot be planned; Hudi on a
   different class loader from Spark; row sets attached per file and none over the cap.
7. **Exact path** (`TestFullTextIndexSharedLookup`). The plan is exact only where the index alone
   answers its conjuncts; a cap-dropped row set is never exact; the rule drops the re-check and
   column only when every file is served exactly; registration and the off switch; adaptive
   re-planning; exact reads return exactly the set, and fail rather than read whole.
8. **Lookup execution.** Executors and driver agree (exact keys, shards, two indexed columns,
   after a rewrite drops a term); one task per (index file group, shard) holding a requested file; pinned
   reads ignore later MDT commits; a failed executor lookup is retried by the next query;
   split-and-combine of a condition equals evaluating it whole (property test).

Missing or partial coverage:

- No test asserts that `DROP INDEX` removes the definition, the partition and the table-config
  entry; the existing drop test checks only the pending-instant cleanup.
- No test checks that CREATE rejects a MOR table. A search of every full-text test source for
  `MERGE_ON_READ` / `mor` finds only a read-path test that changes the table type after the
  index exists.
- No test of an exact plan when the scan falls back to the row-based Parquet reader (see Open
  issues).
- No test of an out-of-range row ordinal.
- No test that the drop rule is absent on Spark 3.4 and 4.x, matching (or contradicting) the
  config documentation.
- No mutation tests (remove one soundness rule, confirm the oracle tests fail).
- No benchmarks of bytes read and latency, pruned vs unpruned.

## Open issues / future work

- **Exactness depends on the vectorized reader.** Exact row sets are enforced only by the
  vectorized Parquet reader; the plan must not drop the re-check when the scan falls back to
  row-based reading (e.g. schemas the vectorized reader cannot batch). Currently gated only on the
  session's vectorized-reader flag. If such a scan reaches the row-based reader, the exact flag is
  ignored and every row of the file would be returned without a re-check. Not yet confirmed
  whether anything upstream prevents this combination.
- **Config doc vs code.** The documentation of `hoodie.fulltext.exact.drop.recheck.enable` says
  Spark 3.4 and later; the rule is registered only on Spark 3.5.1 and later.
- **Files above 2^31 rows are unsupported.** The Parquet reader casts row ordinals to a 32-bit
  `int`, so a base file with more than 2^31 - 1 rows cannot be row-skipped correctly. No check for
  such a file was found.
- **Out-of-range ordinals are ignored.** A row ordinal at or past the file's row count is silently
  ignored and the file is read normally, in both superset and exact mode. It should fail the
  query, since it means the index does not describe that file.
- **MOR tables** are not supported.
- **`tokenizer_version` is not checked by readers.** No reader was found that compares it before
  using the index.
- **Minimum table version.** No full-text-specific table-version check was found in CREATE
  validation; the minimum is to be pinned in review.
- **Older Hudi releases** have not been checked for how they treat a `full_text_index_` entry in
  the table's list of MDT partitions.
- **Readers that do not refresh the file index** may miss an index created or dropped without a
  data commit. Writers reload index definitions per commit; non-refreshing readers are unverified.
- **Rollback cost.** Rollback of a completed commit and restore drop the index; a cheaper path
  would revert the index entries instead.
- **Row-level security.** Nothing in the design hides pruning from `EXPLAIN`; a pruned plan reveals
  which files match a token.
- **Ranking and richer analyzers** are left for a future RFC, behind a new `tokenizer_version`.
