# RFC-118: Unstructured Data Ingestion and Embedding Tables in Hudi Streamer


## Proposers

- @Davis-Zhang-Onehouse

## Approvers
 - @yihua
 - @vinothchandar

## Status

Issue: [#20683](https://github.com/apache/hudi/issues/20683)

> Please keep the status updated in `rfc/README.md`.

## Abstract

RFC-100 gives Hudi a `BLOB` type: a column that holds a file's bytes inline or a reference to bytes stored out of line, and the
`read_blob` function that resolves either form. RFC-102 and RFC-109 make `VECTOR` columns searchable. This RFC keeps such
tables up to date from object storage: when files land in a bucket and are announced by S3 or GCS events, it records each file
version as a blob row, then turns each file into model inputs (text chunks, images, video frames, speech transcripts) and into
embedding vectors, incrementally, once per file version, with failures quarantined instead of failing the pipeline.

This RFC proposes two Hudi Streamer jobs built on one new source, `UnstructuredDataSource`:

1. **Blob job**: reads the cloud storage events table (the one the stock S3/GCS events pipeline already builds) and upserts one
   row per object version into a *blob table*. An object at or below `hoodie.blob.table.inline.max.bytes` is stored inline in
   the row; a larger one is **not copied**: the row holds an out-of-line, unmanaged reference (`managed=false`) to the source
   object where it is, with the size and modification time observed at ingestion. The blob job writes nothing under the
   table's `.hoodie/.blob` folder.
2. **Embedding job**: reads the same events, prepares each object into model inputs (`prep_only`) and optionally computes
   embeddings with a configured model (`prep_and_compute`), upserting one row per input into an *embedding table* with one
   `VECTOR` column per declared model. The only files it writes besides data files are extracted artefacts (the JPEGs of kept
   video frames above an inline threshold), written as managed files under `.hoodie/.blob` inside the round's instant.

Both jobs reuse Hudi Streamer's checkpointing, transformers, error table, table services and commit protocol; the new parts are
the source, a declarative source *contract* the streamer honours, one required transformer per job, and the preparation /
compute libraries behind the embedding transformer.

## Background

- **RFC-100 (Unstructured Data Storage)** defines the `BLOB` logical type (`HoodieSchema.Blob`: inline bytes, or an out-of-line
  reference with path, offset, length and a `managed` flag), its reader (`read_blob`, batched blob reads) and writer phases.
  This RFC writes `BLOB` columns exactly as RFC-100 defines them and adds no storage format. It uses both reference kinds:
  an *unmanaged* reference (a URI with a scheme, owned by the user) for every source object above the inline threshold, and a
  *managed* reference (a path relative to the table, under `.hoodie/.blob`) only for the files the embedding job extracts.
- **RFC-102 / RFC-109** search and index `VECTOR` columns. The embedding table here is an ordinary Hudi table with `VECTOR(n)`
  columns, so both apply unchanged.
- **Hudi Streamer** already turns S3/GCS object notifications into an events table (`S3EventsSource` / `GcsEventsSource`) and
  reads the announced objects as structured files (`S3EventsHoodieIncrSource` / `GcsEventsHoodieIncrSource`). This RFC reads
  the same events table but treats each object as a file to ingest whole.

### Relation to existing work

RFC-100 provides the storage this design writes. #19278 added a separate, simpler path: `UnstructuredFileDFSSource` lists a
folder and writes one row per file (bytes inline or a reference to the original file, Tika text and chunks in a nested column),
and `EmbeddingTransformer` appends one vector from an OpenAI-compatible endpoint. This RFC does not change or remove that path;
the two can be used side by side. Like #19278, it references large files where they are rather than copying them. It differs
in that it is driven by the cloud events table and its checkpoint, versions each object by (modification time, size), keeps
embeddings in their own per-input table with one `VECTOR` column per model, prepares PDF, image, video and speech inputs with
bounded decoders, and pins each table's layout and preparation settings in table config. RFC-102 and RFC-109 apply to the
embedding table as to any table with `VECTOR` columns.

## Implementation

### 1. Shape for users

One source class and a few keys:

| Key | Values | Rule |
|---|---|---|
| `--source-class` (Hudi Streamer) | `org.apache.hudi.utilities.sources.UnstructuredDataSource` | every unstructured stream |
| `hoodie.unstructured.source.mode` | `blob`, `embedding` | required; a table keeps one mode |
| `hoodie.unstructured.source.cloud` | `s3`, `gcs` | required; picks the events table schema |
| `hoodie.blob.table.file.extensions` | `pdf`, `png`, `jpg`, `jpeg`, `gif`, `bmp`, `tif`, `tiff`, `mp4`, `mov`, `avi`, `mkv`, `webm` (default: all) | may only narrow the default; structured types are refused |
| `hoodie.blob.table.inline.max.bytes` | bytes (declared default 1 MiB; 10 KiB on Parquet older than 1.14) | both modes: an object at or below it is carried inline in the source row (the blob table's `blob`, the embedding table's `prepared_image` of an image file); above it, referenced in place (section 2) |
| `hoodie.unstructured.embedding.input.inline.max.bytes` | bytes (declared default 1 MiB; 80 KiB on Parquet older than 1.14) | embedding: a stored input (a video frame JPEG) at or below it is inline, above it a managed file (section 2) |
| `hoodie.unstructured.embedding.mode` | `prep_only`, `prep_and_compute` | required on `embedding`, refused on `blob` |
| `hoodie.unstructured.embedding.models` | comma-separated model aliases | one nullable `VECTOR` column per alias (`prep_and_compute`) |
| `hoodie.unstructured.embedding.model.<alias>.*` | provider, name, dimensions, modalities, column, endpoint, credentials, request/retry bounds | one block per declared model (`prep_and_compute`) |

A job names no transformer, record key, key generator, marker setting or Parquet injector: the source's contract declares them
and the streamer fills them in, refusing a job that sets a conflicting value. User transformers run *after* the required one and
may add nullable columns or filter rows, but may not drop, rename or retype a contract column; a closing schema guard checks the
rows of every round against the table contract.

### 2. Tables

- **Blob table** (record key: `source_path_sha`, `source_modification_time`, `source_file_size`, so a changed object is a new
  row): object metadata columns (path, name, extension, size, content type, modification time) plus one `BLOB` column `blob`.
  - An object at or below `hoodie.blob.table.inline.max.bytes` is read once and stored **inline**.
  - A larger object is **referenced in place**: `blob` is `OUT_OF_LINE` with an unmanaged reference
    (`managed=false`, `external_path` = the object's own URI as listed, for example `s3://bucket/key`, offset 0, length = the
    size its status call observed). The object is not read and nothing is written under `.hoodie/.blob`. A source path without
    a URI scheme is refused, since it would resolve against the table.
  - An object confirmed gone between its announcement and its status call or read is a row with no blob, which the blob job's
    transformer quarantines to the error table ("gone since announced"), or fails the round when the error table is off.
- **Accepted consequences of referencing in place** (part of the design, stated in the config documentation):
  1. A later overwrite or delete of a referenced source object is not frozen. The row keeps the size and modification time of
     ingestion; a reader reads the object as it is then, or fails when it is gone.
  2. Once a large object is overwritten, its version rows all reference the same file: an older version row reads the current
     content, and `read_blob` over several of those rows fails ("Overlapping blob ranges detected"). This is a documented limit.
  3. Readers of the table need read access to the source storage.
  4. Table services and cleaning never touch source objects; the table owns only its data files.
- **Embedding table** (record key: the blob key columns plus `modality` and `chunk_id`): one row per prepared input (text chunk,
  image file, video frame, speech transcript chunk), the input itself (`prepared_text_chunk`, or a `prepared_image` `BLOB`), an
  `aux` map of per-row facts (pages, frame index and time, speech span, `prep_logic_version`), and one nullable `VECTOR(dim)`
  column per declared model (`model.<alias>.column`, default `emb_<alias>`). `prep_only` writes no vector column.
  - `prepared_image` of an **image file** is the file's own blob value: inline at or below the inline threshold, else an
    unmanaged reference to the source object (not a copy), with the same consequences as above; the threshold is
    `hoodie.blob.table.inline.max.bytes`, as for the blob table.
  - `prepared_image` of a **video frame** is a JPEG extracted by the job: inline at or below
    `hoodie.unstructured.embedding.input.inline.max.bytes`, else a **managed** file
    `.hoodie/.blob/[<partition>/]<fileId>_<writeToken>_<instantTime>.bin`, written inside the round's instant after a `CREATE`
    marker of that instant, so the stock marker-based rollback removes it if the round fails. These are the only managed
    out-of-line files of either table. The markers are on by default (`hoodie.write.blob.markers.enable=true`, which also
    requires timeline-server markers and marker-based rollback); with it off, no marker is written and a failed round's frame
    files stay under `.hoodie/.blob`, referenced by no row.
- **Versioning**: the tables record their own layout and schema versions in table config (`hoodie.table.blob.layout.version`,
  `hoodie.table.unstructured.kind`, `hoodie.table.unstructured.schema.version`,
  `hoodie.table.unstructured.key.encoding.version`), and an embedding table records its preparation contract under
  `hoodie.table.embedding.prep.` (the logic version of each input kind, every setting that changes what preparation writes, the
  preprocessor of each file type, the tokenizer and the Java feature release). These are independent of the Hudi table version;
  a stream refuses a table whose versions or preparation contract differ from its own, so a preparation setting is fixed for the
  life of a table.

### 4. A round, end to end

```text
HoodieStreamer.main → StreamSyncService → prepareJob(cfg, props)
  SourceContracts.of(sourceClass, props).prepareJob(props)       // merged copy; a conflicting job setting is refused
StreamSync.<init> (prepared props)
  write config, metrics, error table; meta client (a new table gets contract.tableProperties(): layout/schema versions)
  SourceContracts.validate(contract, basePath, tableConfig)      // existing table: kind, versions, record key
  chain = contract.transformerChain(configured)                  // required transformer first, schema guard last
  SourceContracts.validate(contract, jsc, spark, chain, ...)     // chain planned against the table contract; no data read
StreamSync.syncOnce
  source.fetchNextBatch → events since the checkpoint → UnstructuredObjectMaterializer (one row per object: the latest
    announcement on S3, the first on GCS); rows built lazily: one status call per object (modification time, size), inline
    read ≤ threshold, else an unmanaged in-place reference; the first transformer forces them
  no new data → return, no instant
  blob:
    chain.apply(rows): BlobQuarantineTransformer (gone objects → error table) → user transformers → UnstructuredSchemaGuard
    upsert starts and takes the round's instant as any stock stream does, error table, commit
  embedding (the chain needs the instant):
    start the commit (REQUESTED)
    chain.apply(rows, instant, toInflight):
      EmbeddingTableTransformer runs toInflight (REQUESTED → INFLIGHT, empty inflight file) before it writes, then
        PrepRound (balance, prepare per file, store extracted frames above the threshold under .hoodie/.blob with CREATE
        markers) → [ComputeRound]
      user transformers → UnstructuredSchemaGuard (rows match the table contract)
    upsert takes the instant (InflightTransition), error table, commit
    any throw in the chain → rollback of the instant (marker-based: stored frame files removed), heartbeat released
```

### 5. Failure handling

Every per-file failure is classified: *content* (bad, oversized, gone or changed-since-listed file → the row goes to the error
table with a reason), *transient* (retried in the round with bounded backoff), *platform* (access denied, misconfiguration →
the round fails and rolls back, nothing partial is committed). Decoders run with explicit bounds (PDF stream and object budgets,
image pixel and raster budgets, video frame size and container index checks, a speech duration cap) so one file cannot exhaust
an executor. Provider calls are retried per request and per row; a provider's permanent refusal (credential, quota, unknown
model) or an outage fails the round, which the next sync retries from the same checkpoint. With the error table off, every case
that would write an entry fails the round instead, so no failure is silently dropped.

### 6. Limits and known behaviour

- Only new object versions are ingested. Deletes are not handled: a deleted object's rows stay. The stock GCS events source
  drops notifications that overwrite an existing object.
- One row per object per round: when one object is announced several times in a round, the latest S3 sequencer wins on S3;
  GCS carries no ordering token, so the first announcement is kept.
- Blob table: the four accepted consequences of section 2 (no freezing, the `read_blob` limit after an overwrite, reader
  access to the source, cleaning never touches sources).
- Embedding table: a file whose size or modification time changed between listing and preparation is quarantined ("changed
  since it was listed"); its new version is not ingested in that round. An image row above the inline threshold references the
  source object, so it shares the blob table's consequences.
- The embedding mode, the model of each vector column and every preparation setting are fixed for a table; a change needs a new
  table. The model check runs at the first round with new events.
- Inline thresholds are bounded per task (`*.inline.max.heap.fraction`, default 1/64 of a task's heap share; for the blob key,
  `hoodie.blob.table.inline.ceiling.enforce=false` turns the refusal into a warning). On Parquet older than 1.14, which cannot
  turn off min/max statistics for one column, inline values are capped at 80 KiB.
- `MERGE_ON_READ` blob tables carry rows of up to the inline threshold; the stock log-block and merge buffers are sized for
  small rows, so they need more executor memory per write and read task than a structured table.
- A video job checks on the driver, each round with new events, that the executor heap can hold the frame decodes, and refuses
  the round otherwise.
- Speech comes only from the audio track of video files (audio-only files are not ingested) and needs FFmpeg (section 7). The
  default Whisper model is English (`base.en`); the language is configurable for multilingual models.
- A restore that would roll back a completed embedding round is refused (the files written under the instant before the write
  are not in its write stats); restoring to a later savepoint is allowed.

### 7. Native and third-party dependencies

- **FFmpeg** (video frames, audio decoding) is optional and supplied by the user at runtime. It is reached through
  JavaCV/JavaCPP bindings declared `provided`; the FFmpeg native libraries are LGPL builds and are never bundled (a build rule
  bans them from the bundles, and a bundle check verifies it). The FFmpeg frame source is the default video preprocessor: a
  user who wants it adds the FFmpeg jars to the Spark job; a round with no video runs without them, and the first video without
  them fails the round with a configuration error naming what to add.
- **JCodec** (BSD-2) is a pure-Java frame source for H.264 in MP4 and needs no native library; set
  `hoodie.unstructured.embedding.prep.video.preprocessor.class` to
  `org.apache.hudi.utilities.unstructured.embedding.prep.JcodecVideoFramePreprocessor` to prepare such video without
  FFmpeg. Speech always needs FFmpeg.
- **jtokkit** (MIT) carries the tiktoken BPE vocabularies used for token counts; they are taken under jtokkit's MIT license and
  noted in LICENSE. A `word-count` tokenizer needs no vocabulary.
- **Whisper** transcription uses whisper-jni (Apache-2.0) with whisper.cpp natives (MIT), bundled into the utilities bundle
  with only the Linux x86_64 and aarch64 native folders. Model weights are never shipped; users point at a model file. Speech is
  off by default.
- Test media fixtures are generated by a checked-in script, with a README naming their sources. Each code PR that brings a
  dependency adds its entries to the top-level LICENSE and NOTICE files.

### 8. Edits to existing Hudi code

| Area | Change |
|---|---|
| `HoodieStreamer`, `StreamSync` | job preparation through the source contract; contract validation; table properties on a new table; start the instant before an instant-aware transformer; rollback when it throws |

| `HoodieTable` | marker reconciliation skips marked files under the meta folder (the stored inputs under `.hoodie/.blob`) |

| `CloseableIteratorListener` | releases each per-file iterator of a task once exhausted, instead of at task end |

A stream whose source registers no contract and whose transformers are not instant-aware takes the same streamer path as
today: `prepareJob` is the identity for `SourceContracts.NONE`, and the instant is started before the transformer only when the
transformer asks for it (`InstantAwareTransformer.needsInstant()`). The blob job itself takes that stock path.

## Rollout/Adoption Plan

- Impact on existing users comes from the generic changes of section 8, notably: clustering under the prefer-writer conflict
  strategy with `hoodie.clustering.fail.on.pending.ingestion.during.conflict.resolution` enabled also fails on early-inflight
  ingestion instants; bulk-insert executors accept an instant already moved to INFLIGHT; the row writer applies a configured
  Parquet config injector; restore refuses commits that own unlisted files; serialized records keep one payload copy; BLOB
  reads on MOR and `read_blob` in joins are fixed; iterators are released earlier. The streamer path itself is unchanged for
  sources without a contract and transformers that are not instant-aware; the unstructured jobs are behind a new source class
  and new keys.
- No migration: the tables are new and carry their own layout and schema versions in table config from the first release.
- Development plan: the PR chain below, each PR compiling and tested on its own, each linked to one sub-issue of the Feature
  issue. All PRs target master; each says which PR it is stacked on. The chain ports an implementation that was written when

  34 and 36; PR 37 replaces it with the in-place reference this RFC describes**, and the end state proposed here is the chain

- Follow-ups, each its own PR and sub-issue:
  - **PR 37, blob job references large objects in place** (after the chain). The row of an object above the inline threshold
    becomes an unmanaged reference to the source object; the copy transformer becomes `BlobQuarantineTransformer`, a plain
    transformer that only quarantines gone objects; the copier, its failure classes, the `hoodie.blob.table.copy.*` settings
    and the blob job's timeline-server marker requirement are removed; the four accepted consequences of section 2 are
    documented. Inline behaviour, the inline ceiling and the table layout version are unchanged. The embedding job's stored
    inputs keep their markers.
  - **PR 38, one copy of a serialized record's payload** (`SerializableIndexedRecord`; independent of the chain, based on
    master). It bounds the memory of large blob rows held in spillable maps during MOR merges and upserts. Until it lands, the
    opt-in large-row memory test of PR 12 is known to need it and does not run in default CI.
- Two memory-bound defects found while porting (a run of files that yield no chunk could buffer without bound in the prep
  iterator; PDF extraction could retain a whole page beyond its cap) are fixed within the chain, so its last PR is free of
  them; intermediate PRs may still carry them.

## Test Plan

- Unit tests per component (contract, settings merge and refusals, schema contract, balancing, every preprocessor, every
  provider client against a local HTTP stub, retry and failure classification).
- Functional tests on the local file system with a mock S3/GCS events table feeding both jobs, COW and MOR: a large object
  yields an unmanaged reference to its source URI and nothing under `.hoodie/.blob`; a gone object is quarantined; a blob job
  neither needs nor sets timeline-server markers; an embedding job with video requires them and a failed round removes its
  stored frame files; re-announced objects, the error table, and table version refusals.
- A version-history test asserting the documented behaviour of `read_blob` after a large source object is overwritten.
