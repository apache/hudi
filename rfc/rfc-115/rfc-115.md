# RFC-115: Iceberg-Native Entry Points for Hudi-Managed Iceberg Tables

## Proposers

- @yihua

## Approvers

- @vinothchandar

## Status

> Please keep the status updated in `rfc/README.md`.

## Motivation

The pluggable table format (RFC-93, Iceberg implementation in Apache XTable) lets a Hudi writer keep
an Iceberg table up to date on every commit. To benefit, a user today has to write through Hudi's
entry points: `format("hudi")`, `HoodieCatalog`, `USING hudi`, `connector='hudi'`, or the Hudi
Streamer. For the large population of teams already writing Iceberg tables from Spark, Flink and
Kafka Connect, that is a pipeline rewrite, not a switch, and it is the reason the format has no
adoption path outside of new tables.

Apache DataFusion Comet shows the bar users expect from an accelerator: add one jar and one config,
keep the pipeline, get faster execution, fall back transparently when a plan is unsupported, and see
why in `EXPLAIN`. This RFC proposes the same contract for Hudi's write path, indexing and table
services on existing Iceberg tables: **add a jar and a config, keep writing to the same Iceberg
table in the same catalog, and Hudi takes over the write, the indexes and the maintenance.**

## Abstract

Ship an Iceberg-side plugin that occupies Iceberg's own pluggable seams and delegates to Hudi:

1. **Catalog seam, all engines.** Spark, Flink and Kafka Connect obtain an `org.apache.iceberg.Table`
   from the configured catalog and commit through it. A wrapper catalog loads the user's real catalog
   and returns a table that intercepts every commit, read and maintenance action. This is the commit
   fence and the eject guarantee.
2. **Spark write seam, one config.** `spark.plugins=org.apache.spark.HudiIcebergPlugin` rewrites each
   `spark.sql.catalog.<name>=SparkCatalog` to a subclass whose tables return a `V1Write` backed by
   `HoodieSparkSqlWriter`, and appends a session extension that routes `MERGE`, `UPDATE` and
   `DELETE` to Hudi's SQL commands. Whatever the plugin cannot handle falls back to Iceberg's native
   writer, with the reason visible in `EXPLAIN`.
3. **Maintenance disappears from user DAGs.** `rewrite_data_files`, `rewrite_position_delete_files`,
   `expire_snapshots` and `remove_orphan_files` on a Hudi-managed table become Hudi clustering,
   compaction, clean plus archive, and orphan cleanup; inline and async table services run with
   ingestion.
4. **Adopt and eject are table properties, not migrations.** Setting `hudi.managed=true` on an
   existing Iceberg table bootstraps Hudi metadata from it; unsetting it leaves a valid plain Iceberg
   table.

The pluggable table format remains the publisher: after each Hudi instant completes it commits the
Iceberg snapshot to the user's catalog with the Hudi instant in the snapshot summary. A proof of
concept in Apache XTable covers batch writes, dynamic and static partition overwrite, upserts on
tables with identifier fields, row-level commands, maintenance procedures, adopt and eject,
merge-on-read with deletion vectors (RFC-114) and Structured Streaming on Spark 3.4 (Appendix C).

## Background

### What Iceberg users run today

Spark batch and SQL through `SparkCatalog` or `SparkSessionCatalog` with the Iceberg extensions is
the dominant shape, followed by Flink SQL and DataStream sinks and the Kafka Connect Iceberg sink.
All three obtain an interface-typed `Table` from the catalog and commit through
`newAppend`, `newRowDelta`, `newOverwrite` and `newReplacePartitions`. The pain points the plugin
addresses are the ones Hudi already solves for its own tables: upsert cost without a record-level
index, equality-delete pile-up on streaming upserts, and maintenance jobs that users must schedule
and size themselves.

### Why "switch to Hudi's entry points" is not seamless

Hudi's Spark integration assumes a `USING hudi` catalog table and Hudi-specific write options
(table name, record key, partition path, key generator); `HoodieCatalog` is a different catalog
implementation rather than a wrapper; Flink and Kafka Connect need a different connector. None of
that can be swapped in by configuration alone.

### Iceberg's pluggable seams

`catalog-impl` and `CatalogUtil.loadCatalog` (every engine), `SparkCatalog.buildIcebergCatalog`
and `SparkTable.newWriteBuilder` (Spark), `SparkSessionExtensions` with rule and parser injection,
`BaseProcedure` loading through the catalog, and `TableOperations` behind `BaseTable`. Each is a
public extension point, which is what makes a jar-and-config integration possible without forking
Iceberg.

## Implementation

### Architecture

```
user's Spark job                       (unchanged: spark.sql.catalog.prod=SparkCatalog, type=glue,
   |                                    spark.sql.extensions=IcebergSparkSessionExtensions)
   | + spark.plugins=org.apache.spark.HudiIcebergPlugin
   v
HudiIcebergPlugin (driver plugin)
   rewrites spark.sql.catalog.<n> -> HudiSparkCatalog, appends HudiIcebergExtensions
   |
   +-- HudiSparkCatalog extends SparkCatalog
   |      buildIcebergCatalog -> HudiIcebergCatalog(inner catalog)      <- commit fence, adopt/eject
   |      loadTable           -> HudiSparkTable extends SparkTable
   |         newWriteBuilder  -> V1Write over HoodieSparkSqlWriter      <- INSERT, append, overwrite
   |         (unsupported write -> super.newWriteBuilder, foreign snapshot, reason tagged)
   |      loadProcedure       -> HudiRedirectedProcedure               <- rewrite_data_files -> clustering, ...
   |
   +-- HudiIcebergExtensions (SparkSessionExtensions, appended after Iceberg's)
          parser: converts Iceberg's UPDATE/MERGE nodes back to Spark's for managed tables
          rules:  MergeIntoTable/UpdateTable/DeleteFromTable -> Hudi upsert/delete plans
          explain: which writes were routed and why others fell back
   |
   v
Hudi write path (HoodieSparkSqlWriter, indexes, table services)
   |
   v
IcebergTableFormat (pluggable table format, XTable)  -> Iceberg snapshot in the user's catalog
```

### Behavior derived from Iceberg metadata

The plugin never asks the user for Hudi configuration. The table identifier gives the Hudi table
and database name; the table location is the Hudi base path (`.hoodie/` sits beside `metadata/`);
identifier fields become the record key and select upsert, otherwise the table is key-less with
auto-generated keys and insert; identity partition transforms become Hive-style partition paths and
time transforms become the timestamp key generator; `write.merge.mode=merge-on-read` selects a
merge-on-read table with updates written as positional deletes and inserts (RFC-114); target file
size and compression codec map to their Hudi counterparts. Bucket and truncate transforms,
branch and WAP writes and schema merge on write are unsupported in v1 and fall back to Iceberg's
writer. The full mapping is in Appendix A.

### Foreign commits

Any commit on a managed table that did not originate from Hudi (a fallback write, a Flink or Kafka
Connect commit, a schema DDL) arrives at the wrapper catalog. Two policies: **ingest** registers the
added and removed files and deletion vectors as a Hudi commit and replays schema changes into the
Hudi table schema, so Hudi's file-group view and table services see them; **reject** fails the
commit with a clear error. Ingest is the seamless answer and is required for the Flink and Kafka
Connect commit-fence mode; reject is the safe v1 default until ingest exists. Today the pluggable
table format skips snapshots without its metadata marker, which is the tolerate half of ingest.

### Hudi-side prerequisites

Ordered by leverage; the first two are in the RFC-114 companion PR.

1. **Persist `hoodie.table.format.*` keys in `TableBuilder.set`** so the format receives its
   settings from the first commit.
2. **Tolerate data files Hudi did not name in the file-system view**, so an adopted table with
   Iceberg-written files, or a table that received a foreign write, still builds file groups.
3. **Thread catalog configuration into the format plugin.** `IcebergTableFormat.init(Properties)`
   discards its argument and the plugin commits through `HadoopTables`; the catalog implementation,
   name, namespace and options must be persisted in `hoodie.properties` so that Streamer, Flink and
   async table service jobs publish to the same catalog with the catalog commit as the atomic fence.
4. **Metadata table coexistence.** The format currently forces the metadata table off and the
   plugin's `HoodieTableMetadata` lists the file system; the performance case (record index upsert,
   data skipping) needs the metadata table writer allowed under a non-native format. The SPI also
   lacks lock-provider and conflict-resolution hooks, which multi-writer needs.
5. **Route the file-system view through the format's metadata factory.** `FileSystemViewManager`
   instantiates `FileSystemBackedTableMetadata` directly when the metadata table is off, bypassing
   `getMetadataFactory()`; the embedded timeline server has the same gap.
6. **Return positions from the SPI as plain types.** `HoodieDeleteBlock.getRecordPositions()` exposes
   a RoaringBitmap type that the Spark bundle relocates, so a plugin compiled against `hudi-common`
   fails with `NoSuchMethodError` when only the bundle is on the classpath.
7. **Restore and retention** in the format plugin (savepoint instants keyed by requested time collide
   with the commit they savepoint; snapshot expiry aligned with cleaning, per RFC-114).
8. **`HoodieSparkSqlWriter` and the SQL commands** assume a `USING hudi` catalog table in places
   (`ProvidesHoodieConfig`, `HoodieCatalogTable`); the `V1Write` path must work from a synthesized
   table configuration.

### Where the plugin lives

The Spark pieces depend on `hudi-spark*` and on Iceberg's Spark runtime; the catalog wrapper depends
only on `iceberg-core` and `hudi-common`; the format publisher is the XTable module. The proof of
concept keeps everything in XTable next to `xtable-iceberg-pluggable-tf`. Options are a
`hudi-iceberg-plugin` module here (Spark shims are here, release cadence is Hudi's) or XTable
(publisher is there). This RFC proposes the Spark plugin and the catalog wrapper move to
`apache/hudi` once the SPI prerequisites above land, with the publisher staying in XTable; open for
discussion.

### Packaging

One artifact per Spark minor and Scala binary, with `iceberg-core` and the Iceberg Spark runtime
`provided`: the plugin implements the user's `Catalog` and extends the user's `SparkTable`, so
`org.apache.iceberg.*` cannot be shaded. Hudi's Avro and RoaringBitmap must be relocated exactly as
the Hudi Spark bundle does, or the SPI must stop exposing them. If `hoodie.table.format` names a
format with no service on the classpath, Hudi silently falls back to native; the plugin must detect
that and refuse to write, otherwise data silently stops being published to Iceberg.

## Rollout/Adoption Plan

- **P0, foundation:** Hudi-side prerequisites 1 through 5 above, plus foreign-commit ingest in the
  format plugin.
- **P1, Spark "one config":** plugin, catalog wrapper, `V1Write` append and overwrite, adopt and eject,
  maintenance redirection, kill switches (global, per catalog, per table), `EXPLAIN` fallback
  reasons. Acceptance: Iceberg's own `spark` module tests green with the plugin on, and the table
  read by at least two external Iceberg engines.
- **P2, Spark row-level:** `MERGE`, `UPDATE`, `DELETE` through Hudi commands, merge-on-read with
  deletion vectors, record index; Iceberg's `spark-extensions` row-level suites green with documented
  fallbacks. Structured Streaming through a Hudi-native `StreamingWrite` rather than the staged copy
  of the proof of concept.
- **P3, Flink:** commit fence via `catalog-impl`, then sink routing.
- **P4:** Kafka Connect and Streamer paths, Trino and Athena V2-compatibility mode.
- **Impact on existing users:** none unless the plugin is configured. A managed table can be ejected
  at any time and remains a plain Iceberg table.

## Test Plan

- **Iceberg's own test suites as the parity bar.** Run Iceberg's `spark` and `spark-extensions`
  suites (`TestDataFrameWrites`, `TestSparkDataWrite`, `TestMerge*`, `TestUpdate*`, `TestDelete*`,
  streaming, procedures) with the plugin on; these suites are user code, so they measure "no code
  change" directly.
- **On/off harness.** The same plan with the plugin disabled and enabled, results compared through a
  plain Iceberg reader in a separate JVM without the plugin, plus a Hudi reader. A test labelled as
  falling back must actually fall back.
- **Plugin integration tests** (proof of concept: 15 tests on Spark 3.4, Iceberg 1.11): DDL, inserts,
  DataFrame appends, dynamic and static partition overwrite, upsert via identifier fields, row-level
  commands, clustering and compaction procedures, adopt, eject, native write, re-adopt,
  merge-on-read deletion vectors, streaming micro-batches.
- **Performance claims** follow the project's performance bar: profile first, then measure `MERGE
  INTO` on copy-on-write and merge-on-read with and without the record index, streaming append with
  compaction, and Flink upsert equality-delete pile-up against Hudi merge-on-read, on object storage.

## Appendix A: Iceberg to Hudi behavior mapping

| Iceberg input | Hudi write configuration | Notes |
|---|---|---|
| `TableIdentifier` | `hoodie.table.name`, `hoodie.database.name` | required by Hudi, never typed by Iceberg users |
| `table.location()` | base path | data files stay where Iceberg readers expect them |
| identifier fields present | record key fields, operation `upsert` | same fields Flink upsert and Kafka Connect id-columns use |
| no identifier fields | auto-generated record keys, operation `insert` or `bulk_insert` | key-less table constraints apply |
| identity partition transform | partition path field, Hive-style partitioning | Iceberg's default layout is `f=v`, same as Hudi Hive-style |
| year, month, day, hour transforms | timestamp-based key generator with matching output format | path naming must match Iceberg's transform output |
| bucket, truncate transforms | unsupported in v1, fallback | Hudi bucket index is not an Iceberg bucket partition |
| `write.merge.mode` and friends `= merge-on-read` | `MERGE_ON_READ` with updates as deletes and inserts (RFC-114), format version 3 | `copy-on-write` selects `COPY_ON_WRITE` |
| target file size, compression codec | `hoodie.parquet.max.file.size`, `hoodie.parquet.compression.codec` | |
| distribution mode, sort order | bulk insert sort mode, clustering sort columns | partial |
| snapshot properties, `spark.wap.id` | extra commit metadata copied into the snapshot summary | keeps Flink and Kafka Connect idempotency tokens on foreign commits |
| branch writes, `stageOnly` | unsupported, fallback | branch and tag semantics stay Iceberg-only |
| `mergeSchema`, `ALTER TABLE ADD COLUMN` | schema evolution via commit metadata, DDL replayed from the metadata-only commit | needs the foreign metadata commit handler |

Configuration vocabulary (Comet-style): `spark.hudi.iceberg.enabled` (global kill switch),
`spark.sql.catalog.<n>.hudi.enabled` (per catalog), `spark.hudi.iceberg.write.enabled`,
`spark.hudi.iceberg.rowlevel.enabled`, `spark.hudi.iceberg.maintenance.procedures=redirect|noop|passthrough`,
`spark.hudi.iceberg.foreign-commits=ingest|reject`, `spark.hudi.iceberg.explain.fallback.enabled`,
and `hudi.iceberg.<hoodie key>` as a pass-through for any Hudi write configuration. Managed tables
carry `hudi.managed=true`, `hudi.base-path`, `hudi.table.type`, `hudi.record-key` and the plugin
version as table properties.

## Appendix B: Spark-specific mechanics found by the proof of concept

- `SparkSession.builder().config(...)` re-applies the builder's non-static options on top of the
  `SparkContext` conf and undoes the driver plugin's catalog rewrite; the extension's rule builder
  rewrites again while the analyzer is built, before the first catalog lookup.
- Hudi's writer schema comes from the DataFrame while the Iceberg column may be optional; passing
  the Iceberg schema as Hudi's catalog schema and never tightening nullability in the schema sync
  avoids Iceberg's optional-to-required rejection.
- An unqualified base path derived from the Iceberg location made XTable register the first commit's
  files unqualified and later ones with a scheme, so a replace commit's delete silently missed the
  first file (Iceberg matches paths as strings). The base path is qualified through the Hadoop file
  system; a normalization in `HudiDataFileExtractor` is the upstream fix.
- Spark 3.4 rewrites `DELETE` before any extension rule runs, and Iceberg's 3.4 extension replaces
  `UPDATE` and `MERGE` nodes in its parser; the plugin recognizes the rewritten `ReplaceData` and
  `WriteDelta` plans and injects an outermost parser that converts Iceberg's nodes back for managed
  tables. On 3.5 the conversion is unnecessary.
- `MERGE` semantics: matched rows are the join of target and source projected by the update
  assignments, unmatched rows are the anti-join projected by the insert assignments, unioned into one
  Hudi upsert; key or partition changes, delete actions inside `MERGE`, `NOT MATCHED BY SOURCE` and
  non-key merge conditions are declined with a reason.
- Streaming: `writeStream.format("iceberg").toTable(...)` keeps Iceberg's writer factory for the
  micro-batch (tasks stage parquet files under the data location) and replaces the epoch commit with
  a Hudi write of the staged files followed by their deletion. A re-executed epoch on a key-less
  table writes twice until the batch id is recorded in commit metadata, as Hudi's own streaming sink
  does.
- Iceberg's `SparkCatalog` returns metadata tables whose properties are the base table's, so
  `hudi.managed` leaks to them; the catalog skips `BaseMetadataTable` when wrapping. Another
  session's `CachingCatalog` keeps serving the old snapshot for its cache TTL, exactly as with any
  external Iceberg writer.
- Kryo is a hard requirement of `HoodieSparkSqlWriter`; the plugin disables itself with a named
  warning when `spark.serializer` is not Kryo.

## Appendix C: Proof of concept status

XTable module `xtable-hudi-support/xtable-iceberg-spark-plugin` (Spark 3.4.2, Iceberg 1.11.0,
JDK 17), stacked on the RFC-114 XTable branch, four commits: basic write routing; row-level commands,
maintenance procedures, adopt and eject; merge-on-read with deletion vectors and compaction behind
`rewrite_position_delete_files`; Structured Streaming. `ITHudiIcebergSparkPlugin` 15 of 15 green,
with the pluggable table format module suite and the XTable core Iceberg tests green alongside.

Still open, in priority order: packaging (Spark 3.5 profile and a single bundle relocating
RoaringBitmap and jol like the Hudi bundle); foreign-commit ingest; secrets in persisted catalog
options; declined `UPDATE` and `MERGE` on Spark 3.4 falling back to Iceberg's writer instead of
failing; metadata table and record index under the format; Flink and Kafka Connect commit fence.
